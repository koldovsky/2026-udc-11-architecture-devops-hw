# ADR: Сповіщення та автоматичне повернення посилок

**Статус:** запропоновано  
**Дата:** 2026-11-02

## Context

Сервіс «Поштомат громади» працює як Node.js API + окремий worker із PostgreSQL та SMS-провайдером.

Поточний стан:

- після реєстрації посилка має статус `waiting`, час `arrivedAt`, код і номер комірки;
- worker надсилає лише первинне SMS і позначає його через `notifiedAt`;
- нагадування ще не підтримуються;
- повернення виконується нічним cron-job після 72 годин, тому фактичний час повернення може бути пізнішим;
- поточна модель не має окремого стану комірки або операції її звільнення;
- SMS-провайдер має ліміт 10 повідомлень/с, повторна відправка створює нове платне повідомлення;
- SMS не можна надсилати з 21:00 до 08:00 за київським часом;
- резервне копіювання щодня з 02:00 до 02:30 блокує операції запису;
- відновлення з резервної копії може повернути систему приблизно на 10 хвилин назад.

Явні припущення:

- `arrivedAt` є моментом, від якого відраховуються 24, 48 і 72 години;
- потрібна щонайменше доставка SMS до провайдера, а не гарантована доставка до телефону;
- повернення через 72 години має бути виконане якнайближче до дедлайну, але з допустимою похибкою polling-інтервалу;
- статуси `waiting`, `picked_up` і `returned` залишаються основними статусами посилки;
- комірка може бути звільнена через наявний або новий адаптер locker hardware API;
- повідомлення про повернення відправнику не є обов’язковим, але може бути додане окремою подією.

## Decision

Розширити існуючий worker до єдиного планувальника життєвого циклу посилки. API лише атомарно записує посилку та заплановані повідомлення; зовнішні виклики до SMS-провайдера, поштомата і кур’єрського API виконуються worker-ом.

### 1. Події та outbox

Під час розміщення посилки в одній транзакції:

1. створити посилку зі статусом `waiting`;
2. записати `arrivedAt`;
3. створити три заплановані повідомлення:
   - `arrival` — одразу;
   - `reminder_24h` — `arrivedAt + 24h`;
   - `reminder_48h` — `arrivedAt + 48h`;
4. створити подію аудиту `parcel_placed`.

Для цього додати таблиці на кшталт:

```text
parcel_notifications
- id
- parcel_id
- kind
- due_at
- status: pending | sending | sent | failed
- provider_message_id
- attempts
- sent_at
- last_error
- unique(parcel_id, kind)
```

Outbox потрібен для того, щоб збій SMS-провайдера не скасовував розміщення посилки й не призводив до втрати повідомлення.

### 2. Надсилання SMS

Worker періодично атомарно забирає due-повідомлення через `SELECT ... FOR UPDATE SKIP LOCKED` або еквівалентний механізм.

Для кожного повідомлення:

- перевірити, що посилка досі має статус `waiting`;
- не надсилати нагадування для вже отриманої або повернутої посилки;
- дотримуватися вікна 08:00–21:00 за київським часом;
- застосовувати rate limit провайдера — не більше 10 SMS/с;
- використовувати exponential backoff;
- зберігати `provider_message_id`;
- після успіху позначати повідомлення `sent`.

Якщо дедлайн припав на заборонений нічний час, повідомлення переноситься на 08:00. Це стосується первинного SMS і нагадувань; первинне SMS у такому випадку надсилається при першій дозволеній нагоді після підтвердження розміщення.

Текст первинного SMS:

```text
Посилка чекає у поштоматі №{lockerId}. Код: {code}
```

Тексти нагадувань не повинні містити більше персональних даних, ніж необхідно. Код повторно надсилати можна лише за затвердженим шаблоном і з урахуванням вимоги не дублювати повідомлення через повторний запуск worker-а.

### 3. Точне повернення через 72 години

Замість нічного cron-job додати до worker-а обробку посилок, для яких:

```text
status = waiting
arrivedAt <= now - 72 hours
```

Обробка має бути ідемпотентною та захищеною від подвійного виконання:

1. атомарно захопити посилку;
2. повторно перевірити статус `waiting`;
3. позначити її як таку, що повертається, наприклад `returning`, або встановити `returnStartedAt`;
4. скасувати всі невідправлені нагадування;
5. викликати locker API для звільнення комірки;
6. викликати courier API для повернення відправнику;
7. після успішного прийняття операції оновити:
   - `status = returned`;
   - `returnedAt`;
   - `lockerReleasedAt`;
   - ідентифікатор операції кур’єра;
8. записати події `locker_released` і `parcel_returned`.

Якщо звільнення комірки або виклик кур’єра тимчасово не вдався:

- не позначати посилку остаточно повернутою;
- зберегти помилку та кількість спроб;
- повторити операцію з backoff;
- створити alert після перевищення порогу спроб.

Щоб не втратити посилку між звільненням комірки та викликом кур’єра, операції мають мати ідемпотентні ключі, наприклад `parcel_id + return_operation`. Якщо locker API не підтримує ідемпотентність, це слід додати в адаптер або зафіксувати ручну reconciliation-процедуру.

### 4. Зміни в доменній моделі

Потрібно додати:

- планування повідомлень замість єдиного `notifiedAt`;
- події для розміщення, SMS, отримання, звільнення комірки та повернення;
- статус `returning` або еквівалентний lock/claim-механізм;
- час і результат звільнення комірки;
- ідентифікатори зовнішніх операцій;
- індекси для пошуку:
  - due-повідомлень;
  - посилок `waiting` старше 72 годин.

Операцію `pickup` необхідно зробити конкурентно безпечною: зміна `waiting → picked_up` має виконуватися атомарно. Паралельний процес повернення не повинен обробити посилку, яку щойно забрали.

### 5. Відновлення та експлуатація

Worker має:

- безпечно переживати перезапуск;
- повторно обробляти `pending`, `sending` із простроченим lease та `failed`;
- логувати `parcel_id`, тип операції та зовнішній provider ID;
- мати метрики:
  - кількість pending/failed SMS;
  - вік найстарішого pending-повідомлення;
  - кількість посилок, що очікують повернення;
  - затримку повернення від дедлайну 72 години;
  - помилки locker/courier API.

Під час резервного копіювання записи можуть блокуватися. Worker має обробляти помилки блокування повторно, без втрачених outbox-записів. Після відновлення з backup потрібно перевірити pending-операції та повторно узгодити статуси з поштоматами й кур’єром.

## Consequences

Позитивні наслідки:

- первинне SMS, нагадування та повернення використовують єдиний механізм фонового виконання;
- збій SMS-провайдера не блокує API і не втрачає заплановане повідомлення;
- повторний запуск worker-а не створює дублікати за умови унікальних ключів та ідемпотентності;
- нагадування припиняються після отримання або повернення посилки;
- повернення виконується близько до 72-годинного дедлайну, а не наступної ночі;
- є аудит усіх важливих переходів і зовнішніх операцій;
- рішення відповідає обмеженню бюджету: не потребує окремого брокера повідомлень чи нової інфраструктури.

Негативні наслідки:

- схема бази даних стає складнішою;
- потрібна коректна конкурентна обробка та lease/claim-механізми;
- з’являється розподілена транзакція між БД, SMS, поштоматом і кур’єрським API;
- необхідні додаткові метрики, алерти та reconciliation;
- SMS можуть бути доставлені із затримкою через нічне вікно або недоступність провайдера;
- потрібно врахувати вартість усіх повторних SMS, оскільки провайдер тарифікує кожен повторний запит як нове повідомлення.

## Альтернативи

### Альтернатива 1: залишити cron-job і додати три періодичні скрипти

Окремі cron-задачі запускалися б для:

- первинних SMS;
- нагадування через 24/48 годин;
- повернення через 72 години.

Переваги:

- мінімальні зміни в коді;
- зрозуміле розгортання на наявній VM;
- не потрібен новий scheduler.

Компроміси:

- cron не гарантує точності виконання;
- помилка або пропуск запуску може залишити посилку в комірці;
- складніше забезпечити дедуплікацію SMS;
- виникає кілька незалежних механізмів повторів;
- важче відстежувати стан операції між БД, locker API та courier API;
- поточний запуск о 03:15 очевидно не відповідає вимозі «через 72 години».

Цю альтернативу відхилено через недостатню надійність і складність відновлення після збоїв.

### Альтернатива 2: використати зовнішню чергу або scheduler

Наприклад, Redis/BullMQ, RabbitMQ, cloud scheduler або керований task queue.

Переваги:

- готові delayed jobs, retry, backoff і dead-letter queue;
- зручне горизонтальне масштабування;
- менше scheduler-логіки в application worker;
- краща ізоляція довгих або нестабільних операцій.

Компроміси:

- додаткова інфраструктура та операційні витрати;
- нові секрети, моніторинг і процедура backup/restore;
- бюджет інфраструктури обмежений 60 €/місяць;
- зовнішня черга не усуває потребу в ідемпотентності та узгодженні з PostgreSQL;
- відновлення БД і черги може призвести до розходження станів.

Цю альтернативу залишено як напрям для майбутнього масштабування, але не обрано для поточного обсягу.

### Альтернатива 3: синхронно надсилати первинне SMS у запиті `POST /parcels`

Переваги:

- простий для розуміння потік;
- API може одразу повернути помилку, якщо SMS не відправилось.

Компроміси:

- нестабільність SMS-провайдера погіршує доступність API;
- сканер доставки може повторити запит і створити дубль посилки або дубль SMS;
- HTTP-запит утримує ресурси під час зовнішнього виклику;
- неможливо надійно гарантувати відправку без outbox;
- збільшується час відповіді під час пікових партій у 200–300 посилок.

Цю альтернативу відхилено. API має підтверджувати транзакційне розміщення посилки, а доставку SMS виконуватиме worker.

## Підсумок рішення

Обрати розширення наявного worker-а з транзакційним outbox у PostgreSQL, плануванням SMS на 0/24/48 годин і polling-based обробкою повернення на 72-й годині. Додати ідемпотентні операції, атомарні переходи статусів, звільнення комірки, retry/backoff та операційний контроль за невдалими повідомленнями й поверненнями.
