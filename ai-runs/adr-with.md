Припущення (кожне треба підтвердити)
П1. SMS-провайдер обробляє дані в ЄС. Він уже отримує номери, тож це не нова обробка, але DPO має це підтвердити.
П2. Вебхук звіту про доставку містить id повідомлення, номер одержувача і час.
П3. API повернень служби доставки ідемпотентний за parcel_id: повторний POST /returns для тієї самої посилки не створює другого повернення. Якщо це не так, на нашому боці вистачить стану courier_requested.
П4. «Комірка звільняється» означає таке: код перестає працювати, посилка отримує статус «повертається», служба доставки отримує заявку. Фізично комірка звільняється, коли кур'єр забирає посилку.
П5. «Відправник бачить статус» у системі служби доставки, куди потрапляє наша заявка, а також в адмінці. Окремого SMS відправнику не робимо: юристка каже «не обов'язково».
П6. Нагадування не містять коду. Так я читаю вимогу «той самий код двічі». Текст погоджено юристкою: «Ваша посилка чекає у поштоматі №N. Заберіть до ДД.ММ ГГ:ХХ». Це до 70 символів, тобто одне SMS. Якщо комунікаційна команда захоче код у нагадуванні, це зміна шаблону, а не архітектури.
П7. Відлік 24/48/72 годин іде від arrivedAt, тобто від реєстрації посилки в комірці, а не від моменту надсилання першого SMS.
П8. Обліковий запис SMS використовуємо лише ми. Тому беремо 8/с із ліміту 10/с і лишаємо запас.
Рішення
Усі таймери зберігаються як рядки в окремій таблиці завдань у наявному PostgreSQL. Їх виконує наявний контейнер worker. Нових сервісів немає, вартість 0 €.

1. Таблиця parcel_jobs (outbox + планувальник)

CREATE TABLE parcel_jobs (
  id            bigserial PRIMARY KEY,
  parcel_id     bigint NOT NULL REFERENCES parcels(id),
  kind          text   NOT NULL,  -- arrival_sms | reminder_24h | reminder_48h | return_72h | courier_return
  due_at        timestamptz NOT NULL,
  state         text   NOT NULL DEFAULT 'pending', -- pending | in_flight | done | cancelled | unknown | failed
  attempts      int    NOT NULL DEFAULT 0,
  locked_until  timestamptz,
  provider_id   text,           -- id SMS від провайдера
  last_error    text,           -- без номерів телефонів і кодів
  UNIQUE (parcel_id, kind)      -- одне завдання кожного типу на посилку: дубль неможливий за схемою
);
CREATE INDEX ON parcel_jobs (state, due_at);
2. Створення завдань разом із посилкою
registerParcel в одній транзакції вставляє посилку і чотири завдання:

arrival_sms: due_at = nextSendable(arrivedAt)
reminder_24h: nextSendable(arrivedAt + 24h)
reminder_48h: nextSendable(arrivedAt + 48h). Якщо 48-годинне нагадування відкладуть, це налаштування REMINDER_KINDS, а не код.
return_72h: arrivedAt + 72h рівно, без зсуву, бо це не SMS одержувачу.
nextSendable(t) переносить будь-який момент у проміжку 21:00–08:00 за Europe/Kyiv на найближчу 08:00. Рахується через Intl, без залежностей, з урахуванням переходу на зимовий час (сьогодні, 25.10, саме такий день; це потрібно покрити тестом). Інтервали 24/48/72 год рахуються як фізичний час у UTC, а тихі години як київський годинник.

3. Воркер: дві доріжки
Воркер прокидається кожні 5 с або раніше, якщо найближчий due_at ближчий. Завдання він забирає так:


UPDATE parcel_jobs SET state='in_flight', attempts=attempts+1, locked_until=now()+interval '5 min'
WHERE id IN (SELECT id FROM parcel_jobs
             WHERE state='pending' AND due_at <= now() AND kind = ANY($1)
             ORDER BY due_at LIMIT 50 FOR UPDATE SKIP LOCKED)
RETURNING *;
Доріжка таймерів (return_72h, courier_return) обробляється першою в кожному раунді і не чекає SMS-ліміту. Тому ранковий накопичений обсяг SMS не затримує повернень.
Доріжка SMS (arrival_sms має пріоритет над нагадуваннями) працює через один спільний лімітер на 8/с. Одночасно в обробці лише одне SMS, тож невизначеність після збою стосується не більше ніж одного повідомлення.
4. Як SMS не губиться і не дублюється
У провайдера немає ідемпотентності, тому «рівно один раз» гарантувати неможливо. Ми звужуємо невизначеність до мінімуму і для кожного випадку явно обираємо, як діяти:

Що сталося	Стан	Дія
Перед надсиланням з'ясувалося, що посилку забрали або вона повертається	cancelled	Нічого не шлемо
Перед надсиланням з'ясувалося, що зараз 21:00–08:00 (наприклад, після ретраїв)	pending	due_at переноситься на 08:00
2xx	done + provider_id	Готово
429	pending	due_at = now() + Retry-After. Повідомлення точно не надіслано, повтор безпечний
Запит не пішов (DNS, connection refused)	pending	Повтор з backoff
Інша 4xx (наприклад, неправильний номер)	failed	Алерт черговому, без повторів
5xx, таймаут, обрив після надсилання	unknown	Не повторюємо одразу
Процес упав під час in_flight, locked_until минув	unknown	Так само
Звірка unknown. Новий ендпоінт API POST /sms/delivery-reports зберігає звіти провайдера. Завдання в стані unknown зіставляється зі звітом за номером і часовим вікном (П2). Якщо звіт знайдено, ставимо done. Якщо за годину, тобто за вікно повторів вебхука, звіту немає:

arrival_sms надсилається один раз повторно: втрата коду гірша за малоймовірний дубль;
нагадування не повторюються: втрата нагадування коштує дешевше, ніж дзвінок на гарячу лінію «чи це шахраї».
5. Повернення через 72 години
Одна транзакція:


UPDATE parcels SET status='returning', returned_at=now() WHERE id=$1 AND status='waiting';
-- 0 рядків: посилку вже забрали, завдання стає cancelled
UPDATE parcel_jobs SET state='cancelled' WHERE parcel_id=$1 AND state='pending' AND kind LIKE 'reminder%';
INSERT INTO parcel_jobs (parcel_id, kind, due_at) VALUES ($1, 'courier_return', now());
Після цього завдання courier_return викликає courier.requestReturn з повторами й backoff (П3). Коли API служби доставки підтвердить заявку, статус стає returned. Якщо служба доставки недоступна понад годину, приходить алерт.

pickup стає атомарним: UPDATE parcels SET status='picked_up' … WHERE code=$1 AND status='waiting' RETURNING …, а pending-завдання посилки скасовуються. Гонку «код о 71:59:59 проти повернення о 72:00:00» вирішує той, хто закомітить першим. Двох переможців не буде.

6. Вікно бекапу 02:00–02:30
Воркер не забирає завдань з 01:59 до 02:31. Вікно налаштовується змінною MAINTENANCE_WINDOW. Будь-яку помилку запису в базу він вважає тимчасовою і пробує ще раз пізніше. SMS у цей час і так не надсилаються через тихі години. Повернення, що припадають на це вікно, виконуються близько 02:31, тобто запізнюються не більше ніж на 31 хвилину. Це свідомий компроміс (див. «Наслідки»).

7. Що прибираємо і що додаємо
Cron npm run expire о 03:15 прибираємо. bin/expire-parcels.js перетворюється на страхувальний скрипт (cron щогодини): він створює відсутні завдання для waiting-посилок. Це покриває і посилки, зареєстровані до міграції.
Моніторинг (безкоштовний тариф, алерти в #poshtomat-oncall): вік найстарішого простроченого pending поза тихими годинами й вікном бекапу (понад 5 хв означає алерт), кількість unknown і failed, heartbeat воркера в GET /health.
У логах лише parcel_id і job_id, без номерів і кодів.

Розглянуті альтернативи
А. Redis + BullMQ (delayed jobs) у docker compose на тій самій VM
За: готові відкладені завдання, ретраї й черги з пріоритетами. Таймер спрацьовує з точністю до секунд. Інфраструктура безкоштовна.
Проти:
Подвійний запис. Посилка пишеться в PostgreSQL, завдання в Redis, і спільної транзакції немає. Якщо процес впаде між цими записами, отримаємо посилку без SMS (код загубився) або SMS для посилки, якої немає. Щоб цього уникнути, однаково потрібен outbox у Postgres, тобто фактично наше рішення плюс Redis.
Номери телефонів з'являються в ще одному сховищі. Його треба додати в бекап-runbook, налаштувати AOF-персистентність і задокументувати для DPO.
Ще один сервіс, який черговий має вміти піднімати вночі. Ще ~100–300 МБ RAM на VM з 4 ГБ.
Перша npm-залежність у проєкті, який зараз узагалі не потребує npm install.
Проблему недемпотентного провайдера BullMQ не вирішує: дублі після таймауту лишаються.
Коли варто повернутися: якщо обсяг завдань зросте на порядки і polling Postgres стане вузьким місцем. Для 12 поштоматів цього не очікується.
Б. Керований хмарний планувальник (наприклад, AWS EventBridge Scheduler + SQS або Google Cloud Tasks у регіоні Франкфурт)
За: окремий таймер на кожну подію з точністю до секунд. Не залежить від нашої VM і вікна бекапу, тож повернення о 02:15 спрацює о 02:15. Масштабується без зусиль. За нашого обсягу коштує центи на місяць.
Проти:
Нова стаття бюджету і новий постачальник. Навіть кілька центів треба пояснити в грантовому звіті. Договір обробки даних і погодження з DPO потрібні, бо через сервіс проходить номер або щонайменше parcel_id, за яким його можна знайти.
Хмарний таймер однаково викликає наш вебхук на VM. Якщо VM або база недоступні (той самий бекап), подію все одно треба ставити в чергу й повторювати, тобто без локальної черги не обійтися.
Подвійний запис і недемпотентний провайдер лишаються, як в альтернативі А.
Нова платформа з IAM, секретами й білінгом для команди з двох людей, яка зараз працює з cron і systemd.
Коли варто повернутися: якщо вимога «рівно» стане жорсткою до хвилини навіть уночі, а бекап із блокуванням лишиться.
В. Залишити cron, але запускати щохвилини й сканувати таблицю parcels за часовими полями (reminder1SentAt, reminder2SentAt…)
За: найменше змін. Нова таблиця не потрібна.
Проти: docker compose run щохвилини означає старт контейнера і пул з'єднань 1440 разів на добу. Запуски можуть накладатися, і тоді два процеси надішлють те саме нагадування, якщо не додати блокувань. Логіка «що вже надіслано» розповзається по колонках посилки. Немає місця для стану unknown, звірки й ретраїв з Retry-After. Зимові дублі лишаються як є.
Відкинуто одразу: таймери в пам'яті процесу через setTimeout. Після будь-якого перезапуску або деплою всі таймери губляться, а саме цей сценарій бриф просить виключити.

Наслідки
Позитивні
0 € на інфраструктуру. У бюджеті нової статті немає, рішення виконкому не потрібне.
Нових місць обробки персональних даних немає. Номер лишається в тій самій базі на VM у Франкфурті. Відкриті питання до DPO лише П1 і нова таблиця звітів доставки.
Посилка і всі її таймери створюються атомарно: посилки без SMS не буває. UNIQUE(parcel_id, kind) не дає створити два однакові завдання.
Повернення відбувається через 72 години з точністю до ~5 секунд замість 3–4 діб. Комірки звільняються в середньому на 1–2 доби раніше.
Збої служби доставки більше не губляться: courier_return повторюється до успіху.
Ризик дубля коду зменшується до одного випадку: провайдер прийняв запит, але за годину не надіслав звіту. Ми це свідомо приймаємо, бо втратити код гірше.

Негативні та компроміси
Тихі години мають пріоритет над «щойно». Посилка, покладена о 21:30, отримає SMS із кодом о 08:00. Це вимога юристки, але Ірині варто попередити гарячу лінію.
Повернення в проміжку 02:00–02:30 запізнюються до 31 хвилини через блокування бази під час бекапу. Як це прибрати: окремим ADR перейти на pg_dump без блокування записів. pg_dump сам бере узгоджений знімок, але треба з'ясувати, навіщо зараз синхронно копіюються файли журналу подій.
О 08:00 буде сплеск: вечірні SMS про прибуття плюс нічні нагадування. При 8/с 500 повідомлень розійдуться приблизно за хвилину. Якщо обліковий запис SMS спільний з іншими розсилками громади (П8), ліміт треба переглянути.
Більше SMS. На кожну незабрану посилку до двох додаткових SMS, до +0,07 € з бюджету комунікацій. Ірині варто попередити комунікаційну команду і погодити тексти нагадувань (П6).
Polling раз на 5 с означає кілька легких запитів за індексом. Для нашого обсягу навантаження незначне, але це постійний фон на базі.
Звірка unknown залежить від формату вебхука (П2). Якщо номера там немає, unknown для коду доведеться звіряти вручну: алерт черговому і перевірка в кабінеті провайдера.
Обсяг робіт: міграція схеми, переписування воркера, атомарний pickup, ендпоінт вебхука, страхувальний скрипт, алерти й тести на тихі години, перехід часу, гонку pickup проти повернення і падіння під час in_flight. Якщо доведеться різати обсяг, reminder_48h вимикається налаштуванням без змін архітектури.
Що потрібно від інших до старту
DPO: підтвердити П1, а також зберігання звітів доставки (строк зберігання пропоную 30 днів).
Служба доставки: підтвердити ідемпотентність POST /returns (П3) і як відправник бачить статус (П5).
Комунікаційна команда: тексти нагадувань до 70 символів, з кодом чи без (П6).
Ірина / гаряча лінія: повідомлення про те, що SMS надходять лише з 08:00 до 21:00.
