# ADR-007: Таймери сповіщень і повернення посилок у PostgreSQL (transactional outbox + планувальник у воркері)

**Статус:** запропоновано · **Дата:** 2026-11-03 · **Автори:** команда «Поштомат громади»

Перед тим як писати, я прочитав `materials/`, `docs/ops/`, `app/README.md`, `app/docs/ARCHITECTURE.md` і весь код у `app/src` та `app/bin`.

Одна розбіжність: `AGENTS.md` описує модуль `src/money.ts` і «закладені баги» в ньому. У цій теці такого модуля немає, тож для цієї задачі я ці інструкції не застосовував.

## Контекст

**Що просить бриф (Ірина Коваль, 05.10.2026), у порядку пріоритету:**
1. SMS про прибуття з номером поштомата і кодом.
2. Нагадування через 24 і 48 годин, якщо посилку не забрали. Нагадування через 48 годин можна відкласти.
3. Повернення відправнику рівно через 72 години, а не нічним скриптом, як зараз (фактично через 3–4 доби).

Окремо в брифі є вимога після минулої зими: **код не має губитися, навіть якщо процес упаде посередині, і та сама людина не має отримати той самий код двічі.**

**Як система працює зараз (за кодом):**
- `src/worker.js` кожні 10 секунд вибирає посилки без `notifiedAt`, надсилає SMS і **лише після цього** окремим запитом ставить `notifiedAt`. Якщо процес упаде між успішним `send` і записом, SMS піде вдруге. Саме це сталося взимку. Якщо запустити два воркери, кожне SMS піде двічі, бо вибірка нічого не блокує.
- `bin/expire-parcels.js` запускає cron о 03:15. Скрипт спочатку ставить `returned`, а потім викликає API служби доставки. Якщо API служби доставки впаде, посилка лишиться позначеною як повернена, служба доставки про неї не дізнається, а решта посилок у цьому запуску не обробиться.
- `pickup()` спершу читає посилку, а потім окремо її оновлює, без умови `status = 'waiting'`. Якщо видача і повернення відбудуться одночасно, обидві операції пройдуть.
- `ARCHITECTURE.md` застарів: там 4-значний код і опитування раз на 30 секунд, а в коді 6-значний код і 10 секунд.

**Обмеження з `materials/` і `docs/ops/`:**

| Обмеження | Джерело | Що це означає для рішення |
|---|---|---|

Звіти про доставку приходять вебхуком | sms-provider.md | Гарантувати «рівно один раз» засобами провайдера неможливо. Дублі треба не допускати на нашому боці |

| Сервер — одна VM у Франкфурті, PostgreSQL на ній же, бекапиться щоночі | budget.md, runbook | Дані в PostgreSQL уже в ЄС і вже в бекапі |

**Припущення (явно):**
- **П1.** 72 години рахуються як астрономічний час від моменту, коли посилку поклали в комірку (`arrived_at`), а не від моменту SMS. Перехід на літній чи зимовий час на цей відлік не впливає. Час зберігаємо в `timestamptz` (UTC). Тиха година рахується в зоні IANA `Europe/Kyiv`, без жорстко прописаного зсуву.
- **П2.** Тиха година 21:00–08:00 поширюється і на **SMS про прибуття**. Якщо посилку поклали о 22:00, SMS піде о 08:00. Юридичне правило важливіше за «щойно». Ірині треба це підтвердити, бо фактичний час на отримання для таких посилок скорочується до ~62 годин.
- **П3.** Нагадування **не містять коду**. Текст погоджений юристкою: «Ваша посилка чекає у поштоматі №N до ДД.ММ ГГ:ХХ». Інакше людина отримала б той самий код удруге, а бриф цього прямо не хоче. Ціна: хто загубив перше SMS, з нагадування код не дізнається. Повторне надсилання коду за запитом лишаємо поза цим ADR.
- **П4.** Відправник бачить статус через службу доставки: ми викликаємо `POST /returns` у `courier.js`. Телефону відправника ми не зберігаємо, тому SMS відправнику не шлемо. Юристка вважає окреме повідомлення відправнику не обов'язковим.
- **П5.** API служби доставки `POST /returns` ідемпотентне за `parcel_id`, тобто повторний запит не створить другого повернення. **Це треба перевірити з постачальником.**
- **П6.** Точність «рівно 72 години» означає ±1 хвилину. Виняток — повернення, що припадають на 02:00–02:30 (бекап): вони відбудуться до ~02:31.
- **П7.** Обсяг: ~500 посилок на добу, через 24 години не забрали ~30 %, через 48 годин ~10 %. Ці цифри потрібні лише для оцінки витрат на SMS.

## Рішення

**Таймери живуть як рядки в PostgreSQL. Обробляє їх один цикл-планувальник в існуючому контейнері `worker`. Нових сервісів немає.**

### 1. Модель даних (міграція)

```sql
ALTER TABLE parcels
  ADD COLUMN return_due_at timestamptz;          -- = arrived_at + interval '72 hours'
CREATE INDEX parcels_return_due ON parcels (return_due_at) WHERE status = 'waiting';

CREATE TABLE notifications (               -- outbox SMS одержувачам
  id            bigserial PRIMARY KEY,
  parcel_id     bigint NOT NULL REFERENCES parcels(id),
  kind          text   NOT NULL,           -- 'arrival' | 'reminder_24h' | 'reminder_48h'
  due_at        timestamptz NOT NULL,      -- логічний момент (arrived_at + 0/24/48 год)
  send_after    timestamptz NOT NULL,      -- due_at, зсунутий з тихої години на 08:00 Києва
  state         text   NOT NULL DEFAULT 'pending',
                -- pending | sending | sent | cancelled | uncertain | failed
  attempts      int    NOT NULL DEFAULT 0,
  claimed_at    timestamptz,
  provider_id   text,
  last_error    text,                      -- без номера і без тексту SMS
  UNIQUE (parcel_id, kind)                 -- структурно не більше одного SMS кожного виду
);
CREATE INDEX notifications_due ON notifications (send_after) WHERE state = 'pending';

CREATE TABLE courier_outbox (              -- outbox запитів на повернення
  parcel_id   bigint PRIMARY KEY REFERENCES parcels(id),
  state       text NOT NULL DEFAULT 'pending',   -- pending | done | failed
  attempts    int  NOT NULL DEFAULT 0,
  next_try_at timestamptz NOT NULL DEFAULT now(),
  last_error  text
);
```

Статуси посилки: `waiting → picked_up` або `waiting → return_requested → returned`. Комірка вважається вільною вже на переході в `return_requested`.

### 2. Реєстрація посилки — одна транзакція

`registerParcel` в одній транзакції вставляє посилку з `return_due_at` і три рядки `notifications`. Після цього таймери не можуть «загубитися»: вони існують тоді й лише тоді, коли існує посилка, і потрапляють у нічний бекап разом з нею. Якщо нагадування через 48 годин вирішать відкласти, достатньо не створювати рядок `reminder_48h` (feature-flag у `config.js`).

### 3. Цикл планувальника у `worker` (кожні 5 с)

**a) Повернення:**
```sql
UPDATE parcels SET status = 'return_requested', returned_at = now()
 WHERE status = 'waiting' AND return_due_at <= now()
 RETURNING id;
-- у тій самій транзакції:
INSERT INTO courier_outbox (parcel_id) SELECT ... ON CONFLICT DO NOTHING;
UPDATE notifications SET state = 'cancelled' WHERE parcel_id = ANY(...) AND state = 'pending';
```
Після коміту окремий крок обробляє `courier_outbox` і викликає `courier.requestReturn`. Якщо виклик не вдався, рядок лишається `pending` з експоненційним `next_try_at`, а після N спроб переходить у `failed` і йде алерт. Падіння служби доставки більше не ламає ні наш статус, ні решту посилок.

**b) Видача стає атомарною:** `UPDATE parcels SET status='picked_up' ... WHERE code=$1 AND status='waiting' RETURNING ...`. Якщо видача і повернення збіглися в одну секунду, виграє рівно одна з операцій. Друга побачить 0 рядків. У тій самій транзакції pending-нагадування переходять у `cancelled`.

**c) SMS: «забрати → закомітити → надіслати → закомітити»:**
1. Якщо зараз 21:00–08:00 за Києвом, цикл нічого не надсилає. Цей захист працює навіть тоді, коли черга не встигла розібратися до 21:00.
2. ```sql
   UPDATE notifications SET state='sending', claimed_at=now(), attempts=attempts+1
    WHERE id IN (SELECT n.id FROM notifications n JOIN parcels p ON p.id = n.parcel_id
                  WHERE n.state='pending' AND n.send_after <= now() AND p.status='waiting'
                  ORDER BY n.send_after LIMIT 50 FOR UPDATE OF n SKIP LOCKED)
   RETURNING ...;
   ```
   Коміт відбувається **до** виклику провайдера. `SKIP LOCKED` робить безпечним навіть випадковий другий екземпляр воркера.
3. Виклик провайдера з глобальним темпом **8 SMS/с** (запас нижче ліміту 10). Нагадування не повинні затримувати SMS з кодом, тому `arrival` має пріоритет у `ORDER BY`.
4. Обробка результату:

| Відповідь провайдера | Чи пішло SMS | Дія |
|---|---|---|
| 2xx | так | `state='sent'`, зберігаємо `provider_id` |
| 429 | **ні** (за документацією) | назад у `pending`, `send_after = now() + Retry-After`. Заголовок `Retry-After` поважаємо, на відміну від поточного `sms.js` |
| 4xx (крім 429) | ні | `failed` + алерт (найімовірніше, неправильний номер) |
| 5xx / таймаут / обрив з'єднання | **невідомо** | `uncertain` (див. нижче) |

5. Під час старту воркера всі рядки, що лишилися в стані `sending` довше 2 хвилин, отримують `uncertain`. Це той випадок, коли процес упав між викликом провайдера і комітом.

**d) Що робити з `uncertain`.** Провайдер не має ключа ідемпотентності, тому повністю закрити це вікно неможливо. Воно, однак, звужується до кількох мілісекунд між відповіддю провайдера і комітом. Політика залежить від виду SMS:
- **`arrival`:** код не можна ні загубити, ні надіслати двічі. Тому ми **генеруємо новий код**: старий стає недійсним, а одержувач отримує SMS «Ваш код отримання: NNNNNN. Попередній недійсний». Людина в будь-якому разі має робочий код і ніколи не отримує той самий код двічі. Текст треба погодити з комунікаційною командою.
- **`reminder_*`:** вважаємо надісланим. Загублене нагадування нешкідливе, а дубль дратує.

### 4. Тиха година

`send_after = due_at`. Якщо `due_at` за Києвом припадає на 21:00–08:00, `send_after` = найближча 08:00 за Києвом. Повернення (п. 3a) тихої години не дотримується: це не SMS одержувачу. Якщо нагадування через 48 годин через зсув опиниться пізніше за `return_due_at`, його скасує повернення (п. 3a).

### 5. Експлуатація

- Рядок cron о 03:15 (`npm run expire`) **прибираємо**. `bin/expire-parcels.js` перетворюємо на нічну **звірку**: вона нічого не змінює, а лише шле алерт, якщо знаходить `waiting` з `return_due_at < now() - 5 хв`, застряглі `sending` або `failed` у `courier_outbox`.
- Якщо під час бекапу (02:00–02:30) запис падає, цикл ловить помилку і робить паузу 30 с, без падіння і без crash-loop. SMS у цей час і так не надсилаються через тиху годину. Затримуються лише повернення, до ~02:31 (П6).
- Алерти в #poshtomat-oncall (безкоштовний тариф моніторингу):
  - найстаріший `pending` з `send_after < now() - 5 хв` поза тихою годиною;
  - `uncertain` або `failed` > 0;
  - прострочене повернення > 2 хв (поза 02:00–02:31);
  - `courier_outbox.failed` > 0.
- У логи пишемо лише `parcel_id`, `notification_id`, `kind` і статус. Номер телефону, код і текст SMS туди не потрапляють.
- `ARCHITECTURE.md` оновлюємо, бо він розходиться з кодом, і посилаємося з нього на цей ADR.

## Розглянуті альтернативи

### А. Частіший cron замість нічного (мінімальна зміна)
Запускати `expire` і новий скрипт `remind` щохвилини через cron (`docker compose run --rm worker ...`).
- **Плюси:** найменше коду, звичний для команди інструмент, 0 €.
- **Мінуси:** щохвилини стартує новий контейнер, а запуски можуть накладатися, тож знадобляться ще й lock-файли. Головне ж — проблеми дублів і втрат це не розв'язує: скрипт «вибрав → надіслав → позначив» так само дублює SMS при падінні, а логіка розмазується між cron, worker і скриптами. Фактично це той самий підхід із PostgreSQL, тільки з гіршим планувальником.

### Б. Redis + бібліотека відкладених задач (BullMQ) у docker compose
Кожна посилка ставить у Redis три відкладені задачі на SMS і одну на повернення.
- **Плюси:** готові затримки, повтори й обмеження швидкості. Точність до секунди. 0 € (Redis на тій самій VM, дані лишаються у Франкфурті).
- **Мінуси:** з'являється друге сховище зі станом і персональними даними (номери в payload задач). Його не покриває ні бекап, ні runbook відновлення. Запис «посилка в PostgreSQL + задачі в Redis» — це **dual write**: падіння між двома записами дає посилку без таймерів, тобто код губиться. Саме цього бриф просить уникнути. Додається нова залежність (поточний сервіс без npm-залежностей), ще один компонент для чергового-одинака і окремий пункт для аудиту захисту даних у березні 2027. Дублікати SMS бібліотека теж не прибирає, бо провайдер не має ідемпотентності.

### В. Керований хмарний планувальник і черга (напр., AWS EventBridge Scheduler + SQS + Lambda в eu-central-1)
По одному розкладу на кожну подію, виконавець — функція.
- **Плюси:** точність, масштабованість, не залежить від того, чи жива наша VM. За нашого обсягу витрати лише кілька € на місяць, тобто в межах 60 €.
- **Мінуси:** номери телефонів проходять через сторонній сервіс. Регіон ЄС можна зафіксувати, але це новий обробник даних, і його треба погодити з DPO та внести в повідомлення про обробку. Окремий рахунок означає новий рядок бюджету і пояснення для звіту за грантом. Команда не має досвіду з цими сервісами. Функція все одно ходить у нашу БД на VM, тобто треба відкривати доступ ззовні. Той самий dual write, що і в Б. Для 12 поштоматів це надмірно.

### Г. Таймери в пам'яті процесу (`setTimeout` на кожну посилку)
Відкинуто відразу: перезапуск або деплой (`docker compose up -d`) втрачає всі таймери. Це рівно той сценарій минулої зими.

## Наслідки

**Позитивні**
- Нуль нових компонентів і **+0 € інфраструктури**: лишається ~5 € з 60. Немає нових обробників персональних даних. Дані лишаються в PostgreSQL у Франкфурті й у наявному бекапі.
- Посилка і всі її таймери створюються атомарно, тому код «загубитися» між системами не може. `UNIQUE(parcel_id, kind)` і claim-коміт до виклику провайдера прибирають дублі від перезапусків і від другого воркера. Залишкове вікно невизначеності закрите ротацією коду.
- Повернення відбувається через ≤ 72 години + ~5 с. Комірки звільняються на 1–2 доби раніше, ніж зараз.
- Перегони «видача ↔ повернення» усунуто атомарними умовними `UPDATE`. Збій служби доставки більше не псує статуси.
- Тиха година гарантується двічі: при плануванні й при надсиланні.

**Негативні та ризики**
- PostgreSQL опитується кожні 5 с. Для одиниць тисяч рядків на добу з частковими індексами навантаження мізерне, але кожне опитування бере з'єднання з пулу (`DB_POOL_MAX=4`).
- «Рівно 72 години» не виконується для повернень, що припадають на 02:00–02:30, через блокування бекапу. Рекомендація власникові runbook (Андрію): перейти на `pg_dump` без блокування записів. `pg_dump` і так бере узгоджений знімок. Це також усуне наявну проблему: зараз у цей час падають **видачі** посилок, бо `pickup` пише в БД.
- Посилки, покладені після 21:00, отримують SMS лише о 08:00. Ефективний час на отримання для них менший (П2). Це питання до Ірини і юристки, а не технічне.
- Ротація коду в стані `uncertain` дає рідкісне, але дивне для людини SMS. Текст треба погодити з комунікаційною командою.
- Залежність від П5 (ідемпотентність `POST /returns`). Якщо її немає, потрібен такий самий стан `uncertain` і для служби доставки, з ручною звіркою.
- Обсяг змін: міграція, переписування `worker.js` і `parcels.js`, звірка замість `expire`. Знадобляться нові тести на падіння між кроками, тиху годину на межах і переходи часу, а також на 429 з `Retry-After`. Оцінка: 1,5–2 тижні на двох.
- **Витрати на SMS** (бюджет комунікацій, не ІТ). За П7 це ~500×(0,3+0,1)=~200 нагадувань на добу × 0,035 € ≈ **7 €/день ≈ 210 €/міс**. Тексти мають уміщатися в 70 кириличних символів, інакше кожне SMS тарифікується як два. Якщо 210 €/міс забагато, найпростіший спосіб зекономити — відкласти нагадування через 48 годин, як і дозволяє бриф.

**Що треба зробити поза кодом:** підтвердити П2, П3 і П5. Погодити тексти «нагадування» і «оновлений код» з комунікаційною командою. Прибрати рядок cron о 03:15 після деплою, а не до нього, щоб не лишитися без повернень. Оновити `ARCHITECTURE.md` і runbook.
