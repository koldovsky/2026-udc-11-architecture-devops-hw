# ADR-002: Планування SMS-нагадувань і автоматичного повернення посилок

**Статус:** запропоновано  
**Дата:** 2026-11-02

## Context

Сервіс «Поштомат громади» має такі компоненти:

- HTTP API (`src/server.js`) реєструє посилку через `POST /parcels` і приймає її через `POST /pickup`.
- Сховище посилок містить `arrivedAt`, `status`, `notifiedAt`, `pickedUpAt`, `returnedAt`.
- Worker періодично знаходить ненадіслані повідомлення та відправляє SMS.
- Окрема нічна задача шукає посилки старші за 72 години й запитує повернення через кур’єрський API.
- Поточний worker має лише стан «SMS про прибуття надіслано/не надіслано» і не підтримує повторні нагадування.
- Поточна логіка повернення не звільняє комірку явно та може бути виконана конкурентно кількома процесами.
- У коді використовується 6-значний код отримання, хоча документація згадує 4-значний код. У цьому ADR приймаємо 6-значний формат як фактичний контракт.

Потрібно:

1. Надсилати SMS одразу після розміщення посилки.
2. Надсилати нагадування через 24 і 48 годин після розміщення.
3. Через 72 години повернути посилку відправнику, звільнити комірку та встановити статус посилки.

### Припущення

- `arrivedAt` — момент фактичного розміщення посилки в комірці й основа для всіх таймерів.
- «Одразу» означає асинхронне надсилання протягом секунд, а не блокування HTTP-запиту до завершення виклику SMS-провайдера.
- Для відкриття/звільнення комірок існує або буде доданий API контролера поштомата.
- Повернення посилки до відправника виконується зовнішньою кур’єрською службою.
- Повторне надсилання SMS допустиме лише в контрольованих межах; операції зміни стану посилки мають бути ідемпотентними.

## Decision

Запровадити єдиний DB-backed scheduler на базі таблиці запланованих повідомлень/операцій та окремий worker, який обробляє ці записи.

### 1. Планувати події під час реєстрації посилки

У межах однієї транзакції:

1. Створити посилку зі статусом `waiting`.
2. Створити три заплановані операції:

   - `arrival_sms` — `arrivedAt`;
   - `reminder_24h` — `arrivedAt + 24 години`;
   - `reminder_48h` — `arrivedAt + 48 годин`.

3. Записати доменну подію `parcel_arrived`.

Запланована операція повинна мати щонайменше:

```text
id
parcel_id
type
due_at
status: pending | processing | sent | skipped | failed
attempts
processed_at
last_error
unique(parcel_id, type)
```

Початковий SMS не повинен надсилатися синхронно з HTTP-запитом. API успішно завершує реєстрацію після фіксації посилки й запланованих операцій, а worker забирає `arrival_sms` одразу після появи.

### 2. Worker обробляє SMS за часом виконання

Worker кожні кілька секунд:

1. Вибирає готові записи з `due_at <= now`.
2. Бронює їх атомарно, щоб два worker-и не обробили один запис.
3. Перевіряє, що посилка досі має статус `waiting`.
4. Відправляє відповідний текст через SMS-провайдера.
5. Позначає операцію `sent`.

Для посилки, яку вже забрали:

- `reminder_24h` і `reminder_48h` позначаються як `skipped`;
- SMS не надсилається.

Для кожного SMS потрібен ідемпотентний ключ, наприклад `parcel_id + type`, якщо це підтримує провайдер. Якщо провайдер не підтримує ідемпотентність, треба прийняти ризик дублювання після тайм-ауту та обмежити кількість повторних спроб.

Текст повідомлень:

```text
arrival_sms:
Посилка чекає у поштоматі №{lockerId}. Код: {code}

reminder_24h:
Нагадування: посилка чекає у поштоматі №{lockerId}. Код: {code}.
Заберіть її протягом 48 годин.

reminder_48h:
Нагадування: посилку у поштоматі №{lockerId} буде повернуто відправнику через 24 години.
Код: {code}.
```

### 3. Окремий expiry worker для 72 годин

Замість нічного cron-запуску використовувати частий polling, наприклад кожні 1–5 хвилин. Це забезпечує повернення близько до 72-ї години, а не із затримкою до наступної ночі.

Процес повернення:

1. Атомарно перевести посилку з `waiting` у проміжний статус `returning`.
2. Позначити невиконані SMS-операції як `skipped`.
3. Надіслати команду контролеру поштомата на звільнення комірки або відкриття комірки для кур’єра.
4. Створити запит на повернення кур’єру з ідемпотентним ключем `parcel_id`.
5. Після успішного прийняття операції:

   - встановити статус `returned`;
   - записати `returnedAt`;
   - записати `cellReleasedAt`;
   - створити події `cell_released` і `parcel_returned`.

Якщо зовнішня операція тимчасово неуспішна, залишати посилку у `returning`, зберігати помилку й повторювати спробу з backoff. Повторний запуск не повинен створювати дубльовану заявку кур’єру.

Рекомендовані статуси:

```text
waiting -> picked_up
waiting -> returning -> returned
```

`picked_up` і `returned` є фінальними станами. Перехід `returning -> picked_up` заборонити, щоб не виникла ситуація, коли посилку одночасно забрали та повертають.

### 4. Звільнення комірки зробити окремим адаптером

Додати інтерфейс на кшталт:

```text
locker.release(lockerId, parcelId)
courier.requestReturn(parcel)
```

Звільнення комірки та запит кур’єру мають бути повторюваними й ідемпотентними. Статус `returned` не встановлювати до підтвердження обох необхідних зовнішніх операцій.

Якщо контролер поштомата не має API, тимчасово дозволити оператору виконувати фізичне вилучення, але все одно фіксувати операцію `cell_release_pending` у базі.

### 5. Спостережуваність і контроль

Додати метрики та журнали:

- кількість SMS за типами;
- кількість помилок SMS;
- кількість посилок у `waiting`, `returning`;
- вік найстарішої посилки;
- помилки звільнення комірок;
- помилки кур’єрського API;
- кількість повторних спроб.

Адміністративний список має показувати статуси `returning` і `returned`, але не код отримання та повний номер телефону.

## Alternatives

### Альтернатива 1: Розширити поточний polling worker і поля в таблиці посилок

Додати до посилки поля:

```text
notifiedAt
reminder24SentAt
reminder48SentAt
```

Worker самостійно перевірятиме `arrivedAt` і виставлятиме ці поля. Нічний job розширити до частішого запуску та додати звільнення комірки.

**Переваги:**

- мінімальна кількість нових таблиць;
- просте перенесення на поточну модель;
- невеликий обсяг початкових змін.

**Компроміси:**

- розклад і статуси операцій жорстко зашиті в коді;
- складніше гарантувати ідемпотентність;
- важко відстежити помилки та повторні спроби окремого SMS;
- додавання нових каналів або нагадувань потребуватиме нових колонок;
- конкурентна обробка кількома worker-ами стає складнішою.

Цю альтернативу можна використати як короткострокове рішення для одного worker-а, але не як бажану довгострокову архітектуру.

### Альтернатива 2: Використати зовнішній scheduler або чергу відкладених повідомлень

Після реєстрації посилки створювати delayed jobs у Redis/BullMQ, RabbitMQ, AWS SQS або іншому брокері:

- job для негайного SMS;
- job через 24 години;
- job через 48 годин;
- job через 72 години для повернення.

**Переваги:**

- точніші таймери;
- готові retry, backoff і dead-letter механізми;
- добре масштабується;
- зменшує polling-навантаження на базу.

**Компроміси:**

- з’являється нова критична інфраструктура;
- потрібно синхронізувати стан черги та PostgreSQL;
- складніше локальне розгортання й моніторинг;
- черга не вирішує сама по собі проблему атомарного звільнення комірки та кур’єрського повернення.

Це доцільно при великій кількості поштоматів або значному обсязі посилок.

### Альтернатива 3: Окремий workflow engine

Використати Temporal, Camunda або подібний workflow engine для життєвого циклу кожної посилки.

**Переваги:**

- природне моделювання таймерів, retry і довгих бізнес-процесів;
- зручна історія виконання;
- надійне відновлення після падіння сервісу;
- добре підходить для складніших сценаріїв повернення.

**Компроміси:**

- суттєво більша операційна складність;
- зайва залежність для поточного масштабу;
- команда повинна підтримувати нову платформу та модель розробки.

## Consequences

### Позитивні

- Початкове SMS буде доставлятися асинхронно майже одразу після розміщення.
- Нагадування матимуть точні строки, незалежні від запуску cron.
- Повторні спроби SMS, повернення та звільнення комірки стануть видимими й контрольованими.
- Повторний запуск worker-а не повинен дублювати бізнес-операції.
- Статус посилки буде відображати реальний життєвий цикл, включно з проміжним станом `returning`.
- Архітектура дозволяє згодом додати push-повідомлення або email без нових колонок у таблиці посилок.

### Негативні

- Потрібні міграції схеми та нові таблиці/індекси.
- З’являється складність обробки distributed operations: SMS-провайдер, контролер комірки та кур’єрський API не беруть участі в одній транзакції з базою.
- Можливі дублікати SMS після невизначеного результату мережевого виклику, якщо провайдер не підтримує ідемпотентність.
- Потрібні додаткові метрики, алерти та операційні процедури для завислих `returning` і `failed` записів.
- На час переходу треба узгодити поведінку старого `notifiedAt` з новою таблицею запланованих операцій.

### Необхідні зміни в поточному коді

- Замінити логіку `listUnnotified()` на вибірку готових scheduled operations.
- Додати атомарне бронювання задач і унікальність `(parcel_id, type)`.
- Замінити нічний `expire-parcels.js` на регулярний expiry worker або розширити поточний worker.
- Додати інтеграцію з контролером комірок.
- Зробити `markReturned` умовним переходом `waiting -> returning/returned`, а не безумовним оновленням.
- Додати тести на повторний запуск, конкурентну обробку, забрану посилку до нагадування та відмову SMS/кур’єра/контролера.
