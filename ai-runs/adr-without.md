# ADR-0007: Таймери зберігання посилки (нагадування 24/48 год і повернення через 72 год)

**Статус:** Запропоновано
**Дата:** 2026-11-03

## Context

**Що є зараз (за кодом):**

- `POST /parcels` створює посилку зі статусом `waiting` і полем `arrivedAt`. Окремий процес `worker` кожні 10 с (`POLL_INTERVAL_MS`) бере пачки по 50 посилок, у яких `notifiedAt IS NULL`, і надсилає SMS з номером поштомата й кодом. SMS-клієнт вже має обмеження частоти (5/с) і повтори на 429. Під час SMS-виклику з'єднання з БД не тримається, і тест це перевіряє.
- Повернення робить `bin/expire-parcels.js`, який cron запускає раз на ніч. Отже, фактично посилку повертають через 72–96 год, а не рівно через 72.
- У поточній логіці повернення є дефекти, які новий функціонал посилить:
  1. **Гонка «видача ↔ повернення».** `findExpired` читає список, потім `markReturned` безумовно ставить `returned`. Якщо мешканець забрав посилку між цими кроками, видана посилка стане «поверненою», а кур'єр поїде по неї. `pickup` має ту саму проблему: спершу `findWaitingByCode`, потім окремим з'єднанням `updateParcel`, без умови на статус.
  2. **Втрата заявки кур'єру.** Спочатку `markReturned`, потім `courier.requestReturn`. Якщо API кур'єра впаде, посилка вже `returned`, і повторної спроби не буде, бо наступний запуск шукає лише `waiting`. Крім того, виняток обриває цикл, і решту посилок у ту ніч не обробляють.
  3. Подія `returned` не пишеться в `events`, на відміну від `picked_up`.
  4. Транзакцій немає: `pool.withConnection` дає з'єднання, а не транзакцію.
- Документація розходиться з кодом: в `ARCHITECTURE.md` вказано 30 с і 4-значний код, а в коді 10 с і 6-значний; в документі v1.5, у `package.json` 1.7.3. В ADR я спираюся на код.
- Інфраструктура: одна VM, `docker compose` (`api`, `worker`), PostgreSQL на хості, нуль npm-залежностей (схоже, це свідомий вибір). Контейнери працюють з `TZ=Europe/Kyiv`.

**Припущення (уточнень я не питав, тому формулюю явно):**

- **П1. Що означає «рівно через 72 год».** Допуск до 1 хвилини після `arrivedAt + 72h`. Рахується абсолютна тривалість у UTC, а не «та сама година за київським часом через 3 дні». На тижні переходу на зимовий/літній час це різниця в 1 год.
- **П2. Від чого рахувати.** Усі три терміни відраховуються від `arrivedAt` (момент, коли посилку поклали в комірку), а не від моменту доставки першого SMS. Інакше збій SMS-провайдера подовжував би зберігання.
- **П3. «Тихі години».** Нагадування надсилаються строго за графіком, навіть о 03:00, якщо посилку поклали о 03:00. «Тихі години» в це рішення не входять, але схема дозволяє їх додати.
- **П4. Що означає «комірка звільняється».** Моделі комірок у коді немає, є лише `lockerId`. Тому «звільнення» означає: код отримання миттєво перестає діяти, посилку ставиться в чергу на вилучення, і через API кур'єра йде заявка на повернення. Фізично посилку виймає кур'єр, керування замками в цьому сервісі немає.
- **П5. Як відправник бачить статус.** Окремого кабінету відправника в нас немає, відправник зберігається як рядок. Він бачить статус через службу доставки: ми передаємо їй заявку на повернення та подальші зміни статусу. Додатково з'являється `GET /parcels/:id/status` для інтеграції служби доставки. Персонал бачить статус в `/admin/parcels`.
- **П6.** Одержувачу про повернення окремого SMS не шлемо, бо цього немає у вимогах. Додати його легко, це просто ще один тип дії.
- **П7.** Обсяг: сотні, максимум тисячі посилок на добу. Нагадування збільшують кількість SMS приблизно до 3 на кожну незабрану посилку.

## Decision

**Зберігати терміни як явні рядки-таймери в PostgreSQL. Обробляти їх існуючим процесом `worker` у тому ж циклі опитування, з атомарними умовними переходами статусу та outbox для виклику кур'єра.** Нічний cron прибираємо як виконавця.

### 1. Модель даних

```sql
CREATE TABLE parcel_timers (
  id          bigserial PRIMARY KEY,
  parcel_id   bigint NOT NULL REFERENCES parcels(id),
  kind        text   NOT NULL CHECK (kind IN ('remind_24h','remind_48h','return_72h')),
  due_at      timestamptz NOT NULL,
  state       text   NOT NULL DEFAULT 'pending'   -- pending | done | cancelled | skipped
                     CHECK (state IN ('pending','done','cancelled','skipped')),
  attempts    int    NOT NULL DEFAULT 0,
  last_error  text,
  done_at     timestamptz,
  UNIQUE (parcel_id, kind)
);
CREATE INDEX parcel_timers_due ON parcel_timers (due_at) WHERE state = 'pending';

CREATE TABLE outbox (            -- зовнішні виклики, що мусять відбутися після коміту
  id bigserial PRIMARY KEY, kind text NOT NULL,   -- 'courier_return'
  parcel_id bigint NOT NULL, payload jsonb NOT NULL,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  attempts int NOT NULL DEFAULT 0, sent_at timestamptz, last_error text
);
```

Статуси посилки: `waiting → picked_up` або `waiting → returning → returned`. `returning` означає, що код уже не діє і заявку кур'єру створено. `returned` означає, що служба доставки підтвердила вилучення (поле `returnedAt`). Якщо підтвердження від кур'єра поки немає, `returning` для відправника вже і є «статусом повернення».

### 2. Потоки

**Реєстрація (`registerParcel`).** В одній транзакції створюються посилка і три таймери: `arrivedAt + 24h`, `+48h`, `+72h`. Перше SMS лишається як є (`notifiedAt` + `notifyArrivals`), бо воно має піти «щойно» і вже працює.

**Видача (`pickup`).** Одна транзакція:
```sql
UPDATE parcels SET status='picked_up', picked_up_at=now()
 WHERE code=$1 AND status='waiting' RETURNING id, locker_id;
UPDATE parcel_timers SET state='cancelled' WHERE parcel_id=$id AND state='pending';
INSERT INTO events ...;
```
Якщо `RETURNING` порожній, код невідомий або термін уже минув: 404, а екран показує «термін зберігання минув».

**Обробка таймерів (новий крок `processDueTimers` у циклі `worker` після `notifyArrivals`):**
```sql
SELECT t.*, p.status, p.locker_id, p.code, p.recipient_phone
  FROM parcel_timers t JOIN parcels p ON p.id = t.parcel_id
 WHERE t.state='pending' AND t.due_at <= now()
 ORDER BY t.due_at LIMIT 50
 FOR UPDATE OF t SKIP LOCKED;
```
- **Нагадування.** Якщо `p.status <> 'waiting'`, таймер стає `cancelled`. Якщо для тієї ж посилки вже настав пізніший таймер (наприклад, після простою), поточний позначається `skipped`, і йде лише найсвіжіше нагадування, а коли настав `return_72h`, нагадування не йдуть зовсім. Інакше транзакція комітиться, і SMS надсилається **поза з'єднанням**, як у `notifyArrivals`. Текст: «Нагадування: посилка чекає у поштоматі №N. Код: XXXXXX. Зберігається до 14:00 06.11» (у київському часі). Після успіху `done`, після помилки `attempts+1` і повтор у наступному раунді.
- **Повернення.** Одна транзакція:
  ```sql
  UPDATE parcels SET status='returning', return_requested_at=now()
   WHERE id=$1 AND status='waiting' RETURNING *;
  -- якщо рядок є:
  INSERT INTO events (parcel_id, type, at) VALUES ($1, 'return_requested', now());
  INSERT INTO outbox (kind, parcel_id, payload) VALUES ('courier_return', $1, ...);
  UPDATE parcel_timers SET state='done', done_at=now() WHERE id=$t;
  -- якщо рядка немає (видача встигла першою): state='cancelled'
  ```
  Гонку з видачею розв'язує умова `status='waiting'`: перемагає той, хто закомітився першим, і жодна посилка не опиниться у двох станах.
- **Outbox.** Той самий `worker` бере `outbox` з `next_attempt_at <= now()` і викликає `courier.requestReturn` з `parcel_id` як ключем ідемпотентності, із з'єднанням поза транзакцією. Після помилки застосовується експоненційна затримка (1 хв → 2 → 4 … до 1 год), а після N спроб піднімається алерт. Помилка однієї посилки не зупиняє інші.

**Час.** Вимірюємо за годинником БД (`now()`), а не контейнера, щоб API і worker не розходилися. У пам'ятному сховищі для тестів, як і зараз, використовується інжектований `clock`.

**Цикл worker.** Зараз worker спить 10 с, якщо пачка неповна. Так і лишається: точність ≤ 10 с + час обробки, що вкладається в П1. Повна пачка означає «одразу ще раз».

### 3. Зміни в коді (обсяг)

- `db.js`: `withTransaction(fn)` у пулі; методи `insertTimers`, `claimDueTimers`, `transitionStatus(id, from, to, patch)` (умовний), `cancelTimers`, `enqueueOutbox`, `claimOutbox`. Пам'ятну реалізацію оновлюємо дзеркально.
- `parcels.js`: `registerParcel` і `pickup` переходять на транзакції та умовні оновлення. `RETURN_AFTER_MS` лишається єдиним джерелом 72 год, поруч додаються `REMIND_AFTER_MS = [24h, 48h]`.
- `worker.js`: функції `processDueTimers`, `drainOutbox`, `reminderText`.
- `server.js`: `GET /parcels/:id/status` (П5), а в `/admin/parcels` нові статуси й `dueAt`.
- `bin/expire-parcels.js` перетворюється на **reconciler**: раз на годину лише шукає `waiting` старші за 72 год + 5 хв і посилки без таймерів, логує `error` і нічого не змінює. Це страховка від тихої поломки worker.

### 4. Міграція

1. Міграція схеми (нові таблиці, статус `returning`).
2. Backfill для поточних `waiting`: створити `return_72h` з `due_at = arrived_at + 72h`. Нагадування створювати лише ті, чий `due_at` ще в майбутньому, щоб не надіслати купу запізнілих SMS одразу після деплою.
3. Деплой `worker`, потім `api`. Після першого успішного циклу cron перемкнути в режим reconciler.

### Розглянуті альтернативи

**A. Залишити cron, але запускати щохвилини; терміни виводити з `arrivedAt` (поля `reminder1SentAt`, `reminder2SentAt` у `parcels`).**
- ➕ Найменше змін, знайома модель, без нової таблиці.
- ➖ Окремий процес із власним життєвим циклом: при повільному запуску можливе перекриття, тож потрібен `pg_advisory_lock`. Логіка «що вже надіслано» розмазана по колонках, і кожен новий тип нагадування означає нову колонку та новий запит. Аудиту «що і коли мало статися» немає. Дефекти 1–2 все одно доведеться виправляти. Точність ±1 хв, тобто гірша, ніж у циклі worker.
- Вердикт: прийнятний запасний варіант, якщо нову таблицю заблокують. Але таймери в тому самому worker простіші в експлуатації.

**B. `setTimeout` у процесі worker (запланувати три таймери в пам'яті під час реєстрації або старту).**
- ➕ Точність до мілісекунд, жодних запитів-опитувань.
- ➖ Таймери губляться при кожному рестарті чи деплої, тож після старту однаково потрібне відновлення з БД, тобто фактично альтернатива A з додатковою складністю. Масштабувати на два worker не вийде без розподілу. Тестувати важче.
- Вердикт: відхилено, бо надійність тут важливіша за мілісекунди.

**C. Окрема черга з відкладеними задачами (Redis + BullMQ, RabbitMQ delayed exchange або pg-boss поверх Postgres).**
- ➕ Готові повтори, затримки, дашборди; добре масштабується.
- ➖ Redis чи RabbitMQ означають новий stateful-сервіс на єдиній VM, з бекапами й моніторингом, і це для кількох тисяч задач на добу. Скасування при видачі й «хто першим змінив статус» однаково треба робити в Postgres, тобто з'являється два джерела правди. pg-boss прибирає нову інфраструктуру, але ламає принцип «нуль залежностей» і приносить власну схему.
- Вердикт: варто переглянути, якщо з'являться десятки поштоматів і різнотипні фонові задачі.

**D. Відкладена відправка на боці SMS-провайдера (при реєстрації одразу запланувати два SMS на +24/+48 год).**
- ➕ Майже нуль коду для нагадувань.
- ➖ Потрібна гарантоване скасування за API провайдера під час видачі; якщо його немає або воно не спрацює, одержувач отримує «забери посилку» вже після того, як забрав. Повернення через 72 год це не вирішує. Ми прив'язуємося до можливостей конкретного провайдера.
- Вердикт: відхилено.

## Consequences

**Позитивні**
- Повернення відбувається через 72 год + ≤ ~10 с замість «наступної ночі».
- Виправлено гонку видача/повернення та втрату заявок кур'єру. Ці дефекти є вже зараз, незалежно від нової функції.
- Кожен термін видно як рядок: персонал бачить «наступна дія о …», а аудит повний (`events` + `parcel_timers`).
- Нова інфраструктура не потрібна, залежностей не з'являється. Тестується через вже наявний інжектований `clock`.
- Нові типи дій («тихі години», SMS про повернення, продовження зберігання) додаються як новий `kind`, без змін у схемі посилки.

**Негативні та ризики**
- **SMS доставляються «щонайменше один раз».** Якщо worker впаде між успішною відправкою і `done`, нагадування прийде двічі. Для нагадування це прийнятно. Якщо провайдер підтримує ключ ідемпотентності, передаємо `timer.id` (не перевірено, це ще одне припущення).
- **Мале вікно «нагадування після видачі»:** статус перевірили, SMS ще йде, а мешканець саме забрав посилку. Вікно секундне, і нейтральний текст нагадування згладжує наслідки.
- **Пікові хвилі SMS.** Кур'єри завантажують поштомати вранці пачками, тому через 24 і 48 год приходить така сама хвиля. При 5 SMS/с 300 нагадувань розійдуться за 1 хв. Це прийнятно, але черга першого SMS не повинна стояти за нагадуваннями, тому `notifyArrivals` у кожному раунді йде першим.
- **Worker стає критичним для SLA повернення.** Потрібні метрика/лог `timer_lag_seconds = now() - due_at` для найстарішого `pending` з алертом при > 5 хв, поле в `/health` worker і погодинний reconciler.
- **Більше роботи з БД:** кожні 10 с індексований запит по `parcel_timers` (частковий індекс за `pending`). При П7 навантаження незначне.
- **Операційні нюанси:** код, введений через кілька секунд після 72 год, вже не діє. Потрібен зрозумілий текст на екрані і, можливо, процедура для персоналу. Нагадування можуть прийти вночі (П3).
- Треба оновити `ARCHITECTURE.md`: описати новий потік і заодно виправити розбіжності щодо 30 с / 4 цифр / версії.
