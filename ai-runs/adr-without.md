ADR-0007: Таймери життєвого циклу посилки (нагадування та повернення через 72 год)
Статус: Запропоновано
Дата: 2026-10-25

Context
Що потрібно
SMS про прибуття працює як зараз: номер поштомата і код.
Два нагадування, через 24 і 48 год після прибуття, якщо посилку досі не забрали.
Повернення відправнику рівно через 72 год, а не тоді, коли спрацює нічна задача. Код перестає діяти, кур'єр отримує запит на повернення, відправник бачить статус.
Що зараз у коді (v1.7.3)
worker.js раз на 10 с вибирає з бази посилки без SMS (listUnnotified). Після вибірки він повертає з'єднання в пул, а вже потім викликає SMS-провайдера, бо пул малий (DB_POOL_MAX=4). Доставка гарантується «принаймні один раз»: якщо процес впаде між SMS і записом notifiedAt, людина отримає дубль.
bin/expire-parcels.js запускається cron'ом на VM раз на ніч. Тому реальний строк зберігання становить від 72 до ~96 год.
findExpired у parcels.js читає всю таблицю і фільтрує її в Node.
expireParcels спершу ставить статус returned і лише потім викликає кур'єра. Якщо кур'єр відповів помилкою, посилка вже позначена поверненою, а запиту на повернення немає. Виняток зупиняє цикл, і решта посилок того дня не обробляється.
pickup спершу читає посилку за кодом (findWaitingByCode), а потім окремим кроком оновлює її. Між цими кроками немає атомарності. Поки повернення раз на ніч, гонка майже неможлива. Коли повернення відбувається з точністю до секунд, людина біля поштомата о 71:59:58 і процес повернення стабільно конкуруватимуть за ту саму посилку.
Немає моделі комірки (є тільки lockerId) і немає інтерфейсу для відправника. Зовні статус бачить лише кур'єрська служба через POST /returns.
Контейнери працюють із TZ=Europe/Kyiv, мітки часу зберігаються в ISO UTC.
Документація розходиться з кодом: у ARCHITECTURE.md код 4-значний і опитування раз на 30 с, а в коді код 6-значний і опитування раз на 10 с. На рішення це не впливає, але документ варто оновити разом із цією зміною.
Припущення (у коді їх не видно)
П1. «Рівно через 72 год» означає не пізніше ніж через 1 хвилину після arrived_at + 72h (SLO). Точність до мілісекунди не потрібна.
П2. Інтервали відлічуються в астрономічних годинах від arrived_at. Ніч переходу на літній чи зимовий час не скорочує і не подовжує строк.
П3. О 72:00 код отримання перестає діяти одразу. Фізично посилка лишається в комірці, доки її не забере кур'єр. Комірка звільняється після його сканування; це робить контролер поштомата чи кур'єрська служба, а не цей сервіс.
П4. Відправник бачить статус через систему кур'єрської служби, яка отримує наш POST /returns. Окремий кабінет відправника не входить у цей ADR.
П5. Кур'єрський POST /returns ідемпотентний за parcel_id: повторний запит не створює другого повернення. Якщо це не так, потрібен ключ ідемпотентності на нашому боці (див. «Наслідки»).
П6. «Тихих годин» немає: нагадування може прийти о 03:00, як і SMS про прибуття сьогодні. Це відкрите продуктове питання (див. нижче).
П7. Розгортання те саме: одна VM, PostgreSQL, docker compose з api і worker. Нової інфраструктури (Redis, брокер) не додаємо. У проєкті нуль npm-залежностей, і це варто зберегти.
Decision
Кожна посилка стає скінченним автоматом зі своїм наступним строком, next_action_at, у PostgreSQL. Строки обробляє наявний worker, який захоплює посилки на обмежений час (lease). Нічну задачу прибираємо.

1. Схема

ALTER TABLE parcels
  ADD COLUMN stage          text,         -- 'arrival' | 'remind_1' | 'remind_2' | 'return' | 'courier' | NULL
  ADD COLUMN next_action_at timestamptz,  -- коли виконати stage; NULL = нічого не заплановано
  ADD COLUMN lease_until    timestamptz,  -- захоплено worker'ом до цього моменту
  ADD COLUMN attempts       int NOT NULL DEFAULT 0,
  ADD COLUMN reminded_at    timestamptz[] NOT NULL DEFAULT '{}',
  ADD COLUMN return_requested_at timestamptz;

CREATE INDEX parcels_due ON parcels (next_action_at) WHERE next_action_at IS NOT NULL;
CREATE UNIQUE INDEX parcels_waiting_code ON parcels (code) WHERE status = 'waiting';
Статуси: waiting → picked_up або waiting → returning → returned.

2. Етапи. Строки рахуються від arrived_at, а не від моменту попереднього кроку, щоб затримки не накопичувались
stage	строк	дія	далі
arrival	arrived_at	SMS з номером поштомата і кодом (як зараз)	remind_1 @ +24h
remind_1	arrived_at + 24h	SMS-нагадування	remind_2 @ +48h
remind_2	arrived_at + 48h	SMS-нагадування	return @ +72h
return	arrived_at + 72h	атомарно waiting → returning: код більше не діє	courier одразу
courier	одразу / backoff	POST /returns до кур'єра з повторами	NULL після успіху
Застарілі нагадування пропускаються. Якщо worker не працював і вже настав строк наступного етапу, нагадування не надсилається, автомат переходить далі. Так після простою люди не отримають пачку запізнілих SMS.

3. Цикл worker'а: lease замість довгих транзакцій
Це зберігає нинішній принцип: під час зовнішніх викликів з'єднання з базою не тримається.


-- коротка транзакція: захопити партію
UPDATE parcels SET lease_until = now() + interval '2 minutes'
WHERE id IN (
  SELECT id FROM parcels
  WHERE next_action_at <= now() AND (lease_until IS NULL OR lease_until < now())
  ORDER BY next_action_at
  LIMIT 50 FOR UPDATE SKIP LOCKED)
RETURNING *;
Далі для кожної посилки: зовнішній виклик (SMS або кур'єр), потім коротка транзакція, яка просуває stage і next_action_at і знімає lease. Кожен перехід пишеться в events. Опитування лишається раз на 10 с. Якщо партія повна, наступний цикл починається одразу. Затримка ≈ 10 с плюс черга, що вкладається в П1. Час now() береться з PostgreSQL, а не з годинників контейнерів.

4. Гонка між отриманням і поверненням вирішується в базі
Обидві операції стають умовними атомарними UPDATE:


-- pickup (замість findWaitingByCode + updateParcel)
UPDATE parcels SET status='picked_up', picked_up_at=now(), next_action_at=NULL
WHERE code=$1 AND status='waiting' RETURNING id, locker_id;

-- етап return
UPDATE parcels SET status='returning', return_requested_at=now(), stage='courier', next_action_at=now()
WHERE id=$1 AND status='waiting' AND arrived_at + interval '72 hours' <= now() RETURNING *;
Хто перший закомітив, той і виграв. Другий отримує 0 рядків: або 404 на екрані поштомата, або етап просто завершується. Посилка не може водночас бути виданою і поверненою.

5. Повернення
Спершу локальний перехід у returning, потім запит до кур'єра як окремий етап courier, що повторюється з backoff (1 хв, 5 хв, 15 хв…; attempts). Невдача по одній посилці не блокує інших. Після N невдач пишеться log.error, і посилка видна персоналу в /admin/parcels. Статус returned ставиться, коли кур'єр підтвердить, що забрав посилку (П3), через webhook або його сканер.

6. Розгортання
Міграція. Для посилок у статусі waiting обчислити stage і next_action_at з arrived_at, відразу виставивши найближчий майбутній етап (щоб не розіслати пачку нагадувань у момент деплою). Посилки, старші за 72 год, отримують stage='return'.
Cron expire-parcels вимкнути в тому самому релізі, інакше одну посилку повертатимуть двічі. Файл видалити наступним релізом.
Розглянуті альтернативи
A. Окрема таблиця таймерів (scheduled_jobs)
Рядки (parcel_id, kind, due_at, done_at, attempts) створюються в одній транзакції з insertParcel: arrival, +24h, +48h, +72h.

Плюси. Таблиця універсальна, придатна для будь-яких майбутніх подій (наприклад, «продовжити зберігання на добу»). Кожен таймер має окремий аудит. due_at фіксується в момент створення.
Мінуси. На кожну посилку чотири рядки, плюс доводиться скасовувати таймери при видачі (або перевіряти статус у кожному обробнику). Зміна політики, наприклад 72→96 год, вимагає переписувати вже створені рядки. Більше коду і більше станів, які можуть розійтися з parcels.
Чому не обрано. Наразі процес лінійний і для всіх посилок однаковий. stage разом із next_action_at дає те саме з одним індексом і без синхронізації двох таблиць. Якщо з'являться розгалужені сценарії, перехід на A буде природним.
B. Готова черга з відкладеними завданнями (pg-boss на PostgreSQL або BullMQ на Redis)
Плюси. Повтори, backoff, startAfter, дедуплікація й моніторинг уже готові. Точність до секунд.
Мінуси. Перша залежність у проєкті без залежностей (pg-boss) або новий сервіс на єдиній VM, який треба бекапити й моніторити (Redis для BullMQ). Стан посилки опиняється у двох місцях: у parcels і в черзі. Атомарність між «видано» і «скасувати завдання» доводиться забезпечувати окремо. Для кількох тисяч посилок на день це надмірно.
Чому не обрано. Суперечить П7, а ключову проблему (гонку видачі з поверненням) не розв'язує: її однаково розв'язують умовні UPDATE.
C. Частіший cron (* * * * *) з нинішнім expire-parcels і подібною задачею для нагадувань
Плюси. Найменша зміна. Точність ~1 хв задовольняє П1.
Мінуси. Щохвилини новий процес Node і новий пул з'єднань. Якщо запуск триває довше хвилини, запуски накладаються, і без блокувань посилку повертають двічі. Cron живе на VM поза docker compose: окремий спосіб розгортання й окремі логи. Нинішні вади (markReturned до виклику кур'єра, повне сканування, зупинка циклу на першій помилці) однаково доведеться виправляти.
Чому не обрано. Дає ту саму логіку, що й рішення, але в гіршому середовищі виконання.
D. setTimeout у пам'яті worker'а (відкинуто одразу)
Таймери губляться при кожному рестарті чи деплої, а 72 год довші за типовий час життя контейнера.

Consequences
Позитивні
Повернення через 72:00 + ≤ ~1 хв замість «72–96 год». Нагадування надходять вчасно.
Гонку видачі з поверненням виключено на рівні бази. Заодно закрито нинішню неатомарну pickup.
Невдалий виклик кур'єра більше не лишає посилку в стані «повернена без запиту» і не зупиняє обробку інших посилок.
Нової інфраструктури й залежностей немає. Один процес відповідає за весь життєвий цикл, логи в одному місці.
SKIP LOCKED разом із lease дозволяє запускати кілька worker'ів, якщо колись знадобиться.
Негативні та ризики
SMS-трафік зростає до двох нагадувань на кожну незабрану посилку. Ліміт SMS_RATE_PER_SEC=5 діє в межах одного процесу, тож два worker'и дадуть 10/с. Якщо масштабувати, ліміт треба перенести в базу або провайдера. Через черговість за next_action_at нагадування не витісняють SMS про прибуття.
Доставка лишається «принаймні один раз». Падіння між SMS і комітом дасть дубль нагадування, падіння між запитом до кур'єра і комітом дасть повторний POST /returns. Це прийнятно лише за П5. Якщо кур'єрський API не ідемпотентний, треба передавати ключ return:<parcel_id> і зберігати courier_return_ref.
Межа о 72:00 жорстка. Людина, яка ввела код о 72:00:05, отримає відмову. Екран має показувати «посилка повертається відправнику», а не «невідомий код». Це потребує нової відповіді POST /pickup (наприклад, 410).
Стан посилки ускладнюється (stage, lease_until, attempts). Потрібні тести на переходи, пропуск застарілих нагадувань, протухлий lease і гонку з видачею.
Деплой має бути скоординований: міграція з backfill і вимкнення cron в одному релізі.
Документацію треба оновити: ARCHITECTURE.md (прибрати нічну задачу, виправити 4→6 цифр і 30→10 с) і README.md.
Відкриті питання до продукту
Чи потрібні тихі години для нагадувань (П6)? Якщо так, нагадування переноситься на 08:00, а повернення лишається о 72:00.
Чи надсилати отримувачу SMS «посилку повернено відправнику»?
Чи має відправник бачити статус безпосередньо в нас (П4)? Тоді потрібен окремий ADR про автентифікацію відправника.
Я лише прочитав код у app/; нічого не змінював і тестів не запускав. Два місця в коді вже зараз вимагають виправлення, бо без них «рівно 72 години» не запрацює. По-перше, pickup неатомарна: вона спершу читає посилку, а потім окремо оновлює її. По-друге, expireParcels позначає посилку поверненою ще до виклику кур'єра, тож при його помилці лишається «повернена» посилка без запиту на повернення.
