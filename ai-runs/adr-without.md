# ADR-001: Сповіщення та повернення посилок через дедлайни й чергу задач у PostgreSQL

**Статус:** Запропоновано
**Дата:** 2026-11-03

## Context

**Потрібно:**
- SMS із номером поштомата й кодом одразу після закладання посилки;
- нагадування через 24 і 48 годин, якщо посилку не забрали;
- повернення відправнику рівно через 72 години: комірка звільняється, а відправник бачить статус.

**Що є в коді зараз:**

| Вимога | Стан | Чого бракує |
|---|---|---|
| SMS про прибуття | Є: [worker.js](app/src/worker.js) опитує БД кожні 10 с | Надійності: див. дефект 4 |
| Нагадування | Немає | Усього механізму |
| Повернення | Нічний cron, [expire-parcels.js](app/bin/expire-parcels.js) | Точності в часі й надійності |
| Звільнення комірки | Немає: є лише `lockerId`, а модель комірок відсутня | Моделі комірки й події вилучення посилки |
| Статус для відправника | Немає: `sender` це вільний текст, а список посилок доступний лише персоналу | Каналу для відправника |

**Обмеження:**
- Одна VM, `docker compose` із двома сервісами (`api`, `worker`), PostgreSQL на тій самій VM.
- У `package.json` немає залежностей.
- Ліміт SMS (5/с) рахується окремо в кожному клієнті ([sms.js](app/src/sms.js)), тож другий процес із власним клієнтом його подвоїть.
- Тести фіксують два інваріанти: під час виклику SMS-провайдера з'єднання з БД не утримується, а `/health` не звертається до БД.

**Дефекти, відтворені запуском на сховищі в пам'яті (усі 15 наявних тестів проходять, але цього не ловлять):**
1. **Збій кур'єрського API губить повернення.** Посилка вже позначена `returned`, а кур'єра не викликано. Наступної ночі її не вибрано, тож кур'єр про неї не дізнається. Решта посилок чекає ще добу.
2. **Код працює після 72 годин.** Посилку вдалося забрати на 84-й годині, бо `pickup` не перевіряє дедлайн.
3. **Гонка між отриманням і поверненням.** Запис безумовний, тому вийшов рядок зі статусом `returned` і заповненим `pickedUpAt`. Нічний запуск майже приховує цю гонку, а дедлайн у довільний час доби зробить її реальною.
4. **«Отруйні» SMS блокують чергу.** 50 постійно невдалих SMS займають весь пакет, і 51-ша посилка не отримала SMS за 5 раундів.
5. **Нові поля витікають у список для персоналу.** `listForAdmin` копіює весь рядок через `...rest`, тому туди потрапив доданий для перевірки `trackingToken`.
6. **`POST /parcels` без `sender` дає 500 замість 400.** Для повернення це поле обов'язкове.

Крім того, з читання коду: `findExpired` читає всю таблицю в пам'ять, а `fetch` у клієнтах SMS і кур'єра не має тайм-ауту. Завислий провайдер зупинить послідовний цикл.

**Припущення:**
- **П1 (найважливіше).** Посилка фізично лишається в комірці, доки її не забере кур'єр (так описано в [courier.js](app/src/courier.js)). Тому о T+72 год комірка стає недоступною отримувачу, а вільною для нових посилок лише після вилучення.
- **П2.** Сканер може передавати номер комірки, а кур'єр або його сканер може підтвердити вилучення.
- **П3.** Відправник не має облікового запису. Статус він бачить за посиланням із токеном, яке передає служба доставки.
- **П4.** «Рівно» означає: код перестає діяти точно о T+72 год, статус змінюється протягом 15 с, кур'єра викликають асинхронно з повторами.
- **П5.** `arrivedAt` (час реєстрації сканером) вважаємо часом закладання. Години рахуємо як реальні, тому перехід на зимовий час не зсуває дедлайн.
- **П6.** «Тихих годин» немає: нагадування може прийти вночі, як і вимагає точне формулювання.
- **П7.** Працює один екземпляр `worker`, а compose перезапускає його після збою.
- **П8.** Кур'єрський API не гарантує ідемпотентність за `parcel_id`; це треба узгодити.

**Чого не вдалося перевірити:** PostgreSQL-адаптера та `deploy/` у цій теці немає. Тому SQL нижче є ескізом, а продакшн-значення `DB_POOL_MAX` і розклад cron невідомі. [ARCHITECTURE.md](app/docs/ARCHITECTURE.md) застарів (30 с і 4-значний код проти 10 с і 6-значного в коді), тому за джерело правди взято код.

## Decision

Зберігаємо всі дедлайни в PostgreSQL, а виконуємо їх у наявному сервісі `worker`. Нових сервісів і залежностей не додаємо. Зміна стану й запис задачі відбуваються в одній транзакції, а зовнішні виклики йдуть поза нею.

**Стани посилки:**

```text
waiting ──(код до T+72 год)──► picked_up
waiting ──(T+72 год)──► returning ──(кур'єр вилучив, комірка вільна)──► returned
```

**Схема (ескіз):**

```sql
ALTER TABLE parcels
  ADD COLUMN return_due_at timestamptz,        -- arrived_at + 72 год
  ADD COLUMN return_requested_at timestamptz,
  ADD COLUMN cell_no int,
  ADD COLUMN cell_released_at timestamptz,
  ADD COLUMN tracking_token text UNIQUE;

CREATE TABLE parcel_tasks (
  id bigserial PRIMARY KEY,
  parcel_id bigint NOT NULL REFERENCES parcels,
  kind text NOT NULL,  -- sms_arrival | sms_reminder_24h | sms_reminder_48h | courier_return
  due_at timestamptz NOT NULL,                 -- час наступної спроби
  state text NOT NULL DEFAULT 'pending',       -- pending | done | cancelled | dead
  attempts int NOT NULL DEFAULT 0,
  last_error text,
  UNIQUE (parcel_id, kind)
);
CREATE INDEX ON parcel_tasks (due_at) WHERE state = 'pending';
CREATE INDEX ON parcels (return_due_at) WHERE status = 'waiting';
CREATE UNIQUE INDEX ON parcels (locker_id, cell_no)
  WHERE cell_no IS NOT NULL AND cell_released_at IS NULL;
```

**Реєстрація.** Посилка і три SMS-задачі створюються однією транзакцією. Нагадування мають `due_at` T+24 год і T+48 год.

**Отримання.** Це один атомарний запит:

```sql
UPDATE parcels SET status = 'picked_up', ...
WHERE code = $1 AND status = 'waiting' AND return_due_at > $now
```

Та сама транзакція скасовує SMS-задачі й звільняє комірку. Так межа 72 годин точна, навіть якщо `worker` лежить, а гонка з поверненням неможлива.

**Три незалежні цикли у `worker`:**
- **Повернення, кожні 15 с, лише БД.** Одна транзакція переводить прострочені посилки з `waiting` у `returning`, створює задачу `courier_return` і подію. Зовнішніх викликів тут немає, тому збій провайдера чи кур'єра повернення не затримає.
- **SMS.** Один спільний клієнт, тому ліміт 5/с зберігається. Задачі про прибуття йдуть першими. Нагадування не надсилається, якщо посилка вже не в статусі `waiting`, а коли прострочено кілька SMS, іде лише найновіше. Після вичерпання спроб задача стає `dead`, тож черга не блокується.
- **Кур'єр.** Повтори з наростанням паузи до 15 хв. Задача не стає `dead`, але після порогу піднімає тривогу.

**Захоплення задачі.** Короткий `UPDATE` зсуває `due_at` на 2 хв (оренда задачі) і збільшує `attempts`, після чого з'єднання повертається в пул. Виклик іде вже без з'єднання, тож тестований інваріант лишається чинним. Гарантія доставки: щонайменше один раз. Рідкісний дубль SMS прийнятний.

**Інші зміни:**
- **Клієнти:** тайм-аут `AbortSignal.timeout` для SMS і кур'єра.
- **Сховище:** нові атомарні методи `pickupWaiting`, `expireDue`, `claimDueTasks`, `completeTask`, `failTask`. Їх реалізують і в сховищі в пам'яті, і в адаптері PostgreSQL.
- **Текст нагадування:** `Посилка у поштоматі №12 чекає до 05.11 14:30. Код: 123456`. Абсолютний час (Europe/Kyiv) лишається правдивим при затримці, а текст вміщається в один кириличний сегмент (70 символів).
- **Статус для відправника:** `GET /parcels/status?token=…`, лише статус і дати. Токен генерує `crypto.randomBytes`, а не `Math.random`. Він у query-рядку, бо логер пише тільки `pathname`, і явно виключений з `listForAdmin`.
- **Підтвердження вилучення:** `POST /returns/collected` з автентифікацією звільняє комірку й переводить посилку в `returned`.
- **Моніторинг:** окремий `GET /health/jobs` показує вік найстарішої простроченої задачі й кількість прострочених повернень. `/health` лишається без звернень до БД.

### Розглянуті альтернативи

| | **Обрано: черга в PostgreSQL** | **А: cron щохвилини** | **Б: Redis + BullMQ** | **В: pg-boss** |
|---|---|---|---|---|
| Точність межі 72 год | Точна (перевірка в `pickup`) | Точна, якщо додати ту саму перевірку | Точна, якщо додати ту саму перевірку | Точна, якщо додати ту саму перевірку |
| Зміна статусу | До 15 с | До 60 с | Частки секунди | Секунди |
| Атомарність із посилкою | Так | Так | Ні, запис у дві системи | Можлива, потребує спільної транзакції |
| Ліміт SMS 5/с | Зберігається | Потребує спільного лімітера | Вбудований | Налаштовується |
| Нова інфраструктура | Немає | Немає | Redis і його резервні копії | Немає (але окрема схема в БД) |
| Нові залежності | Немає | Немає | 2 | 1 |
| Власний код | Найбільше | Найменше | Менше | Менше |

- **А: cron щохвилини.** Найдешевший старт із колонками `reminder_*_sent_at`. Але кожен запуск має власний пул і SMS-клієнт, запуски можуть накластися й подвоїти виклик кур'єра, а сам cron лежить поза compose. Логіку повторів усе одно довелося б писати. **Відхилено**, бо економія майже зникає після виправлення дефектів 1–4.
- **Б: Redis + BullMQ.** Зрілі відкладені задачі, повтори й обмеження швидкості. Але втрата задачі в Redis означає посилку, яка ніколи не повернеться, а для однієї VM це другий стан, який треба резервувати. **Відхилено**; варто переглянути, якщо з'явиться кілька VM і великий потік задач.
- **В: pg-boss.** Найсильніший конкурент: та сама БД і готові повтори та планування. Ціна: перша залежність у проєкті, її власна схема й оновлення, а також перебудова `worker`. **Відхилено для трьох фіксованих дедлайнів**. Якщо типів задач стане більше 5–6 або власна черга почне обростати функціями, варто перейти на нього.

## Consequences

**Позитивні:**
- Код перестає діяти точно о T+72 год незалежно від стану `worker`.
- Рестарт нічого не губить: усі дедлайни лежать у БД.
- Збій SMS чи кур'єра не затримує зміну статусу, а дефекти 1–5 усуваються самим дизайном. Дефект 6 закриває окрема валідація `sender`.
- Нових сервісів немає, тому експлуатація майже не ускладнюється.

**Негативні:**
- Власну чергу доведеться підтримувати й покривати тестами.
- Кількість SMS зростає до 3 на незабрану посилку, тож зростають і витрати.
- `worker` стає критичним для повернень, тому моніторинг `/health/jobs` обов'язковий.
- Таблиця задач росте, тож потрібне прибирання старих рядків.
- Цикли додають постійне навантаження на пул, тому продакшн-значення `DB_POOL_MAX` треба перевірити.

**Ризики й наслідки для продукту:**
- Якщо SMS-провайдер не працював усі 72 години, посилка повернеться, хоча отримувач нічого не дізнався. Це відповідає вимозі, але таку подію треба логувати як помилку.
- Отримувач, який прийшов на 73-й годині, бачить посилку за дверцятами, але код уже не діє. Відповідь `/pickup` має пояснювати це окремо, а не «unknown or already used code».
- Комірка зайнята, доки не приїде кур'єр. Потрібні домовленість про час вилучення і тривога на задовгий `returning`.

**Розгортання:**
1. Додати схему без зміни наявної поведінки й заповнити дані для посилок у статусі `waiting`. Нагадування створювати лише для ще не настілих моментів, щоб уникнути хвилі застарілих SMS.
2. Вимкнути нічний cron перед запуском нового циклу, інакше кур'єр отримає подвійні запити. Пауза між кроками нешкідлива: посилки просто трохи почекають.
3. Викатити `api` і `worker`. Перший цикл одразу поверне весь накопичений залишок понад 72 години.
4. Після цього оновити контракт сканера (`cell_no`), підключити підтвердження кур'єра, видалити `bin/expire-parcels.js` і `listUnnotified`, оновити `ARCHITECTURE.md`.

**Обов'язкові тести:**
- межа T+72 год мінус 1 мс і рівно T+72 год;
- гонка отримання й повернення;
- збій кур'єра з подальшим повтором;
- рестарт між захопленням задачі й завершенням;
- блокування черги «отруйними» SMS;
- кілька прострочених нагадувань одразу;
- 72 години через зміну часу 25.10.2026;
- відсутність токена в `listForAdmin`.

**Поза межами цього ADR (проблеми вже існують):** `POST /parcels` без автентифікації, `/pickup` без обмеження спроб для 6-значного коду, дублікати посилок при повторному запиті сканера. Нагадування двічі повторно надсилають код, тому обмеження спроб на `/pickup` варто зробити наступним.

---

Найбільше на рішення впливає припущення **П1**. Я свідомо відійшов від буквального «комірка звільняється о 72 годині»: якщо позначити її вільною, поки посилка всередині, сканер може закласти туди нову. Якщо ж посилку о 72 годині вилучає персонал, зміниться лише джерело події `collected`, а решта рішення залишиться.
