# ADR: сповіщення та повернення посилок із поштомата

**Статус:** пропозиція  
**Дата:** 3 листопада 2026 року

## Context

Зараз API реєструє посилку зі статусом `waiting`, а окремий worker періодично надсилає SMS про прибуття. Нічна задача шукає посилки, що пролежали понад 72 години, і повертає їх через API служби доставки.

Такий підхід не забезпечує потрібного часу сповіщень і повернення: нагадувань через 24 та 48 годин немає, а нічна задача може спрацювати значно пізніше за 72 години. Крім того, вона змінює статус на «повернено» **до** запиту кур’єру: якщо запит не вдасться, статус не відповідатиме фактичному стану. У поточній моделі також не видно обліку зайнятості комірок або способу показати відправнику статус повернення.

Поточний код і документація вказують на PostgreSQL у продакшні, окремий worker, API SMS-провайдера та інтеграцію зі службою доставки. Це дає змогу додати надійну обробку за розкладом, не запроваджуючи окрему систему черг.

## Decision

Використовувати **PostgreSQL як джерело стану та чергу запланованих дій**. Після реєстрації посилки в одній транзакції зберігати її та записи про дії на заданий час:

- SMS про прибуття — одразу після розміщення;
- нагадування — через 24 та 48 годин від `arrivedAt`;
- повернення — рівно через 72 години від `arrivedAt`.

Зберігати час у UTC. Worker часто опитує записи, строк яких настав, і обробляє їх із блокуванням рядків, щоб кілька екземплярів не виконали одну дію паралельно. Кожна дія має стабільний ідентифікатор для ідемпотентних повторів. Помилки SMS або інтеграції з кур’єром не гублять завдання: worker повторює їх із затримкою та журналює результат. Для цього потрібна підтримка ідемпотентності з боку зовнішнього сервісу або можливість звірити результат запиту.

До 72-годинного строку посилка лишається доступною для отримання. Якщо отримання і строк повернення збігаються, атомарна операція в базі визначає один результат: отримання приймається лише до дедлайну; на дедлайні посилка переходить до повернення і код більше не працює.

Процес повернення фіксує проміжний стан, наприклад `return_pending`, і викликає API кур’єра. Статус `returned` встановлюється після підтвердження фактичного вилучення посилки. Комірка звільняється тоді ж, а не лише після створення запиту на повернення. Події та поточний статус зберігаються в базі; авторизований інтерфейс або API для відправника показує статус, зокрема «очікує повернення» та «повернено».

**Припущення:** «рівно 72 години» означає, що повернення запускається на дедлайн `arrivedAt + 72 години`, а не що кур’єр фізично забирає посилку в ту саму мить. Фактичний час вилучення залежить від кур’єрської служби. Під «відправник бачить статус» мається на увазі автентифікований канал для відправника; його спосіб входу потребує окремого узгодження з наявною бізнес-моделлю.

## Consequences

- Розклад і повторні спроби переживають перезапуски worker та API.
- Один worker може обробляти SMS і повернення; окрема брокерна система на першому етапі не потрібна.
- Потрібні таблиці запланованих дій або outbox, стани повернення, часові мітки та події стану. Потрібно оновити API статусу для відправника й інтеграцію підтвердження кур’єра.
- SMS та запити на повернення мають можливість дублюватися на рівні мережі. Ідемпотентність або звірка зовнішнього результату потрібні, щоб повторні спроби не створювали дублікатів.
- Часте опитування бази додає невелике навантаження, а доставка SMS та обробка кур’єром лишаються залежними від зовнішніх сервісів. «Рівно» гарантується для строку запуску завдання в системі, але не для фактичного отримання SMS чи фізичного повернення.

### Розглянуті альтернативи

1. **Залишити cron/нічну задачу та додати два окремі cron-запуски для нагадувань.** Це простіше змінити, але точність залежить від частоти запуску; завдання важче надійно повторювати й координувати, а нічний цикл не відповідає дедлайну 72 години.

2. **Запровадити окремий брокер повідомлень із відкладеними повідомленнями.** Він добре масштабується та відокремлює worker від бази, але додає інфраструктуру й узгодження стану брокера з PostgreSQL. За нинішньої архітектури це складніше, ніж зберігати заплановані дії в базі.

3. **Надсилати SMS і викликати кур’єра синхронно з HTTP-запитів API або таймерів у пам’яті.** Це має менше компонентів на схемі, але втрачає заплановані дії при перезапуску, сповільнює API зовнішніми викликами й ускладнює повтори.
