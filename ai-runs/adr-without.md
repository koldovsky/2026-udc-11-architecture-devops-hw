# ADR-0001. Нагадування й повернення через 72 год: дедлайни зберігаються в PostgreSQL, виконує їх наявний worker

**Статус:** Запропоновано · 2026-11-01
**Що змінюється:** `src/parcels.js`, `src/worker.js`, `src/db.js`, `bin/expire-parcels.js`, схема PostgreSQL, `docs/ARCHITECTURE.md`

## Context (Контекст)

### Що потрібно
1. **SMS про прибуття.** Працює так само, як зараз.
2. **Нагадування.** Через 24 і 48 год, якщо посилка досі `waiting`.
3. **Повернення рівно через 72 год.** Код перестає діяти, статус змінюється, службі доставки йде запит на повернення, відправник бачить статус.

### Як працює зараз
- **Стек.** Node 22+ без жодної npm-залежності; README підкреслює це як свідомий вибір. PostgreSQL стоїть на тій самій VM. `docker compose` запускає `api` і `worker` з одного образу. Повернення робить нічна задача з cron на хості.
- **SMS про прибуття.** Worker кожні 10 с перевіряє базу (`src/worker.js:8`). SMS відправляється, коли з'єднання з базою вже повернуто в пул, і лише після відправки ставиться `notifiedAt`. Тобто SMS доходить щонайменше один раз, але може прийти двічі.
- **Ліміт SMS 5 за секунду.** Його рахує кожен процес окремо (`src/sms.js:17-23`). Другий процес, який теж шле SMS, про цей ліміт не знає.
- **Повернення.** Нічний `bin/expire-parcels.js`. Насправді посилка повертається через 72–96 год, а не через 72.

### Проблеми в коді, які безпосередньо зачіпають цю функцію
- **Запит на повернення може загубитися.** У `bin/expire-parcels.js:14-15` посилка спершу позначається повернутою (`markReturned`), і тільки потім іде запит кур'єру (`requestReturn`). Окремої обробки помилки для кожної посилки немає. Якщо API кур'єра впаде, посилка вже матиме статус `returned`, а запит кур'єру так і не піде. Повторно його теж не надішлють, бо `findExpired` шукає лише `waiting`. Решту посилок тієї ночі задача вже не обробить.
- **Гонка «отримання проти повернення».** `pickup` (`src/parcels.js:61-65`) спершу читає посилку, а потім окремим запитом записує новий статус, нічого не перевіряючи. Поки повернення було нічним, ця гонка була суто теоретичною. Якщо ж повертати рівно о 72:00, людина з кодом о 71:59:59 справді може зіткнутися з поверненням. Наслідок: `picked_up` перезапише `returned`, або кур'єр поїде по посилку, яку вже забрали.
- **Повний перебір таблиці.** `findExpired` (`src/parcels.js:78-80`) читає всі посилки й фільтрує їх у JS. Раз на ніч це терпимо, кожні кілька секунд уже ні.
- **Документація застаріла.** `docs/ARCHITECTURE.md:18-19` пише про 30 с і 4-значний код, а в коді 10 с і 6 цифр. Теки `deploy/`, на яку посилається документ, тут немає, тому compose-файл і crontab я не бачив.

### Припущення
- **П1. Що означає «рівно».** Код отримання перестає діяти в момент `arrivedAt + 72 год`, з точністю до секунди. Статус і запит кур'єру можуть запізнитися максимум на 10 с. Точність до мілісекунд не потрібна.
- **П2. 72 год — це 259 200 секунд реального часу.** Перехід на літній чи зимовий час на це не впливає. Контейнери працюють з `TZ=Europe/Kyiv`.
- **П3. Після 72 год код не діє.** Навіть якщо кур'єр ще не приїхав, мешканець не забере посилку кодом.
- **П4. Відправник бачить статус у трекінгу служби доставки.** Трекінг оновлюється нашим викликом `POST /returns` (`src/courier.js`). Окремого кабінету відправника не робимо: поле `sender` у нас містить лише назву, контактів немає.
- **П5. API кур'єра ідемпотентне за `parcel_id`.** Повторний запит не створює другого повернення. **Це треба підтвердити в служби доставки до релізу.** Якщо ні, додаємо ключ ідемпотентності.
- **П6. «Комірка звільняється»** означає, що посилка більше не `waiting` і код не діє. Фізично комірку відкриває кур'єр своїм доступом. Обліку зайнятих комірок у сервісі немає, і цей ADR його не додає.
- **П7. Нагадування приходять рівно через 24 і 48 год,** зокрема вночі, як і SMS про прибуття зараз. «Тихі години» в цей ADR не входять.
- **П8. Масштаб.** До кількох тисяч посилок на добу, один екземпляр worker. API і worker на одній VM, годинник синхронізований через NTP.
- **П9. PostgreSQL 9.5 або новіший,** бо потрібен `FOR UPDATE SKIP LOCKED`.

## Decision (Рішення)

Дедлайни зберігаються в PostgreSQL. Усе, що виходить назовні (SMS, запит кур'єру), записується в таблицю-чергу `outbox`. Обробляє все наявний процес `worker` у трьох незалежних циклах. Нічну задачу прибираємо. Нової інфраструктури й npm-залежностей не додаємо.

**1. Схема**
```sql
ALTER TABLE parcels
  ADD COLUMN return_due_at       timestamptz,  -- arrived_at + interval '72 hours'
  ADD COLUMN return_requested_at timestamptz;  -- кур'єр прийняв запит
CREATE INDEX parcels_waiting_due ON parcels (return_due_at) WHERE status = 'waiting';

CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  parcel_id    bigint NOT NULL REFERENCES parcels(id),
  kind         text NOT NULL,  -- arrival_sms | reminder_24h | reminder_48h | courier_return
  due_at       timestamptz NOT NULL,
  state        text NOT NULL DEFAULT 'pending',  -- pending | done | skipped | dead
  attempts     int  NOT NULL DEFAULT 0,
  locked_until timestamptz,
  last_error   text,
  UNIQUE (parcel_id, kind)
);
CREATE INDEX outbox_due ON outbox (due_at) WHERE state = 'pending';
```
Писати треба саме `interval '72 hours'`, а не `'3 days'`. Коли PostgreSQL додає дні до `timestamptz`, він зберігає час на годиннику. Тому при переході на літній чи зимовий час «3 дні» стають 71 або 73 годинами (див. П2).

**2. Реєстрація (`POST /parcels`).** Усе в одній транзакції: запис у `parcels` разом із `return_due_at` і три рядки в `outbox`: `arrival_sms` (на зараз), `reminder_24h`, `reminder_48h`. Термін фіксується в момент прибуття. Якщо згодом політику змінять, наприклад, на 96 год, для вже покладених посилок діятиме той термін, що вказаний у їхніх SMS.

**3. Отримання (`POST /pickup`) стає однією атомарною операцією.**
```sql
UPDATE parcels SET status = 'picked_up', picked_up_at = $now
 WHERE code = $1 AND status = 'waiting' AND return_due_at > $now
RETURNING id, locker_id;
```
У тій самій транзакції незавершені записи в `outbox` для цієї посилки переводяться в `skipped`, і пишеться подія `picked_up`. Саме умова `return_due_at > $now` гарантує людині біля екрана точну межу 72 год, хоч би на скільки відставав worker. Гонку з поверненням вирішує блокування рядка: виграє той, хто першим змінив статус `waiting`.

**4. Worker: три незалежні цикли в одному процесі.** Один спільний цикл не підходить: партія SMS при ліміті 5 за секунду і з паузами на відповіді 429 може тривати десятки секунд, і повернення не повинно стояти за нею в черзі.

| Цикл | Період | Що робить |
|---|---|---|
| **returns** | 2 с | Одна транзакція: `UPDATE parcels SET status='returned', returned_at=$now WHERE status='waiting' AND return_due_at <= $now RETURNING id`. Для кожної такої посилки додає в `outbox` запис `courier_return` (`ON CONFLICT DO NOTHING`) і пише подію `returned`. Працює лише з базою, без мережевих викликів. |
| **sms** | 5 с | Бере до 50 записів `arrival_sms` і `reminder_*`, час яких настав; `arrival_sms` іде першим. Резервує їх на 2 хв (`locked_until`, `SKIP LOCKED`), повертає з'єднання в пул і **тільки потім** шле SMS. Цей принцип уже перевіряє `worker.test.js`. Перед нагадуванням перевіряє, чи посилка ще `waiting`; якщо ні, ставить `skipped`. Після успіху ставить `done`, а для `arrival_sms` ще й `notified_at`, щоб адмінка працювала як раніше. Після помилки переносить спробу на пізніше, а після N невдалих спроб ставить `dead` і пише помилку в лог. |
| **courier** | 5 с | Так само обробляє `courier_return`. Після успіху ставить `done` і `return_requested_at`. Повторює спроби з дедалі довшими паузами до ~24 год, потім ставить `dead` і піднімає тривогу. |

**Решта змін**
- **Статус `returned` лишається.** Так не ламаються адмінка та `expire.test.js`. Те, що кур'єр прийняв запит, видно з `return_requested_at`.
- **Текст нагадування.** Номер поштомата, код і крайній строк. Час форматується явно в `Europe/Kyiv` через `Intl.DateTimeFormat`, а не через часовий пояс контейнера.
- **Нічна задача.** `bin/expire-parcels.js` і рядок у cron прибираємо через один реліз. Протягом цього релізу обидва механізми можуть працювати разом без шкоди: нічна задача просто нічого не знайде.
- **Моніторинг.** Раз на хвилину worker пише в лог три показники:
  - найбільше запізнення повернення (`returned_at − return_due_at`);
  - скільки чекає найстаріший запис, час якого вже настав;
  - кількість записів `dead`.

  Тривога, якщо запізнення перевищує 60 с або з'явився `dead courier_return`. Записи `done` і `skipped`, старші за 30 днів, видаляємо.
- **Міграція посилок, що вже чекають.** Для них ставимо `return_due_at = arrived_at + 72 год`. Створюємо лише ті нагадування, час яких ще не настав, щоб не розіслати пачку запізнілих SMS.
- **`src/db.js`.** Нові методи приймають параметр `now`, тож тести керують часом через наявний `clock`.

### Розглянуті альтернативи

**А. Запускати cron щохвилини, розширивши `bin/expire-parcels.js`.** Додати колонки `reminder_24h_sent_at` і `reminder_48h_sent_at`. Скрипт щохвилини шле нагадування й повертає прострочені посилки.
- ➕ Найменше змін: без нової таблиці, за вже знайомою схемою.
- ➖ Запізнення до 60 с плюс час на запуск Node. Межу для людини можна зробити точною тією ж умовою в `pickup`, але статус і кур'єр усе одно запізнюватимуться.
- ➖ SMS почнуть слати два процеси. Ліміт 5 за секунду в `sms.js` кожен рахує сам, тож разом вийде до 10 за секунду, і провайдер почне відповідати 429.
- ➖ Запуски можуть накластися: якщо провайдер гальмує, 50 SMS із паузами займуть понад 60 с, і без `flock` чи advisory lock люди отримають подвійні нагадування.
- ➖ Cron живе на хості поза compose: окремий деплой, окремі логи, окремі змінні оточення. Для повторних запитів кур'єру знадобиться ще одна колонка.
- Підсумок: годиться як тимчасовий крок «на завтра», але проблеми з лімітом SMS і накладанням запусків доведеться латати окремо.

**Б. Окремий брокер черг з відкладеними задачами** (Redis + BullMQ, RabbitMQ з плагіном delayed-message) **або бібліотека pg-boss.**
- ➕ Затримки, повтори, наростаючі паузи й панелі моніторингу вже готові. Точність до мілісекунд, воркери легко масштабуються.
- ➖ Redis чи RabbitMQ — нова інфраструктура зі своїми даними на одній VM. Треба налаштувати збереження на диск: задача з затримкою 72 год у Redis без AOF зникне при перезапуску. Плюс резервні копії й моніторинг. Для сервісу громади це забагато.
- ➖ Запис у дві системи не атомарний: посилка збережена в PostgreSQL, а задачу в брокер не поставлено, або навпаки. Щоб не губити повернення, однаково знадобиться `outbox` у PostgreSQL. Тобто це прийняте рішення плюс ще брокер.
- ➖ Коли посилку забирають, відкладені задачі треба скасовувати окремою логікою за їхніми ID.
- ➖ З'являються перші npm-залежності в проєкті, який свідомо обходиться без них.
- pg-boss працює в тому ж PostgreSQL, тож нової інфраструктури не потребує. Але це залежність, і в неї своя схема та міграції. Це розумний наступний крок, якщо власна черга почне розростатися: нові типи задач, розклади, пріоритети.

**В. Таймери в пам'яті worker (`setTimeout` на кожну посилку).**
- ➕ Найточніше й найменше коду.
- ➖ Таймери губляться при кожному перезапуску чи деплої. Їх довелося б відновлювати з бази, тобто дедлайни в базі й регулярна перевірка все одно потрібні. Якщо запустити два екземпляри, задачі виконаються двічі. Варіант відкинуто.

| | Прийняте | А. cron щохвилини | Б. брокер | В. таймери |
|---|---|---|---|---|
| Межа 72 год для людини | точна | точна, якщо додати умову в `pickup` | точна | точна |
| Запізнення статусу й запиту кур'єру | ≤ 2–5 с | ≤ 60 с | мілісекунди | мілісекунди, але таймери губляться при перезапуску |
| Чи може загубитися запит кур'єру | ні | без окремої колонки так | так, через запис у дві системи | так |
| Ліміт SMS 5 за секунду | один процес | два процеси, відповіді 429 | як налаштуєш | один процес |
| Нова інфраструктура чи залежності | ні | ні | так | ні |
| Обсяг змін | середній | малий | великий | малий, але крихкий |

## Consequences (Наслідки)

**Позитивні**
- Код перестає діяти рівно о 72:00:00, а статус і запит кур'єру оновлюються за кілька секунд, а не до наступної ночі.
- Гонку «отримання проти повернення» усунено атомарними операціями з умовою на статус. Заодно виправлено нинішню втрату запиту кур'єру при збої його API.
- Експлуатація не ускладнюється: та сама VM, ті самі два контейнери, без cron і без залежностей.
- Новий дедлайн, наприклад «тихі години» з П7, додається новим `kind` у `outbox`, без зміни архітектури.
- Усе тестується з підставним годинником, як і зараз.

**Негативні та ризики**
- Власну просту чергу (резервування, повтори, `dead`; орієнтовно 200–300 рядків) доведеться підтримувати самим.
- SMS може прийти двічі: якщо worker впаде між відправкою і позначкою `done`. Запит кур'єру може піти двічі, тільки якщо його API не ідемпотентне (П5).
- Людина може отримати одне зайве нагадування, якщо забирає посилку в ту ж секунду, коли воно відправляється.
- Від worker тепер залежать повернення. Якщо він не працює, код усе одно перестане діяти вчасно, бо це перевіряє API. Статус і запит кур'єру підтягнуться після перезапуску: worker обробляє все, чий час уже настав, тож нічого не пропуститься. Потрібні `restart: unless-stopped` і тривога, якщо worker перестав писати в лог.
- Записів у базі більше: 3–4 рядки в `outbox` на посилку, плюс прості запити до бази кожні 2–5 с. За часткових індексів і обсягів із П8 це практично безкоштовно, але `outbox` треба регулярно чистити.
- На посилку, яку не забрали, тепер припадає до трьох SMS замість одного, тож витрати на SMS зростуть.
- Три цикли worker ділять пул на 4 з'єднання. З'єднання короткі, але `PoolTimeoutError` у worker варто відстежувати.

**Що зробити разом із цим ADR**
- Підтвердити в служби доставки ідемпотентність `POST /returns` (П5).
- Оновити `docs/ARCHITECTURE.md` (заодно виправити 30 с і 4 цифри) та `README.md`.
- Додати тести:
  - межа 71:59:59 і 72:00:00 для `pickup`;
  - одночасні отримання й повернення;
