## ADR-0007: Планові SMS-нагадування та точне повернення посилок за 72 год.

**Статус:** Пропонується
**Дата:** 2026-11-02

---

### Context

Сервіс «Поштомат громади» вже відправляє SMS про прибуття через довго живий процес `worker.js` (опитування бази кожні 10 с) і звільняє комірку нічним cron-скриптом `bin/expire-parcels.js` (запускається зовнішнім планувальником, зазвичай раз на добу о 02:00).

Нові вимоги:

| # | Подія | Момент |
|---|-------|--------|
| 1 | SMS про прибуття | вже реалізовано |
| 2 | Нагадування 1 | +24 год. від `arrivedAt`, якщо `status = 'waiting'` |
| 3 | Нагадування 2 | +48 год. від `arrivedAt`, якщо `status = 'waiting'` |
| 4 | Повернення відправнику | рівно +72 год. від `arrivedAt`, не «наступної ночі» |

**Ключові обмеження та припущення:**
- Zero-dependency Node.js — жодних зовнішніх пакетів без явної згоди команди.
- `worker` вже розгорнутий як daemon (завжди живий, реагує на SIGTERM).
- Прийнятна точність повернення — ±хвилини (не секунди і не дні).
- Нічний cron вже викликає ускладнення: посилка, покладена о 23:59, фактично отримує +47–71 год. замість 72.
- Телефон відправника є в полі `sender` у вигляді довільного тексту — **припущення**: відправником є кур'єрська служба, якій надсилається запит через `courier.js`, а не пряме SMS; SMS-нагадування адресовані лише отримувачу (`recipientPhone`).

---

### Decision

**Розширити внутрішній цикл `worker.js` до ролі планувальника часових подій** (pattern: «polling scheduler»).

#### Що змінюється в схемі

Додати два нові поля до таблиці посилок:

```sql
ALTER TABLE parcels
  ADD COLUMN reminder24_sent_at TIMESTAMPTZ,
  ADD COLUMN reminder48_sent_at TIMESTAMPTZ;
```

Існуючі поля `notified_at`, `picked_up_at`, `returned_at` залишаються без змін. Нові поля `NULL` = нагадування ще не відправлено.

#### Що змінюється в `worker.js`

Замість одного запиту (`listUnnotified`) кожна ітерація циклу виконує чотири незалежні «прогони»:

| Прогін | Умова вибірки | Дія |
|--------|--------------|-----|
| **arrival** | `notified_at IS NULL` | SMS про прибуття (вже існує) |
| **reminder24** | `notified_at IS NOT NULL AND reminder24_sent_at IS NULL AND arrived_at ≤ now − 24 h AND status = 'waiting'` | SMS «Посилка очікує вже добу» |
| **reminder48** | `reminder24_sent_at IS NOT NULL AND reminder48_sent_at IS NULL AND arrived_at ≤ now − 48 h AND status = 'waiting'` | SMS «Посилка буде повернена завтра» |
| **return72** | `arrived_at ≤ now − 72 h AND status = 'waiting'` | виклик `courier.js` → `markReturned()` |

Кожен прогін — окремий запит із власним `pool.withConnection(...)`, щоб не блокувати пул на час SMS-дзвінків (той самий патерн, що вже застосований для arrival).

Інтервал опитування змінюється з 10 с → **60 с** (точність ±60 с при дедлайні 72 год. = похибка 0.002%).

#### Що видаляється

`bin/expire-parcels.js` і відповідний зовнішній cron-рядок у `docker-compose` / systemd — їхню роль бере на себе прогін `return72` всередині worker.

#### Текст SMS-нагадувань

```
Reminder 24 h: «Посилка у поштоматі №{lockerId} ще чекає. Код: {code}. Залишилося ~48 год.»
Reminder 48 h: «Нагадування: посилка у поштоматі №{lockerId}. Код: {code}. Завтра буде повернена відправнику.»
```

---

### Alternatives Considered

#### Альтернатива A — Таблиця запланованих завдань (`scheduled_jobs`)

При реєстрації посилки вставляти 3 рядки в окрему таблицю:

```sql
CREATE TABLE scheduled_jobs (
  id          SERIAL PRIMARY KEY,
  parcel_id   INT REFERENCES parcels(id),
  type        TEXT,          -- 'reminder24' | 'reminder48' | 'return72'
  due_at      TIMESTAMPTZ,
  executed_at TIMESTAMPTZ
);
```

Worker опитує `WHERE due_at <= now AND executed_at IS NULL`.

**Переваги:**
- Завдання дуговічні: зберігаються навіть якщо worker лежить; при перезапуску він знає точно, що пропустив.
- Легко аудитувати (окремий рядок на кожну дію).
- Додавання нових типів подій (reminder72h, return120h) — лише новий рядок без зміни схеми посилок.

**Недоліки:**
- Потребує міграції нової таблиці і 3 `INSERT` при кожному `registerParcel`.
- Транзакційна цілісність: якщо `INSERT INTO parcels` успішний, а `INSERT INTO scheduled_jobs` ні — потрібна транзакція або компенсація.
- Поки parcels невеликих обсягів (громадський поштомат), ця складність не виправдана.
- Worker усе одно залишається єдиним виконавцем, тому «виживання» завдань при його падінні — лише теоретична перевага: arrival-SMS теж «зависнуть» під час падіння.

**Висновок:** виправдана, якщо команда планує >5 типів подій або хоче адмін-UI «що відбудеться далі з посилкою». Надмірна для поточних трьох подій.

---

#### Альтернатива B — Зовнішня черга з підтримкою затримок (pg-boss або Redis + BullMQ)

При реєстрації посилки ставимо три завдання у чергу з `delay`:

```js
// pseudo-code
await queue.add('sms-reminder', payload, { delay: 24 * 3600 * 1000 });
await queue.add('sms-reminder', payload, { delay: 48 * 3600 * 1000 });
await queue.add('return-parcel', payload, { delay: 72 * 3600 * 1000 });
```

Worker є consumer черги; завдання виконуються точно в момент `due_at`.

**Переваги:**
- Найточніша доставка: wake up точно через N мс, без poll-overhead.
- Масштабується горизонтально — кілька worker-інстанцій без дублювань.
- Природна підтримка retry, dead-letter queue.
- Якщо використовувати **pg-boss** (PostgreSQL-based), нова зовнішня залежність — лише npm-пакет поверх вже наявного Postgres.

**Недоліки:**
- **pg-boss** або **Redis + BullMQ** — явна зміна філософії «zero-dependency».
- При використанні Redis: новий інфраструктурний компонент (окремий контейнер, моніторинг, failover).
- `pg-boss` вирішує dependency-проблему, але додає складність обслуговування таблиць черги в тому ж Postgres.
- Over-engineering для 1–2 поштоматів; доцільний при >1 000 посилок/добу або кількох worker-нодах.

**Висновок:** правильний вибір для продуктового масштабування, але передчасний для поточного масштабу. Перейти на pg-boss легко пізніше — вхідний інтерфейс `notifyArrivals` залишиться незмінним.

---

### Consequences

#### Позитивні

- **Точність 72 год. ±60 с** замість ±12 год. при нічному cron.
- **Zero нової інфраструктури** — нічого не додається до `docker-compose`.
- **Видалення `bin/expire-parcels.js`** і cron-рядка — менше рухомих частин.
- **Єдина точка відповідальності**: всі часові події — у worker; розуміти систему простіше.
- Retry-семантика нагадувань та повернення — та сама, що у arrival: при тимчасовій недоступності SMS-провайдера worker повторить на наступній ітерації.

#### Негативні / ризики

- **Затримка при падінні worker**: якщо worker не відповідає 2 год., посилка отримає нагадування із запізненням. Мітигація: alert на відсутність log-запису worker за >5 хв., вже закладений у `ARCHITECTURE.md`.
- **Один процес — чотири обов'язки**: при налагодженні складніше ізолювати, який саме прогін спрацював. Мітигація: структуровані логи вже мають поле `msg` — додати поле `job` зі значенням `'arrival'|'reminder24'|'reminder48'|'return72'`.
- **Порядок прогінів має значення**: прогін `return72` повинен виконуватись **після** `reminder48`; якщо посилка пролежала точно 48 год., вона може отримати обидва нагадування в одній ітерації. Мітигація: перевірка `reminder48_sent_at IS NOT NULL` як передумова для return72 — **не** застосовується; повернення настає незалежно від стану нагадувань (посилку можуть скласти після збою нагадувань).
- **Міграція схеми**: потрібна `ALTER TABLE`; у поточній in-memory реалізації для тестів поля просто додаються до об'єкта без міграції — тести потребують оновлення фікстур.
- **Видалення cron** не є зворотно сумісним: якщо розгортання залишить старий cron у crontab, він спробує запустити відсутній файл. Мітигація: задокументувати в `CHANGELOG` і перевірити в CI.
