### Першопричина

**Worker v1.8.0 витікав DB-з'єднання або захоплював їх на старті у великій кількості, вичерпавши глобальний ліміт з'єднань БД. API отримав лише 4 з'єднання — скільки залишилось після worker'а — і задихнувся під навантаженням 11–12 rps.**

Ключові докази:

1. **Точний момент:** перший `db pool wait timeout` стався через 7 секунд після старту worker v1.8.0 — не після старту API.
2. **"Магічна четвірка":** `db_pool_in_use` = рівно **4** без жодного відхилення протягом 45 хвилин. Це не "повільні запити", це жорстка стеля — та, що залишила БД після того, як worker'забрав решту.
3. **Миттєве відновлення без рестарту API:** коли worker дістав SIGTERM (14:46:59), рівно наступну хвилину `db_pool_in_use` стрибнув на 14 — саме стільки з'єднань звільнилось. API продовжив роботу без перезапуску.
4. **До деплою конкуренції не було:** до 14:02 API сам по собі використовував до 13 з'єднань без будь-якого `waiting`.

SMS-проблема (429) — **окрема, супутня, не першопричина.** Вона з'явилась через органічне зростання трафіку, а не спричинила DB-катастрофу.

### Впевненість: **85%**

**Що підтримує:** точний збіг моментів старту worker → перший таймаут; точний збіг SIGTERM → відновлення; DB-пул застряг на константі 4; відновлення без рестарту API.

**Що залишається припущенням** (звідси -15%): немає прямих метрик кількості з'єднань worker'а до БД. Технічно, одночасно з SIGTERM worker'а оператор міг вручну розширити DB `max_connections` або application pool — але тоді збіг із SIGTERM був би дивним збігом. Я вважаю це малоймовірним.

**Що варто перевірити для підтвердження:** конфіг пулу БД у worker v1.8.0 (`pool_size`, час утримання з'єднань), diff між v1.7.x та v1.8.0 у частині DB-клієнта, метрики `pg_stat_activity` або аналог за той самий час.
