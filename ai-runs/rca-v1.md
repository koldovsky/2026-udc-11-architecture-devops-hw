# RCA v1 — інцидент «Поштомат громади» 14.10.2026

## 1. Короткий висновок

14.10.2026 о **14:02:00 Europe/Kyiv** API сервісу оновили з **1.7.3** до **1.8.0**. Одразу після старту 1.8.0 пул з'єднань API з БД перестав видавати більше **4 з'єднань одночасно**, тоді як до оновлення при тому самому навантаженні спостерігалося **12–13**. При трафіку **11–12 RPS** чотирьох з'єднань не вистачило: з'явилася черга до пулу (`db_pool_waiting` 4→23), запити почали чекати понад 2000 мс і падати з **503 “db pool wait timeout after 2000ms”**, p95 виріс з ~250 мс до **~4,5–5 с**, error rate — до **10–13%**.

О **14:47:00** виконали відкат на **1.7.3**. Перші ж запити після відкату пішли за 108–140 мс, p95 повернувся до ~200–300 мс, черга до пулу стала нульовою, 503-помилки припинилися. Це класична ознака регресії релізу, а не навантаження, БД чи мережі.

**Першопричина page-інциденту:** регрес у релізі API **1.8.0**, який обмежив ефективну ємність пулу з'єднань з БД до **4 з'єднань**. Найімовірніше, у 1.8.0 зменшили явний `max pool size` або втратили його конфігурацію й отримали малий дефолт драйвера. Точний код/конфіг у наданих даних відсутній, тому це сформульовано як висновок за спостережуваною поведінкою, а не як доведений рядок зміни.

**Впевненість:**

| Твердження | Впевненість | Обґрунтування |
|---|---:|---|
| Page-інцидент спричинений саме 1.8.0 | **~95%** | Точний збіг початку з стартом 1.8.0; рестарт тієї ж версії не допоміг; відкат на 1.7.3 прибрав проблему за хвилину; навантаження не змінилося |
| Ефективна причина — обмеження пулу до 4 з'єднань | **~80%** | `db_pool_in_use` рівно 4 усі 45 хвилин інциденту проти 12–14 у 1.7.3; при цьому є черга `db_pool_waiting` |
| Конкретно це зміна `max pool size`, а не інший механізм | **~70%** | Дані не розрізняють зменшення ліміту, витік/довше утримання з'єднань чи іншу регресію 1.8.0; усі варіанти — регресії саме 1.8.0 |
| SMS 429 — окремий інцидент, не причина page-інциденту | **~90%** | 429 почалися за 34 хв до деплою 1.8.0; API був здоровий; після відкату API 429 ще тривали |

## 3. Першопричина та механізм

### 3.1. Що видно в метриках

| Показник | 14:01 (1.7.3) | 14:02–14:46 (1.8.0) | 14:47+ (1.7.3) |
|---|---:|---:|---:|
| `rps` | 11,3 | 11,0–12,8 (median 11,8) | 11,5 → поступово до 4–11 |
| `p95_ms` | 245 | 945–4962 (median 4650) | 618 → 296 → 232 |
| `error_rate` | 0,44% | 10–13% (median 11%) | 0,14–0,57% |
| `db_pool_in_use` | 12 | **рівно 4 усі 45 хвилин** | 14 → 11–12 |
| `db_pool_waiting` | 0 | 4–23 (median 17) | 0 |

Ключове: у 1.8.0 `db_pool_in_use` **ніколи не перевищує 4**, хоча навантаження 11–12 RPS і є черга `db_pool_waiting` до 23. Це означає, що пул (або доступна йому ємність) впирається в стелю 4. У 1.7.3 до і після інциденту той самий сервіс на тому самому навантаженні тримає 12–14 з'єднань і нульову чергу.

### 3.2. Чому це дає саме такі симптоми

Коли всі 4 з'єднання зайняті, нові запити стоять у черзі. Якщо очікування перевищує 2000 мс, застосунок повертає **503 “db pool wait timeout after 2000ms”**. У логах API **3380 таких 503** — і всі вони в інтервалі **14:02:07–14:46:58**, тобто рівно під час роботи 1.8.0. До 14:02 і після 14:47 — **нуль**. Це ~75 помилок/хв, що збігається з `error_rate` 10–13% при 11–12 RPS (~78–94 помилки/хв).

p95 4,5–5 с — це сума часу очікування в черзі, обробки та, ймовірно, повторів запиту після таймауту. Успішні запити в 1.8.0 теж повільні: `/pickup` median 2538 мс проти 58 мс до і 61 мс після; `/parcels` 201 median 1051 мс проти 64 мс до і 76 мс після; `/admin/parcels` median 2278 мс проти 68 мс до і 59 мс після.

### 3.3. Що саме могло змінитися в 1.8.0

У наданих даних немає diff між 1.7.3 і 1.8.0, конфігів пулу, коду або метрик БД. Тому явно фіксую припущення:

- **Найпростіше пояснення:** у 1.8.0 зменшено `max pool size` до 4 явно або через змінений дефолт драйвера/бібліотеки. Це найкраще збігається з тим, що `db_pool_in_use` весь інцидент рівно 4.
- **Альтернатива:** 1.8.0 тримає з'єднання довше (наприклад, синхронний зовнішній виклик або зайві запити в межах транзакції), через що навіть 4 слоти стають вузьким місцем. Але саме по собі довше утримання не пояснює, чому `in_use` не росте вище 4, якщо ліміт пулу більший.
- **Альтернатива:** витік або невчасне повернення з'єднань у 1.8.0. Дані не розрізняють це від зменшення ліміту; для перевірки потрібні `pg_stat_activity`, налаштування `max_connections` і графік кількості відкритих з'єднань з боку БД.

Усі три варіанти — це регресії саме 1.8.0. Для відповіді «що сталося і чому» важливо, що проблема не в рості трафіку і не в деградації БД: вона з'явилася з новою версією і зникла з відкатом.

## 4. Чому інші версії причин не підходять

1. **Зростання трафіку.** RPS до інциденту 11,3; під час 1.8.0 — 11,0–12,8. Це те саме плато. Після відкату о 14:47 навантаження ще деякий час лишалося 11–12 RPS, і 1.7.3 спокійно його витримував. Трафік не був причиною.
2. **Деградація БД або мережі.** Відкат застосунку за хвилину повернув p95 до ~200–300 мс на тій самій БД. Якби проблема була в БД, відкат коду не допоміг би.
3. **SMS 429.** Детально нижче: 429 почалися за 34 хвилини до деплою 1.8.0, увесь цей час API працював нормально, а після відкату API 429 тривали ще ~14 хвилин. SMS-тротлінг не є причиною API-деградації.
4. **Помилки 500 “Cannot read properties of undefined (reading 'trim')”.** Їх 125, усі на `POST /parcels`, час від часу з 12:39 до 15:57 — тобто до, під час і після інциденту, включно з роботою 1.7.3. Вони швидкі (3–14 мс) і не збігаються з початком 503. Перший 503 у 1.8.0 стався о 14:02:07, а перша така 500 після деплою — лише о 14:03:00, тому вони не могли виснажити пул на старті. Це окремий дефект валідації вхідних даних, який варто виправити, але не першопричина.
5. **Витік пам'яті / OOM.** `heap_used_pct` весь день коливається 42–82% (пила з GC), під час інциденту — ті самі 42–82%. OOM або падінь процесу в логах немає; були SIGTERM і старти, а не crash.
6. **Тимчасовий збій після рестарту.** Повторний старт тієї ж 1.8.0 о 14:20:31 не допоміг: перший же залогований запит після нього о 14:20:35 повернув 503 із `ms=4445`. Отже, проблема відтворювалася на чистому процесі тієї ж версії.

## 5. Окремий SMS-інцидент

Це важливо розділити з page-інцидентом API.

- До 13:28 воркер відправляв ~**15,5 SMS/хв**, і 429 не було.
- З 13:28 до 15:02 — ~**182 SMS/хв** (у ~12 разів більше), і почалися 429.
- Після 15:02 — знову ~**17 SMS/хв**, і 429 припинилися.
- Усього за 13:28–15:02 воркер залогував **3065** записів `sms provider rate limited` (status 429, спроби 1–2, `retry_in_ms` 400/800).
- Warning `SmsProvider429RateHigh` горів **13:37–15:03**.

Це схоже не на відмову провайдера, а на **перевищення його ліміту**: при ~15 SMS/хв 429 не було, при ~182 SMS/хв — стабільно були, після повернення до ~17 SMS/хв — зникли. Чому обсяг стрибнув у 12 разів, у наданих даних не видно. Явні припущення: масова кампанія/пакетне завантаження повідомлень, розбір накопиченої черги або дублювання повідомлень через retry/enqueue.

Окремо зауважу: 182 SMS/хв — це те, що воркер залогував як `sms batch sent`; якщо retry'ї після 429 рахуються як окремі відправлення, фактичний унікальний обсяг міг бути меншим. Тому причиною міг бути як стрибок enqueue, так і зниження квоти провайдера з подальшою retry-ампліфікацією; даних для розрізнення немає. Впевненість у конкретній причині стрибка низька (~35%); впевненість у тому, що це окрема проблема, не причина API page-інциденту, висока (~90%).

Чому 429 не могли спричинити API-деградацію:

- 429 почалися о 13:28, а API деградував о 14:02 — 34 хвилини API працював нормально на тлі вже активного SMS-тротлінгу.
- О 14:47 відкатили API на 1.7.3, і API відновився, хоча 429 тривали до 15:01.
- Після 14:47, коли API вже працював на 1.7.3, SMS-потік ще був ~182/хв до 15:02, і це не заважало p95 ~200–300 мс. Отже, навіть фонове DB-навантаження від SMS-воркера саме по собі не вичерпувало пул API.
- Загалом SMS-тротлінг не є ні достатньою, ні необхідною умовою API-деградації. Він міг бути фоновим навантаженням, але не першопричиною.

## 6. Що робити

**Негайно / до з'ясування:**

1. Залишити API на 1.7.3, заблокувати розгортання 1.8.0.
2. Порівняти конфігурацію 1.7.3 і 1.8.0: `DB_POOL_MAX`/`max pool size`, дефолти драйвера БД, параметри транзакцій, чи не з'явився синхронний зовнішній виклик (SMS/HTTP) усередині запиту або транзакції.
3. Перевірити на БД `max_connections`, кількість відкритих з'єднань і `pg_stat_activity` (або аналог), щоб виключити витік з'єднань у 1.8.0.
4. Прогнати 1.8.0 під навантаженням 12+ RPS у canary/staging з перевіркою p95, error rate і `db_pool_waiting`, перш ніж повертати в прод.

**Щоб не повторилося:**

5. Додати алерт на насичення пулу: `db_pool_waiting > 0` протягом 1–2 хв або `db_pool_in_use / max_pool_size > 0.8`.
6. Додавати на графіки анотації деплоїв/відкатів, щоб зміна версії була видна поруч з p95/5xx.
7. Виправити `POST /parcels`: замість 500 “Cannot read properties of undefined (reading 'trim')” повертати 400 з описом відсутнього поля; додати тести на неповний payload.
8. Розібратися з 12-кратним стрибком SMS: знайти джерело enqueue, перевірити дублікати, додати дедуплікацію за `parcel_id`/message id, token bucket на відправку та узгодити пікову пропускну здатність із квотою провайдера. Окремо алертити не лише 429, а й різке зростання обсягу SMS до виникнення 429.
