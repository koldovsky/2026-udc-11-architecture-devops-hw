**Першопричина — помилка в конфігурації релізу v1.8.0: пул з’єднань API з БД зменшився з 20 до 4.** За звичного денного навантаження пул заповнився, запити стали чекати на з’єднання й отримувати 503 після тайм-ауту. Саме це пояснює повідомлення поштоматів «Сервіс зайнятий, спробуйте пізніше».

**Впевненість дуже висока — орієнтовно 98%.** Це експертна оцінка, не статистично обчислена ймовірність.

Причинний ланцюжок підтверджується трьома незалежними видами даних:

- У [diff релізу](/private/tmp/ws11-c2-task-c/incident/changes/v1.8.0.diff) `DB_POOL_MAX: "20"` перейменували на `DB_POOL_SIZE: "20"` для API та worker. Але [завантажувач конфігурації](/private/tmp/ws11-c2-task-c/app/src/config.js:9) читає лише `DB_POOL_MAX`. Без нього він мовчки використовує **4**.
- У [метриках](/private/tmp/ws11-c2-task-c/incident/metrics/2026-10-14.csv) від хвилини розгортання зайняті з’єднання API впираються рівно в **4**, з’являється черга до **23** запитів. Перед релізом API використовував приблизно 10–13 з’єднань без черги.
- У [логах API](/private/tmp/ws11-c2-task-c/incident/logs/api-2026-10-14.jsonl) зафіксовано **3380 відповідей 503**, усі з `db pool wait timeout after 2000ms`. Код [обробника API](/private/tmp/ws11-c2-task-c/app/src/server.js) перетворює саме цю помилку на 503 із текстом `service busy, try again`.

Отже, технічна деградація почалася **о 14:02**, раніше за приблизний початок користувацьких скарг у вступному описі. Серед 503 було **2586 запитів `/pickup`**, 650 `/parcels` і 144 `/admin/parcels`. Це кількість невдалих запитів; кількість постраждалих людей із цих даних визначити неможливо.

Інші підозрілі сигнали не пояснюють цей збій:

- **SMS 429:** були до релізу й залишалися після відновлення API — зокрема 40 за хвилину о 14:47. У [метриках попереднього дня](/private/tmp/ws11-c2-task-c/incident/baseline/metrics-2026-10-13.csv) за схожих 429 та навантаження API працював нормально. Worker має окремий пул і відправляє SMS поза утриманням з’єднання; `/pickup` не викликає SMS.
- **TLS timeout о 14:01:37:** одинична помилка worker. Її поява раніше за деплой не доводить причинного зв’язку з наступними 503.
- **Heap 81%:** попереднього дня також доходив до 82%. Після розгортання heap упав до 42%, а API вже деградував. Доказів витоку пам’яті немає.
- **500 через `sender.trim()`:** окремий наявний дефект — 125 таких помилок у день інциденту та 128 напередодні. Він не пояснює масові 503.
- **Зелений `/health`:** цей маршрут повертає 200 без звернення до БД, тому не виявляє вичерпання пулу.

**Межа висновку:** немає дампа оточення контейнера чи внутрішньої телеметрії PostgreSQL. Я явно припускаю, що реліз застосував конфігурацію з наданого diff. Точна межа пулу в метриках, характер помилок, невдалий перезапуск і відновлення після відкату дуже сильно підтверджують це припущення.

Помилці дозволили потрапити в продакшн мовчазний fallback на локальний default і відсутність перевірки відповідності deployment-конфігурації коду: наявні тести перевіряють `DB_POOL_MAX`, але не змінні з Compose.
