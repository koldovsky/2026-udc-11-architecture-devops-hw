# RCA інциденту 2026-10-14: поштомати не видають посилки

## Короткий висновок

Причина не в SMS-провайдері, не у витоку пам'яті й не в зростанні трафіку. Це регрес конфігурації в релізі v1.8.0: у `deploy/compose.yaml` змінну `DB_POOL_MAX` перейменували на `DB_POOL_SIZE`, але код застосунку досі читає `DB_POOL_MAX`. Через це після деплою 14.10 о 14:02 API отримав не 20 з'єднань пулу БД, а дефолтні **4**. Пул наситився, запити чекали на з'єднання 2 секунди й падали з `PoolTimeoutError`, який API перетворює на **HTTP 503 `{"error":"service busy, try again"}`**. Саме це екран поштомата показував як «Сервіс зайнятий, спробуйте пізніше».

**Впевненість: дуже висока, ~0,97.** Прямого `docker inspect` з env-змінними немає, але збіг усіх незалежних сигналів — точний і однозначний (див. розділ «Докази»).

## Першопричина

У v1.8.0 в `deploy/compose.yaml` (рядки 86–87 для api і 106–107 для worker у `incident/changes/v1.8.0.diff`) зробили «наведення порядку» в блоці `environment` і замінили:

```diff
-      DB_POOL_MAX: "20"
+      DB_POOL_SIZE: "20"
```

Але `app/src/config.js` у v1.8.0 не змінювався — там досі:

```js
dbPoolMax: Number(env.DB_POOL_MAX) || 4,
```

`DB_POOL_MAX` після деплою в контейнері відсутній, тому `Number(undefined)` дає `NaN`, а `NaN || 4` — дефолт **4**, призначений для локальної розробки. Перевірка на реальному коді:

```text
loadConfig({DB_POOL_SIZE: "20", DB_POOL_WAIT_MS: "2000"}).dbPoolMax -> 4
loadConfig({DB_POOL_MAX:  "20", DB_POOL_WAIT_MS: "2000"}).dbPoolMax -> 20
```

### Механізм відмови

1. До деплою API мав пул на 20 з'єднань; метрики показують 9–13 одночасно зайнятих з'єднань при тому ж навантаженні ~12 rps. У baseline 13.10 максимум — 13 зайнятих, `db_pool_waiting` = 0.
2. Після деплою максимум зайнятих — рівно 4, а черга охочих сягає 23. Це не збіг: 4 — це і є новий дефолт.
3. Кожен запит `/pickup` робить до трьох послідовних захоплень з'єднання (`findWaitingByCode`, `updateParcel`, `addEvent`). При насиченому пулі кожне захоплення може чекати до 2 с, тому p95 сягає ~4,5–5 с, а не 2 с.
4. Після `waitMs = 2000` кидається `PoolTimeoutError`; `server.js` мапить його на 503 с текстом `service busy, try again`. Це дослівно той стан, який бачили мешканці.
5. `/health` весь час відповідав 200, бо він не звертається до БД — тому health-перевірка не побачила деградацію.

## Докази, на яких тримається висновок

1. **Точний збіг старту.** Деплой о 14:02:00, перший 503 — о 14:02:07.172 (на `/parcels`), перший 503 на `/pickup` — о 14:02:27.126. До деплою 503 не було взагалі. Уже о 14:02:02.946 запит `/pickup` тривав 2668 мс — ще до старту worker о 14:02:07, тобто API деградував самостійно.
2. **Стрибок метрик саме на деплої.** 14:01: `db_pool_in_use=12`, `db_pool_waiting=0`, p95=245 мс. 14:02: `in_use=4`, `waiting=4`, p95=945 мс. Далі `in_use` ніколи не перевищує 4, `waiting` сягає 23.
3. **Зворотний стрибок на відкаті.** 14:46: `in_use=4`, `waiting=17`, p95=4697 мс. 14:47: `in_use=14`, `waiting=0`, p95=618 мс. 14:48: p95=296 мс. Це виключає версії про «само пройшло», провайдера чи пам'ять.
4. **Текст помилки.** Усі 3380 відповідей 503 — з `db pool wait timeout after 2000ms`; `server.js` для `PoolTimeoutError` віддає 503 `service busy, try again`. Це і є повідомлення на екрані.
5. **Код і diff.** Єдина функціональна зміна v1.8.0 — перейменування `DB_POOL_MAX` → `DB_POOL_SIZE` у compose. `config.js` читає тільки `DB_POOL_MAX`; `DB_POOL_SIZE` не зустрічається в коді ніде, крім diff. Перевірка `loadConfig` дає 4 за `DB_POOL_SIZE=20` і 20 за `DB_POOL_MAX=20`.
6. **Baseline.** 13.10 — звичайний день без деплою: p95 максимум 260 мс, error_rate максимум 0,69 %, `db_pool_waiting` = 0 весь день, максимум зайнятих — 13. Це показує, що конфігурація на 20 була нормальною для того ж трафіку.
7. **Тести.** `npm test` проходить 15/15, але покриває лише `DB_POOL_MAX` у `config.test.js`; контракт між `compose.yaml` і `config.js` не тестується, тому регрес і проскочив.

## Припущення (явно)

1. `incident/changes/v1.8.0.diff` — це саме той diff, який був задеплоєний о 14:02, без незакомічених змін у конфігурації. Це випливає з `deploys.log` («v1.8.0, config cleanup (#212)») і збігу метрик.
2. Відкат на v1.7.3 повернув і старий `compose.yaml` з `DB_POOL_MAX=20`. Інакше після відкату `db_pool_in_use` не міг би стрибнути до 14: у коді v1.7.3 дефолт теж 4.
3. `db_pool_in_use` / `db_pool_waiting` у метриках — це пул процесу API (так описано в `incident/README.md`), а не спільний пул API і worker.
4. «Сервіс зайнятий, спробуйте пізніше» на екрані поштомата — це UI-текст для 503 `service busy, try again`; прямого логу екрана в теці немає, але текст збігається дослівно.
5. Часи в логах, метриках і `deploys.log` узгоджені в Europe/Kyiv.

## Що варто виправити

1. **Негайно:** повернути в compose `DB_POOL_MAX` (або навчити `config.js` приймати обидва імені з попередженням). Перевірити, що в проді `dbPoolMax=20`.
2. **Захист від повтору:** логувати ефективні значення критичних налаштувань на старті (`db_pool_max`, `db_pool_wait_ms`) і падати на старті, якщо в проді стоїть локальний дефолт.
3. **Контрактний тест:** перевіряти, що кожна env-змінна з `compose.yaml` реально читається `config.js`, і навпаки.
4. **Моніторинг:** алерт на `db_pool_waiting > 0` протягом 2–3 хв і на `db_pool_in_use == db_pool_max`; додати `/ready`, який пробує взяти з'єднання з БД (окремо від легкого `/health`).
5. **Дрібне:** виправити 500 на `POST /parcels` (`sender.trim()` без перевірки) і розібратися з хронічними 429 (знизити `SMS_RATE_PER_SEC` або узгодити ліміт із провайдером), щоб вони не відволікали під час інцидентів.
