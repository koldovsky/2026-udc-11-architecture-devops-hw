Сталося дві пов’язані, але різні проблеми.

Основний інцидент — після деплою `v1.8.0` API фактично перейшов із пулу БД на 20 з’єднань до пулу на 4 з’єднання. У `v1.8.0` в `compose.yaml` змінну `DB_POOL_MAX` перейменували на `DB_POOL_SIZE`, але код читає тільки `DB_POOL_MAX`. Тому спрацював fallback:

```js
dbPoolMax: Number(env.DB_POOL_MAX) || 4
```

Через це під навантаженням запити накопичувалися в черзі, чекали понад 2 секунди й повертали `503`.

Першопричина: несумісна зміна назви production-змінної конфігурації без відповідної зміни коду або перевірки конфігурації під час старту.

Докази:

- Деплой `v1.8.0` відбувся о `14:02:00`.
- API стартував як `v1.8.0` о `14:02:00`.
- Одразу після цього:
  - p95 зріс із приблизно `250 ms` до `945 ms`, потім до `4–5 секунд`;
  - `db_pool_in_use` став `4`, а `db_pool_waiting` зріс до `20+`;
  - error rate піднявся до `10–13 %`;
  - API-логи містять численні `503: db pool wait timeout after 2000ms`.
- Перезапуск API о `14:20` не допоміг, бо застосунок знову прочитав ту саму неправильну змінну й знову використав пул 4.
- Після rollback на `v1.7.3` о `14:47` API швидко відновився: p95 близько `250 ms`, сторінки закрилися о `14:48`.

Упевненість у цій першопричині: дуже висока, приблизно 95%. Збігаються точний час деплою, конкретна помилка конфігурації, метрики пулу, логи таймаутів і ефект rollback. Прямого логу PostgreSQL немає, тому я не стверджую, що база даних сама була несправна; дані показують саме виснаження клієнтського пулу API.

Окремо з приблизно `13:28` була проблема з SMS-провайдером:

- `sms_429_per_min` стабільно перевищував поріг;
- worker масово отримував `429`;
- о `14:01:37` зафіксовано `TLS handshake timeout`;
- причина — імовірно, зовнішнє обмеження або деградація SMS-провайдера.

Це не є першопричиною падіння API: SMS-алерти почалися до деплою, а API деградував саме відразу після `14:02`. SMS-проблема могла збільшити фонове навантаження й погіршити ситуацію, але доказів, що вона спричинила виснаження API-пулу, немає.

Додаткове спостереження: `/health` увесь час відповідав `200`, бо health-check, очевидно, не перевіряє доступність пулу БД або реальний функціональний шлях pickup. Це дозволило інциденту тривати, хоча сервіс формально вважався здоровим.
