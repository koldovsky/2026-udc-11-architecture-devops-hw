# Post-mortem: API не видавав посилки 2026-10-14

- **Дата й тривалість:** 14 жовтня 2026, технічна деградація приблизно 14:02–14:48 (46 хвилин); помітний користувачам вплив приблизно 14:05–14:50. `rg -n '14:05|14:50' incident/README.md` → цей інтервал; межі метрик і алертів — у хронології [RCA](rca.md).
- **Вплив:** частина мешканців не змогла забрати посилки; `rg -c '"path":"/pickup","status":503' incident/logs/api-2026-10-14.jsonl` → `2586` невдалих запитів, не людей. `rg -c '"path":"/parcels","status":503' incident/logs/api-2026-10-14.jsonl` → `650`; `rg -c '"path":"/admin/parcels","status":503' incident/logs/api-2026-10-14.jsonl` → `144`. Кількість людей і долю кожної посилки дані не встановлюють.
- **Виявлення:** `rg -n 'ApiLatencyP95High|Api5xxRateHigh|fired_at' incident/alerts.json` → API page-алерти о 14:06 та 14:07, приблизно через 4–5 хвилин після технічного початку; `rg -n '14:08' incident/oncall-chat.md` → повідомлення гарячої лінії.
- **Причина:** релізний Compose перейменував `DB_POOL_MAX` на `DB_POOL_SIZE`, а код продовжив читати `DB_POOL_MAX` і використав fallback 4. `rg -n -e 'DB_POOL_MAX' -e 'DB_POOL_SIZE' incident/changes/v1.8.0.diff` → зміна в обох сервісах; повний ланцюжок та обмеження доказів — у [RCA](rca.md).

Рішення чергової розглядалися в контексті доступних тоді сигналів: SMS warning спрацював раніше, heap warnings були помітні, `/health` залишався зеленим, а точну конфігураційну несумісність не було видно без зіставлення diff і коду. Це системна прогалина в перевірках і спостережуваності.

## Що спрацювало добре

- Пейджі затримки й 5xx повідомили про вплив; час і умови видно командою `rg -n 'ApiLatencyP95High|Api5xxRateHigh|fired_at' incident/alerts.json` (14:06 і 14:07).
- Відкат повернув сервіс: `rg '2026-10-14T14:47:' incident/deploys.log` → v1.7.3; `rg '^2026-10-14T14:48:' incident/metrics/2026-10-14.csv` → p95 296 мс, черга 0.

## Що спрацювало погано

- Зміна назви змінної в релізному Compose не перевірялася проти `loadConfig()`; fallback 4 зробив помилку непомітною при старті. Докази — рядки 1–3 таблиці RCA.
- `/health` перевіряє тільки процес, а не доступність маршруту, що використовує БД. Доказ — рядок 9 таблиці RCA.
- SMS 429 і heap warnings відвели увагу від часової межі деплою; повторний запуск тієї ж версії не змінив конфігурацію. Команди — хронологія й розділ «Що НЕ є причиною» RCA.

## Де нам пощастило

- Попередній реліз v1.7.3 був доступний для відкату; `rg '2026-10-14T14:47:' incident/deploys.log` показує фактичний rollback. Це не гарантує, що попередній образ буде доступним наступного разу.

## Action item → правило перевірки (Task D)

Для Task D реалізовано **#1** як правило `I1` у `tools/check-deploy.mjs`. Воно перевіряє, що `api` і `worker` у Compose задають саме `DB_POOL_MAX` додатним числом або обов'язковим посиланням `${DB_POOL_MAX:?…}`; необов'язкове посилання, яке може залишити змінну порожньою, не проходить. Код читає `DB_POOL_MAX` у `app/src/config.js:9`, тому перейменування на `DB_POOL_SIZE` в будь-якому з двох сервісів буде FAIL ще до деплою. Тест `tools/test/check-deploy.test.mjs` відтворює конфігурацію інциденту (FAIL) і допускає коректну форму `environment:` як список, обов'язкове посилання та сторонній сервіс без пулу БД (PASS). Перша чернетка AI провалила **0** з 13 наявних правил; результат збережено в `ai-runs/check-deploy-v1.txt`.
