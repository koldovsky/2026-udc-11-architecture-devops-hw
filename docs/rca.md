# RCA: інцидент 2026-10-14 — поштомати відповідають «Сервіс зайнятий»

## Коротко

14 жовтня 2026 з 14:02 до 14:47 у середньому ~11 % (пік 13,5 %) запитів до API, зокрема
`POST /pickup`, завершувалися 503 — екран поштомата показував «Сервіс зайнятий, спробуйте
пізніше», і частина мешканців не могла забрати посилки. Причина: реліз v1.8.0
(«config cleanup») перейменував у `deploy/compose.yaml` змінну `DB_POOL_MAX` на
`DB_POOL_SIZE`, якої застосунок не читає, — пул з'єднань БД в API впав з 20 до
дефолтних 4. Відкат на v1.7.3 о 14:47 повернув стару назву змінної і відновив сервіс.

## Першопричина

Ланцюжок, ланка за ланкою:

1. Реліз v1.8.0 «config cleanup» відсортував змінні оточення в `deploy/compose.yaml` за
   алфавітом і при цьому **перейменував `DB_POOL_MAX: "20"` на `DB_POOL_SIZE: "20"`** для
   обох сервісів (`incident/changes/v1.8.0.diff:86-87` і `:106-107`).
2. Застосунок читає тільки `DB_POOL_MAX`: `dbPoolMax: Number(env.DB_POOL_MAX) || 4`
   (`app/src/config.js:9`). Змінної `DB_POOL_SIZE` у коді немає взагалі
   (`grep -rn DB_POOL_SIZE app/src app/bin` → порожньо).
3. Після перезапуску о 14:02 API піднявся з **пулом 4 з'єднання замість 20** — мовчки,
   бо `|| 4` — це «розумний дефолт для локальної розробки», і жодної помилки не було.
4. Пообідній трафік (~12 rps, як і напередодні) не вміщається в 4 з'єднання: запити
   чекають на пул до `DB_POOL_WAIT_MS = 2000` мс і падають з `PoolTimeoutError`
   (`app/src/db.js:74-78`).
5. `PoolTimeoutError` API перетворює на **503 `service busy, try again`**
   (`app/src/server.js:65`) — саме цей текст бачить екран поштомата: «Сервіс зайнятий».
6. Рестарт о 14:20 не допоміг — конфіг у compose той самий. Відкат на v1.7.3 о 14:47
   повернув `DB_POOL_MAX: "20"`, пул знову 20 — одужання миттєве (p95 з 4697 до 296 мс
   за дві хвилини).

## Чинники, що сприяли (contributing factors)

- **Мовчазний фолбек конфігу:** `Number(env.DB_POOL_MAX) || 4` (`app/src/config.js:9`) —
  незнайома чи загублена змінна не дає ні помилки, ні попередження: сервіс стартує
  «здоровим» з непридатним для продакшну пулом.
- **`/health` не торкається БД** (`app/src/server.js:37`; тест
  `app/test/server.test.js` «health answers without touching the database») — тож
  «/health весь час відповідає 200» (чат, 14:29) нічого не каже про пул.
- **Немає алерту на `db_pool_waiting`** — черга в пул росла з 14:02, а перший пейдж
  прийшов о 14:06 за наслідком (p95).
- **Немає детермінованої перевірки відповідності compose ↔ config.js** — перейменування
  пройшло рев'ю і деплой без жодного сигналу.
- **Щоденний шум 429** (`SMS_RATE_PER_SEC: "20"` у compose на момент інциденту —
  `git show main:deploy/compose.yaml`, рядок 20 — понад контрактний ліміт 10/с,
  `materials/vendors/sms-provider.md:16`; у Task D знижено до 10) — перша гіпотеза
  чергової пішла хибним слідом.
- **Деплой у пообідній пік** (14:02) — збільшив вплив і ускладнив діагностику.

## Впевненість

**Висока.** Ланцюжок повний і незалежно підтверджений чотирма видами даних: зміна
(diff) → механізм (код) → симптоми (метрики: пул рівно 4; логи: 3380 × `db pool wait
timeout`) → одужання точно в момент відкату. Трафік, heap і 429 виключені порівнянням з
базовим днем. Бракує лише прямого знімка env контейнера під час інциденту
(`docker inspect`), але непрямі докази однозначні; змінити висновок міг би хіба лог, де
API з v1.8.0 стартує з пулом 20, — такого немає.
