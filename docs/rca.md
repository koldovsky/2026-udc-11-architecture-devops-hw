## Першопричина

Реліз v1.8.0 перейменував ключ Compose для API й worker з `DB_POOL_MAX: "20"` на `DB_POOL_SIZE: "20"`, не змінивши `loadConfig()`. Функція читає `DB_POOL_MAX`, а за його відсутності повертає 4. API створює пул із цього значення. При звичайному навантаженні чотири з'єднання заповнилися, запити чекали понад 2000 мс, а `PoolTimeoutError` перетворювався на HTTP 503 з текстом `service busy, try again`. `/pickup` використовує цей пул. Повторний запуск тієї самої конфігурації залишив дефект; відкат повернув ключ і працездатність.

Немає дампа фактичних змінних оточення продакшн-контейнера чи телеметрії PostgreSQL. Застосування конфігурації з релізного diff — припущення, яке узгоджується з межею 4 у метриках та відновленням після відкату. Наявний `deploy/compose.yaml` — стан до v1.8.0; інцидентна зміна показана в `incident/changes/v1.8.0.diff`.

## Чинники, що сприяли

- Мовчазний fallback `4` для локальної розробки приховав відсутність продакшн-змінної: `rg -n 'DB_POOL_MAX|dbPoolMax' app/src/config.js app/test/config.test.js` → код і тести очікують тільки `DB_POOL_MAX`. У наданих матеріалах немає перевірки контракту з релізним Compose.
- `/health` повертав 200 без БД і не показував неспроможність `/pickup`: `rg -n 'GET.*health|async pickup|withConnection' app/src/server.js app/src/parcels.js` → рядок 37 `server.js` і рядки 59–67 `parcels.js`.
- Паралельні SMS 429 і heap warnings дали правдоподібні хибні напрямки діагностики: `rg -n '14:10|14:12|14:29' incident/oncall-chat.md` → обговорення SMS, heap та зеленого `/health`. Це пояснює затримку локалізації, не провину людей.

## Впевненість

**Висока** щодо конфігураційної регресії та механізму 503: diff, `loadConfig()`, відтворення `4 20`, часова межа в метриках, тайм-аути, невдалий перезапуск і успішний відкат узгоджуються. Без дампа prod-env це не формальний 100% доказ. Ефективний `dbPoolMax` у контейнері v1.8.0 і телеметрія PostgreSQL могли б уточнити висновок. Кількість постраждалих людей і факт втрати посилок із наданих даних не визначаються.
