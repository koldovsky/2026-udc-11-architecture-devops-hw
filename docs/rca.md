# RCA: інцидент 2026-10-14

## Коротко

З 14:02:07 до 14:46:58 (майже 45 хвилин) API відповів 3380 разів кодом 503, з них 2586 — на
`POST /pickup`, тому частина мешканців бачила на екрані поштомата «Сервіс зайнятий» і не могла
забрати посилку. Причина: реліз v1.8.0 перейменував у `compose.yaml` змінну `DB_POOL_MAX` на
`DB_POOL_SIZE`, а код читає лише стару назву, тому пул з'єднань мовчки впав із 20 до 4. Сервіс
відновив відкат на v1.7.3.

## Першопричина

1. **Що змінилося.** Реліз v1.8.0 упорядкував змінні в `deploy/compose.yaml` за алфавітом і серед
   перестановок замінив `DB_POOL_MAX` на `DB_POOL_SIZE` для `api` і `worker` (докази 2, 3).
2. **Що через це стало інакше.** Код читає лише `DB_POOL_MAX`, а якщо її немає, бере значення для
   локальної розробки — 4, без жодної помилки (`app/src/config.js:8-9`, доказ 4). API стартував із
   пулом 4 замість 20, тоді як за денного навантаження йому потрібно 10–13 з'єднань (докази 5, 7).
3. **Чому користувачі побачили саме це.** Запити стали в чергу до пулу, а після 2000 мс очікування
   пул дає `PoolTimeoutError`, який API перетворює на 503 «service busy» (`app/src/db.js:77`,
   `app/src/server.js:65`, докази 6, 9). Найбільше постраждав `/pickup`, бо бере з'єднання тричі
   поспіль (`app/src/parcels.js:61-67`, докази 10, 11).
4. **Чому перезапуск не допоміг, а відкат допоміг.** Перезапуск лишив ту саму версію і ті самі
   змінні, тож пул знову став 4 (доказ 12). Відкат повернув v1.7.3 з `DB_POOL_MAX`, і вже в першу
   хвилину API тримав 14 з'єднань (доказ 13).

## Чинники, що сприяли (contributing factors)

Команди — з кореня репо, функції з розділу «Докази» тут не потрібні.

- **Значення для локальної розробки діє в продакшні мовчки.** Без `DB_POOL_MAX` сервіс стартує з
  пулом 4 і нічого не повідомляє, а старт пише в лог лише версію.
  - `sed -n 8,9p app/src/config.js` → `// sensible default for local dev`, `dbPoolMax: Number(env.DB_POOL_MAX) || 4,`
  - `sed -n 95p app/src/server.js` → `log.info("service started", { version: VERSION })`: розміру пулу немає.
- **Тести це закріплюють і не звіряють назви.** Тест вимагає пул 4 за порожнього оточення, а тести застосунку
  взагалі не читають `compose.yaml`.
  - `sed -n 8p app/test/config.test.js` → `assert.equal(config.dbPoolMax, 4);`
  - `grep -rl 'compose' app/test` → нічого не знаходить.
- **Перейменування загубилося в перестановках.** Реліз «config cleanup» переставив усі змінні, тож зміна змісту
  виглядала як наведення порядку: із 22 змінених рядків блоку `environment:` перейменування стосуються лише 4.
  - `sed -n '80,115p' incident/changes/v1.8.0.diff | grep -c '^[-+]'` → `22`
  - `sed -n '80,115p' incident/changes/v1.8.0.diff | grep -c '^[-+].*DB_POOL_[MS]'` → `4`
- **`/health` не показує проблему.** Він не звертається до бази, тому відповідав 200 увесь час.
  - `sed -n 37p app/src/server.js` → `return [200, { status: "ok", version }]`, без виклику пулу.
  - `grep -n '/health' incident/oncall-chat.md` → рядок 17, 14:29: «весь час відповідає 200».
- **Немає алерту на пул.** Метрика черги є, але алертів на неї немає. Перший пейдж прийшов о 14:06, за 4 хвилини
  після релізу, і показував симптом, а не причину.
  - `head -n 1 incident/metrics/2026-10-14.csv` → серед колонок є `db_pool_waiting`.
  - `grep -c 'db_pool' incident/alerts.json` → `0`
  - `grep -n 'fired_at' incident/alerts.json` → 13:37, 14:06, 14:07.
- **Алерт на 429 — щоденний шум, який відвів увагу.** 13.10 без збою `sms_429_per_min` перевищував 20 протягом 87
  хвилин. Експорту алертів за 13.10 немає, але умова спрацювання тоді теж виконувалась. Цей шум забрав час:
  провайдера перевіряли до 14:36. Імовірне джерело самих 429 — наш конфіг: темп удвічі вищий за ліміт провайдера.
  - `awk -F, '$8>20{n++} END{print n}' incident/baseline/metrics-2026-10-13.csv` → `87`
  - `grep -n 'провайдер' incident/oncall-chat.md` → рядки 6, 10, 13, 14, 18, 21, зокрема 14:10 «провайдер нас душить», 14:36
    «у них інцидентів немає».
  - `git show main:deploy/compose.yaml | grep -n 'SMS_RATE_PER_SEC'` → рядки 20 і 34, `"20"`. Конфіг узято з `main`, бо
    Task D змінює цей файл у гілці.
  - `sed -n 16p materials/vendors/sms-provider.md` → `Ліміт нашого облікового запису — 10 повідомлень на секунду…`
- **Немає правила «спершу відкотити останній реліз».** Про реліз згадали о 14:13, а відкат почали о 14:45, бо реліз
  здавався несуттєвим.
  - `grep -n 'викотив' incident/oncall-chat.md` → рядок 12, 14:13: «нічого суттєвого».
  - `grep -n 'відкочую' incident/oncall-chat.md` → рядок 19, 14:45: «на всяк випадок».

## Впевненість

**Висока.** Ланцюжок сходиться з чотирьох незалежних боків: diff показує перейменування, код дає
рівно 4 (відтворено запуском), метрика стоїть рівно на 4 всі 45 хвилин, а межі збою збігаються з
релізом і відкатом до секунд. День 13.10 з тим самим навантаженням і тими самими 429 збою не мав.

**Чого бракує:**

- Немає `docker inspect` контейнера v1.8.0, тому значення змінної в ньому виведено, а не прочитано.
- Немає метрик самої бази, тому гіпотеза про PostgreSQL спростована лише непрямо.
- `app/` у репо — версія 1.7.3, а v1.8.0 не запускалась під навантаженням. `config.js` реліз не змінював,
  тож для читання пулу це не важить, але логіку пулу в продакшні (PostgreSQL) тут не видно.

**Що могло б змінити висновок:** якщо в контейнері v1.8.0 пул виявиться 20, або якщо v1.8.0 із
поверненою назвою `DB_POOL_MAX` дасть той самий збій на стенді. Цю перевірку варто зробити перед
повторним випуском.
