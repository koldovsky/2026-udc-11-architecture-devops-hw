# Runbook: API повільний або віддає 5xx (`ApiLatencyP95High`, `Api5xxRateHigh`)

Для чергового, який інциденту 2026-10-14 не бачив. Розбір того інциденту — `docs/rca.md`.

- **Алерт(и):** `ApiLatencyP95High` — `p95_ms > 2000` протягом 3 хв; `Api5xxRateHigh` —
  `error_rate > 0.05` протягом 3 хв (`incident/alerts.json`). Обидва — page.
- **Що це означає для користувачів:** мешканці на екрані поштомата бачать «Сервіс зайнятий,
  спробуйте пізніше» (`503`) або довго чекають і не можуть забрати посилку; служба доставки не
  може зареєструвати посилки (`POST /parcels`), персонал — відкрити список.
- **Скільки є часу:** вплив уже є, коли прийшов пейдж. Удень у будні (12:00–17:00 — пік
  доставок і видач) кожні 10 хв — сотні відмов і дзвінки на гарячу лінію. Мета — відновити
  за 15 хв; якщо за 15 хв причини немає, а деплой був — відкочуйте (крок 3 «Перших 5 хвилин»).

Усі команди — на VM, з теки репозиторію сервісу (там, де лежить `deploy/compose.yaml`):

```bash
ssh poshtomat-prod-1
cd <тека репо на VM>          # та сама, з якої робили docker compose up -d
DC="docker compose -f deploy/compose.yaml"
```

## Перші 5 хвилин

1. **Напишіть у #poshtomat-oncall** «взяв(ла) `<алерт>`, дивлюсь» — щоб ніхто не деплоїв паралельно.
2. **Чи був деплой або рестарт за останню годину?**
   ```bash
   $DC ps --format '{{.Service}} {{.Status}}'          # "Up 12 minutes" = свіжий старт
   curl -s localhost:8080/health                       # {"status":"ok","version":"1.8.0"}
   ```
   Версія відрізняється від учорашньої або `Up` < 60 хв → імовірно, причина в релізі.
3. **Свіжий деплой + пейдж → відкат одразу, не з'ясовуючи причину** (розділ «Що робити», рядок 1).
   Повідомте автора релізу. Розбиратися — після відновлення.
4. **Деплою не було → яка помилка домінує** (розділ «Діагностика», рядок 1).

> `/health` повертає 200, навіть коли пул з'єднань забитий: він не ходить у БД
> (`app/src/server.js:37`). **200 від `/health` не означає, що сервіс здоровий.**

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Яка помилка домінує в API за 10 хв? | `$DC logs --no-log-prefix --since 10m api \| grep -o '"error":"[^"]*"' \| sort \| uniq -c \| sort -rn` | `db pool wait timeout after …ms` — запити не дочікуються з'єднання з пулу → «Як підтвердити причину». `reading 'trim'` — давній фоновий баг `/parcels`, буває щодня, не причина пейджу |
| Що було в цей самий час учора? | `$DC logs --no-log-prefix --since 24h10m --until 24h api \| grep -o '"error":"[^"]*"' \| sort \| uniq -c` | Що є й учора, те не причина сьогоднішнього пейджу. Шукайте **нове** |
| Які запити падають? | `$DC logs --no-log-prefix --since 10m api \| grep '"status":5' \| grep -o '"path":"[^"]*","status":[0-9]*' \| sort \| uniq -c` | `/pickup` з 503 — мешканці не можуть забрати посилки, найвищий пріоритет |
| Які налаштування пулу реально в API? | `$DC exec api node -e 'import("./src/config.js").then(c=>{const x=c.loadConfig();console.log("dbPoolMax",x.dbPoolMax,"dbPoolWaitMs",x.dbPoolWaitMs)})'` | Норма для продакшну — `dbPoolMax 20`. `4` = змінна `DB_POOL_MAX` не задана, спрацювало значення за замовчуванням (`app/src/config.js:9`) |
| Які змінні пулу передано контейнеру? | `$DC exec api printenv \| grep '^DB_POOL'` | Має бути `DB_POOL_MAX=20`. `DB_POOL_SIZE` або інша назва — код її **не читає** |
| Чи пул забитий? (метрики) | у моніторингу: `db_pool_in_use` і `db_pool_waiting` за останні 15 хв | `db_pool_in_use` рівний пласкій лінії на значенні `dbPoolMax`, `db_pool_waiting` > 0 — пул замалий або з'єднання тримаються довго |
| SMS-провайдер повертає 429? | `$DC logs --no-log-prefix --since 10m worker \| grep -c 'rate limited'` | Десятки на хвилину вдень — норма (так щодня, `docs/rca.md`). На API **не впливає**: worker — окремий процес зі своїм пулом |
| Пам'ять API | `$DC logs --no-log-prefix --since 10m api \| grep -c 'heap usage high'` | Кілька за 10 хв — норма (щодня ~60–70 за 4 год). Сам по собі не причина 503 |
| БД жива? | `time sudo -u postgres psql -d poshtomat -c 'select 1'` | `1` за частки секунди — БД жива, шукайте в API; довго або помилка → «Ескалювати». PostgreSQL — на самій VM, поза compose (`docs/ops/backup-runbook.md:7`) |
| Зараз 02:00–02:30? | `date` | У це вікно бекап блокує записи в БД (`docs/ops/backup-runbook.md:10-11`) — помилки запису очікувані, чекайте 02:30 |

## Як підтвердити причину

**Пул з'єднань API замалий / не той конфіг** (інцидент 2026-10-14) — обидва факти разом:

1. У лозі API домінує `db pool wait timeout`, а вчора о тій самій порі його не було.
2. `dbPoolMax` у контейнері (рядок «Які налаштування пулу реально в API?») менший за 20,
   **або** `db_pool_in_use` — пласка лінія на одному значенні, а `rps` такий самий, як учора.

Якщо `dbPoolMax` = 20, а тайм-аути пулу все одно є — з'єднання тримаються довго: повільна БД
або важкий запит → «Ескалювати».

## Що робити

| Ситуація | Дія | Команда | Ризик / що перевірити після |
|---|---|---|---|
| Деплой за останню годину | Відкотити **образ і compose** на попередній тег | `git fetch --tags && git checkout <попередній тег> && $DC up -d --build` (**припущення**: на VM — робоча копія репо з тегами; тег — з `git tag --sort=-creatordate \| head -3`) | Відкочувати лише образ без `deploy/compose.yaml` недостатньо — конфіг живе в compose. Після: «Як переконатися…» |
| `dbPoolMax` ≠ 20, змінна названа інакше | Якщо відкат неможливий — виправити назву на `DB_POOL_MAX` у `deploy/compose.yaml` і перезапустити | `$DC up -d api worker` | Зміна на VM поза git — одразу PR з тим самим виправленням, інакше наступний деплой її затре |
| Тайм-аути пулу, `dbPoolMax` = 20, деплою не було | Не перезапускати навмання; ескалювати (БД) | `sudo -u postgres psql -d poshtomat -c "select state, count(*) from pg_stat_activity group by 1"` | Перезапуск API лише скине чергу на хвилину; 2026-10-14 рестарт не допоміг |
| Лише 429 / heap / TLS-збій, без тайм-аутів пулу | Це не причина пейджу — шукайте далі по «Діагностиці» | — | Не витрачайте час на звернення до провайдера SMS, поки API віддає 503 |

## Коли ескалювати і кого кликати

- 15 хв без зрозумілої причини, а відкат не допоміг або деплою не було → розробник, що не
  чергує (Андрій / Олена), у #poshtomat-oncall і дзвінком.
- БД не відповідає на `select 1` або в `pg_stat_activity` сотні сесій → розробник,
  відповідальний за інфраструктуру й бекапи (`docs/ops/backup-runbook.md`, власник).
- Підозра на витік персональних даних (номери телефонів у логах/відповідях) → додатково
  dpo@example.org протягом доби (`materials/compliance.md:25-26`).
- Відмови `/pickup` понад 30 хв у робочий час → повідомити координаторку проєкту, щоб гаряча
  лінія відповідала мешканцям однаково.

## Як переконатися, що все гаразд

- Через 2–3 хв після дії: `$DC logs --no-log-prefix --since 2m api | grep -c 'db pool wait timeout'` → `0`.
- `curl -s localhost:8080/health` показує очікувану версію.
- У моніторингу: `p95_ms` < 300 мс, `error_rate` < 0.01, `db_pool_waiting` = 0 — 10 хв поспіль;
  пейджі закриваються самі (умова «протягом 3 хв»).
- Попросіть гарячу лінію перевірити, чи є свіжі скарги з поштоматів.
- Напишіть у #poshtomat-oncall: що зроблено, о котрій відновилось, чи потрібен розбір.
