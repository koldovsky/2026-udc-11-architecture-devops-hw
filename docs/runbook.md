# Runbook: API повільний або віддає 5xx (`ApiLatencyP95High`, `Api5xxRateHigh`)

> Для чергового, який не бачив інциденту 2026-10-14. Кожен крок — команда для копіювання і
> як читати її результат. Найчастіша причина цього класу — **вичерпаний пул з'єднань з БД у
> процесі API**. Розбір прикладу — у `docs/rca.md`.

- **Алерти:**
  - `ApiLatencyP95High` (page) — `p95_ms > 2000` протягом 3 хв;
  - `Api5xxRateHigh` (page) — `error_rate > 0.05` протягом 3 хв;
  - `ApiDbPoolWaiting` (page, коли з'явиться — post-mortem #4) — `db_pool_waiting > 0` дві
    хвилини поспіль.
  - **Не цей клас:** `SmsProvider429RateHigh` (warning). Це worker, а не API, і він
    спрацьовує майже щодня в обідній пік (13:25–15:00). API до SMS-провайдера не звертається.
- **Що це означає для користувачів.** Поштомат після введення коду пише «Сервіс зайнятий,
  спробуйте пізніше» — люди не можуть забрати посилки. Також не реєструються нові посилки
  (`POST /parcels`) і не відкривається адмінка. **`/health` при цьому відповідає 200** — він
  не торкається БД (`app/src/server.js:37`), тож не вірте йому.
- **Скільки є часу: вплив уже серйозний.** У пік (13:00–15:30) це ~75 відмов на хвилину:
  14.10 — 3380 за 45 хв. Кожна хвилина додає ризик «напів-видачі»: посилка позначена
  виданою, а комірка не відчинилася. **Мета — пом'якшити за 15 хв від пейджа**, причину
  шукати після.

Усі команди — на VM `poshtomat-prod-1`, з теки з checkout репозиторію. Деплой — це
`docker compose up -d` на VM після злиття в `main` (`materials/team.md`). Припущення: код
оновлюють `git pull` у цій теці.

```bash
ssh poshtomat-prod-1
cd /opt/poshtomat        # припущення: там само, де backup.sh. Інакше шлях покаже: docker compose ls
dc() { (cd deploy && docker compose "$@"); }   # з теки deploy/, як звичайний деплой: підхопить compose.override.yaml і .env, якщо вони є
```

- **Нова SSH-сесія — повторіть цей блок.** Функція `dc` живе лише в поточній оболонці. Без
  неї пишіть повністю: `(cd deploy && docker compose …)`. Явний `-f deploy/compose.yaml` не
  використовуйте: з ним Compose не читає `compose.override.yaml`.
- **Припущення:** ваш користувач на VM може запускати `docker` без `sudo` (входить до групи
  `docker`). Якщо ні: `dc() { (cd deploy && sudo docker compose "$@"); }`.
- **Звідки справжній `SMS_TOKEN`.** У репо в `deploy/compose.yaml` і `deploy/Dockerfile`
  стоїть `CHANGE_ME`, а продакшн шле SMS з токеном (`materials/vendors/sms-provider.md`).
  Отже, токен на VM додано поза комітом: локальною правкою `compose.yaml` або файлом
  `compose.override.yaml` (чи `.env`, якщо один із них посилається на `${SMS_TOKEN}`).
  Звірте раз за зміну, не друкуючи токен:

  ```bash
  git diff HEAD --name-only; ls -a deploy/
  dc exec -T worker sh -c 'test -n "$SMS_TOKEN" && test "$SMS_TOKEN" != CHANGE_ME && echo "token ok" || echo "NO TOKEN"'
  ```

  `NO TOKEN` — SMS про прибуття зараз не надсилаються. Це окрема проблема від пейджа API:
  повідомте в #poshtomat-oncall і другому розробнику. Токен — у менеджері паролів команди
  (`materials/vendors/sms-provider.md`).

  Якщо `git diff HEAD --name-only` показує `deploy/compose.yaml`, токен вписано локально. Тоді
  ознака «хтось правив конфіг» у кроці 2 — лише інші змінені рядки, а відкат іде з
  відновленням токена (див. «Відкат» нижче). Поза інцидентом краще перенести токен у
  `deploy/compose.override.yaml` (для `api` і `worker`) і повернути `compose.yaml` до коміту:
  тоді відкат і повернення на `main` проходять без `stash`.
- **Дашборд** — у системі моніторингу, з якої приходять пейджі. Посилання — в анотації
  пейджа. Припущення: там поминутні `rps`, `p95_ms`, `error_rate`, `db_pool_in_use`,
  `db_pool_waiting`, `heap_used_pct` — ті самі колонки, що в `incident/metrics/`. Сам API
  метрик через HTTP не віддає. Без дашборда стелю пулу покажуть проба з кроку 5 і команда
  `loadConfig` з «Діагностики».

## Перші 5 хвилин

1. **Візьміть пейдж** у #poshtomat-oncall одним рядком: «взяв(-ла) <алерт>, дивлюсь».
2. **Чи змінювалося щось за останні 2 години?** Це головне питання.

   ```bash
   git reflog -5 --date=iso      # коли на цій VM змінювався код (pull/checkout) — це і є час деплою
   git diff HEAD -U0 | grep '^[-+][^-+]' | grep -v SMS_TOKEN   # непорожньо = відстежувані файли змінено без коміту (рядки з токеном не рахуються)
   dc ps -a                      # CREATED — коли контейнер створено (деплой, зміна compose.yaml); STATUS «Up N minutes» — коли (пере)запущено
   dc logs api --since 2h --no-log-prefix | grep '"msg":"service started"'   # версія на кожному старті
   ```

   Як читати:
   - Рядок `reflog` або `CREATED` ≤ 60 хв до пейджа, або непорожній вивід `git diff` → після
     кроку 3 (30 с на докази) — **одразу «Що робити», рядок 1 (відкат)**. Не перезапускайте і
     не шукайте причину до відкату.
   - `CREATED` давно, свіжий лише `STATUS`, а версія в `service started` та сама — це був
     перезапуск, а не деплой. Відкат не допоможе, йдіть до кроку 3, потім 4.
   - Нічого свіжого — крок 3 (докази не завадять), далі крок 4.
3. **Перед відкатом чи перезапуском — 30 с на докази.** Після перестворення контейнера
   `dc logs` старих рядків уже не покаже. 14.10 фактичних змінних контейнера ніхто не зберіг
   (`docs/rca.md`, «Впевненість»).

   ```bash
   ts=$(date +%Y%m%d-%H%M); mkdir -p ~/incident-$ts
   dc logs api --since 3h --no-log-prefix > ~/incident-$ts/api.jsonl
   dc logs worker --since 3h --no-log-prefix > ~/incident-$ts/worker.jsonl
   dc exec -T api env | grep -E '^(DB_POOL|NODE_ENV|PORT)' > ~/incident-$ts/env.txt   # лише ці змінні: повний env містить SMS_TOKEN
   git rev-parse HEAD > ~/incident-$ts/commit.txt; git status --short -uno >> ~/incident-$ts/commit.txt
   ```

4. **Яка помилка?**

   ```bash
   dc logs api --since 10m --no-log-prefix | grep '"level":"error"' | grep -o '"error":"[^"]*"' | sort | uniq -c | sort -rn
   ```

   - `db pool wait timeout after 2000ms` — запити не дочекалися з'єднання з пулу. Пул
     вичерпано, переходьте до «Діагностики».
   - `Cannot read properties of undefined (reading 'trim')` — відомий фоновий баг: 500 на
     `POST /parcels`. Щодня: ~5 на годину поза 13:00–15:00, ~45 у 13:00–14:00 і ~70–75 у
     14:00–15:00 (у вікні `--since 10m` — до ~20: 13.10 — 19). Сам він пейдж не викликає. Якщо крім нього
     нічого немає, а пейдж є — шукайте далі.
   - Помилок немає, а p95 високий — повільно, але без відмов. Дивіться БД і хост у
     «Діагностиці».
5. **Проба, яка справді йде через пул.** У нашому коді вона лише читає: шукає неіснуючу
   сесію (`app/src/db.js:55-57`), тому завжди закінчується `403`, якщо дочекалася
   з'єднання. `CHANGE_ME` залиште як є: сесії з таким id немає. З токеном персоналу
   відповідь буде `200` зі списком посилок, а не `403`, як нижче.

   ```bash
   for i in 1 2 3 4 5; do curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -H 'Authorization: Bearer CHANGE_ME' http://localhost:8080/admin/parcels; done
   ```

   - `403` за < 0,5 с усі п'ять разів — пул і БД відповідають без черги.
   - `403` за 0,5–2 с — черга до пулу вже є: запит чекав на з'єднання, але дочекався. Це той
     самий клас проблеми — переходьте до «Діагностики». 14.10 так відповідала більшість
     успішних запитів: 90 % тривали ≥ 0,5 с.
   - `503` за ~2 с (рівно `DB_POOL_WAIT_MS`) — черга довша за таймаут, пул вичерпано. Це той
     самий симптом, що на поштоматах.
   - `000` — API не відповідає взагалі. Перевірте `dc ps -a` (рядок `api` зі статусом
     `Exited` або його немає) і `dc logs api --tail 50 --no-log-prefix`. У `compose.yaml` немає
     `restart:`, тож процес, що впав, сам не підніметься: `dc up -d api`, далі ескалюйте з
     останніми рядками лога.

## Як підтвердити причину

Два факти відрізняють **«пул замалий через конфігурацію»** (так було 14.10) від інших
причин:

1. `db_pool_in_use` стоїть рівно на одному числі **нижче 20**, а `db_pool_waiting` > 0, хоча
   `rps` звичайний для цієї години.
2. `dc exec api ... loadConfig()` (див. «Діагностику») показує `dbPoolMax` ≠ 20.

Інші причини цього класу і їхні ознаки:

- **Повільна БД або блокування.** `in_use` = 20 (повна стеля), у `pg_stat_activity` довгі
  запити. З 02:00 до 02:30 нічний бекап тримає блокування на запис
  (`docs/ops/backup-runbook.md`). `INSERT`/`UPDATE` (`/pickup`, `POST /parcels`) тоді або
  чекають — і з'являється черга до пулу, — або падають з помилкою — і з'являються 500 з новим
  текстом (крок 4). В обох випадках у цьому вікні — рядок 3.
- **Аномальний трафік.** `rps` значно вищий за звичний для цієї години.

**Що НЕ є причиною пейджа API**, хоч і впадає в око (усе це було 14.10 і буває щодня —
`docs/rca.md`, Н1–Н3):

- SMS 429 і `sms provider rate limited` у worker-і;
- `heap usage high` при 75–82 %;
- поодинокий `TLS handshake timeout to sms.example.net`;
- `/health` = 200.

Тимчасово можна підняти `DB_POOL_MAX` до 30, якщо БД має запас з'єднань | `sudo -u postgres psql -tAc "show max_connections;"` — має бути ≥ 30 (api) + 20 (worker) + 20 (нічна задача о 03:15 відкриває ще один пул з тими самими змінними) + 10. Далі правка `compose.yaml` і `dc up -d api` | Після — `db_pool_waiting` = 0. Повернути 20, коли трафік спаде |
| 5. Помилки не про пул (новий текст 500) | 02:00–02:30 — спершу рядок 3 (бекап). Якщо помилки з'явилися після деплою — рядок 1. Інакше — ескалювати з текстом помилки і часом першої появи | `dc logs api --since 1h --no-log-prefix \| grep '"level":"error"' \| grep -v -e "reading 'trim'" -e 'db pool wait timeout' \| head -3` | Порожньо — нових помилок немає, лише відомі (крок 4) |
| 6. `heap_used_pct` стабільно > 90 % і не падає (справжній витік) | Перезапуск api — **лише в цьому випадку**. Від вичерпаного пулу перезапуск не допомагає. Спершу — крок 3 (докази) | `dc restart api` | Кілька секунд простою. Якщо за 30 хв heap знову росте — ескалювати |

### Відкат (рядок 1)

**Після переходу на pipeline** — одна команда, без git і без токена у файлах: `.env.prev` уже
містить образ і секрети попереднього релізу.

```bash
cd /opt/poshtomat
cp .env.prev .env && cp compose.yaml.prev compose.yaml && docker compose up -d --wait
docker compose ps     # api — healthy, worker — running
```

- Працює, лише поки образ попереднього релізу є на VM. Compose його не тягне
  (`pull_policy: never`); якщо відповідає «image not found» — ескалюйте, не чистьте образи.
- Перевірка токена — блок 3 нижче.
- Наступний деплой з `main` знову покладе свіжий реліз, тож виправлення — звичайним PR.

**До переходу (ручний деплой з checkout)** — блоки нижче. Вставляйте їх по одному.

1. Знайдіть попередній розгорнутий коміт і спробуйте звичайний відкат:

   ```bash
   git reflog -5 --date=iso          # попередній розгорнутий коміт — той, що був до останнього pull
   h=<хеш з reflog>
   git checkout "$h" && dc up -d --build
   ```

2. **Лише якщо `checkout` відмовив** через локальні зміни (токен у `compose.yaml`) — замість
   цього:

   ```bash
   git stash push -m incident && git checkout "$h" &&
     t=$(git show 'stash@{0}:deploy/compose.yaml' | grep 'SMS_TOKEN:' | grep -v CHANGE_ME | head -1 | cut -s -d'"' -f2) &&
     sed -i "s#SMS_TOKEN: \"CHANGE_ME\"#SMS_TOKEN: \"$t\"#" deploy/compose.yaml && unset t && dc up -d --build
   ```

   Повертає в `compose.yaml` лише токен, не друкуючи його.
3. Після будь-якого варіанта:

   ```bash
   dc exec -T worker sh -c 'test -n "$SMS_TOKEN" && test "$SMS_TOKEN" != CHANGE_ME && echo "token ok" || echo "NO TOKEN"'
   ```

   `NO TOKEN` після відкату означає, що API працює, а SMS не підуть. Відкат не скасовуйте:
   - впишіть токен з менеджера паролів команди в `deploy/compose.override.yaml` для `worker`
     і `api`, далі `dc up -d worker api` і знову ця перевірка;
   - не можете — повідомте другому розробнику і в #poshtomat-oncall: «SMS про прибуття не
     надсилаються».

Зауваги:

- **`git stash pop` не робіть.** Після релізу, що переставив рядки `compose.yaml` (як
  v1.8.0), він дає конфлікт, а в половині зі stash разом з токеном лежить зламаний блок
  релізу. Якщо конфлікт уже трапився: `git checkout --ours deploy/compose.yaml && git reset -q`,
  далі рядки з `t=` і `sed` з блоку 2. Stash лишається в `git stash list` як копія токена.
- **Припущення:** у локальному `compose.yaml` значення токена — у подвійних лапках і без
  символів `#`, `&`, `\`. Інакше `t` буде порожнім, і перевірка в блоці 3 покаже `NO TOKEN`.
- **Повернення на `main`.** Після відкату VM у стані «detached HEAD», і звичайний
  `git pull` не спрацює. Коли виправлення злите в `main`, спершу подивіться, який там
  `compose.yaml`: `git fetch && git show origin/main:deploy/compose.yaml | grep -n SMS_TOKEN`.
  - `SMS_TOKEN: "CHANGE_ME"` — поверніться так само: `git stash push -m return`,
    `git checkout main && git pull`, рядки з `t=` і `sed` з блоку 2, `dc up -d --build`,
    перевірка з блоку 3.
  - `${SMS_TOKEN:?…}` — у `main` уже compose для pipeline: образ, токен і решту секретів він
    бере з `.env`, тож `sed` нічого не замінить, а `dc up` без `.env` відмовиться стартувати.
    Checkout не чіпайте: це вже перехід на pipeline (`pipeline/deploy.yml`, «Перехід»), і
    `.env` на VM пише він.

## Ролі

У команді двоє розробників, і чергує один із них (`materials/team.md`). «Другий розробник» —
той, хто зараз не чергує, незалежно від його спеціалізації.

- **Черговий веде інцидент.** Він вирішує про відкат і виконує кроки цього runbook.
- **Другий розробник, щойно підключився, відповідає за комунікацію.** Він пише оновлення в
  #poshtomat-oncall кожні 15 хв (що бачимо, що робимо, коли наступне оновлення). Якщо
  видача не працює > 15 хв, він повідомляє координаторку проєкту. Причину паралельно не
  шукає, доки сервіс не відновлено.
- Поки другий не підключився, черговий робить обидва, але оновлення може бути одним
  рядком.
- **Якщо черговий ескалює технічне питання** («Коли ескалювати», рядки 3–5 «Що робити»),
  другий розробник береться за нього, а оновлення в каналі тоді пише черговий, одним
  рядком. «Причину паралельно не шукає» стосується лише самостійного пошуку, поки черговий
  веде відкат.

## Коли ескалювати і кого кликати

- **Відкат або виправлення не повернули метрики в норму за 10 хв** → дзвінок другому
  розробнику.
- **Підозра на БД або VM** (`Lock` поза вікном бекапу, Postgres не відповідає, диск ≥ 95 %,
  load average > `nproc`) → другий розробник. Див. також `docs/ops/backup-runbook.md`.
- **Видача не працює > 15 хв** (це робить другий розробник — див. «Ролі») → повідомити координаторку проєкту в
  #poshtomat-oncall і на poshtomat-team@example.org: вона попередить гарячу лінію і
  мешканців.
- **SMS-провайдер** (support@sms.example.net, відповідає лише в робочий день) — тільки для
  проблем worker-а з доставкою SMS. На пейджі API він не впливає.

## Як переконатися, що все гаразд

1. **10 хв поспіль** на дашборді:
   - `p95_ms` < 500 (норма 140–260);
   - `error_rate` < 0,01;
   - `db_pool_waiting` = 0;
   - `db_pool_in_use` < 20.

   14.10 після відкату норма повернулася за хвилину (`docs/rca.md`, Д15).
2. Помилок пулу немає, версія очікувана:

   ```bash
   dc logs api --since 5m --no-log-prefix | grep -c "db pool wait timeout"     # → 0
   dc logs api --since 30m --no-log-prefix | grep '"msg":"service started"'    # → очікувана версія
   ```

3. Проба з кроку 5 «Перших 5 хвилин» — `403` за < 0,5 с, п'ять разів поспіль.
4. Пейджі закрилися самі.
5. Напишіть у #poshtomat-oncall, що зробили і коли, і де лежать докази (`~/incident-<час>`).
   Заведіть задачу на розбір.
6. **Чи віддавав `/pickup` 503** — за логом, збереженим на кроці 3:

   ```bash
   d=$(ls -td ~/incident-*/ | head -1); echo "$d"                     # тека з кроку 3 (у новій сесії $ts порожня)
   grep '"status":503' "${d}api.jsonl" | grep -c '"path":"/pickup"'   # > 0 — так
   grep '"status":503' "${d}api.jsonl" | head -1 | cut -c8-36         # нижня межа — перший 503
   dc logs api --since 3h --no-log-prefix | grep '"msg":"service started"' | tail -1 | cut -c8-36   # верхня межа — старт після відкату чи перезапуску
   ```

   Лог із кроку 3 зібрано **до** відкату, тож його останній 503 — не кінець інциденту. Якщо
   API не перезапускали (наприклад, скінчився бекап), верхня межа — останній 503 у живому
   лозі: `dc logs api --since 3h --no-log-prefix | grep '"status":503' | tail -1 | cut -c8-36`.

   Якщо `/pickup` віддавав 503 — заведіть задачу перевірити напів-видані посилки наступного
   робочого дня. Запуск: `sudo -u postgres psql -d poshtomat`. Межі підставте як є: `cut -c8-36`
   лишає зміщення `+03:00`, і PostgreSQL приймає `'2026-10-14T14:02:07.172+03:00'` без
   перетворень. Назви таблиць і полів — припущення, звірте з продакшн-схемою:

   ```sql
   select p.id, p.locker_id, p.picked_up_at
   from parcels p
   where p.status = 'picked_up'
     and p.picked_up_at between '<нижня межа>' and '<верхня межа>'
     and not exists (
       select 1 from events e where e.parcel_id = p.id and e.type = 'picked_up'
     );
   ```
