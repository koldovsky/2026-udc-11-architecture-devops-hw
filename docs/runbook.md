# Runbook: API повільний або відповідає 5xx

- **Алерт(и):** `ApiLatencyP95High` (`p95_ms > 2000` протягом 3 хв) і `Api5xxRateHigh` (`error_rate > 0.05` протягом 3 хв). Обидва — пейдж у `#poshtomat-oncall` і дзвінок черговому.
- **Що це означає для користувачів:** екран поштомата пише «Сервіс зайнятий, спробуйте пізніше», мешканці не можуть забрати посилку, а служба доставки — зареєструвати нову.
- **Скільки є часу:** запасу майже немає: у попередньому інциденті за 3 хвилини помилок стало 12 %. Мета — відновити сервіс за 15 хвилин, навіть якщо причина ще невідома.

> **Де що лежить на VM.** Деплой робить `pipeline/deploy.yml` (у репозиторії сервісу — `.github/workflows/deploy.yml`, workflow `deploy`). Він кладе в `/opt/poshtomat` два файли: `compose.yaml` і `.env` (режим 600: `POSHTOMAT_IMAGE` з digest образу, `DATABASE_URL`, `SMS_TOKEN`) — і переписує обидва на кожному деплої. Клону репозиторію на VM для роботи сервісу не потрібно.
>
> **Припущення:** дашборд моніторингу — `poshtomat-dashboard`. У документації цього не вказано: перевірте й виправте, якщо інакше. Команди для VM не перевірялись на справжньому сервері.

## Перші 5 хвилин

Усі команди виконуйте на VM у теці деплою:

```bash
ssh poshtomat-prod-1
cd /opt/poshtomat
```

1. **Напишіть у `#poshtomat-oncall`:** «Взяв(ла) пейдж, дивлюсь».
2. **Перевірте, чи не було нещодавно деплою.** Це найважливіше питання:

   ```bash
   date; stat -c '%y %n' .env compose.yaml
   grep '^POSHTOMAT_IMAGE=' .env
   docker inspect -f '{{.Config.Image}} запущено {{.State.StartedAt}}' "$(docker compose ps -q api)"
   ```

   Як читати:
   - **`.env` змінено менше ніж 30 хвилин тому, і образ `api` збігається з `POSHTOMAT_IMAGE`** → на VM розгорнуто новий реліз. Підтвердіть в історії GitHub Actions (workflow `deploy`: останній успішний запуск і його час) і **одразу відкочуйтесь** (див. «Відкат»). Розслідування потім.
   - **Контейнер запущено недавно, але `.env` старий** → це перезапуск, а не деплой (`restart: unless-stopped` після падіння, ребут VM, ручний `restart`). Відкат тут нічого не дасть: продовжуйте діагностику.
   - **`.env` свіжий, але образ `api` інший** → деплой не дійшов до кінця або його відкотили. Подивіться лог останнього запуску `deploy` і не відкочуйтесь наосліп.

   **Ризик:** час зміни `.env` змінює й ручне редагування файлу, тому без підтвердження в історії Actions не вважайте це деплоєм.
3. **Перевірте, чи справді зачеплена БД.** Запит із недійсним токеном безпечний, нічого не змінює, але бере з'єднання з пулу:

   ```bash
   curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -H 'Authorization: Bearer probe' http://localhost:8080/admin/parcels
   ```

   `403` швидше ніж за 1 с — пул працює. `503` або час понад 2 с — пул вичерпано.

**`/health` не допоможе:** він не звертається до БД і відповідає `200` навіть під час такого збою.

## Діагностика

**Команди з `docker compose logs … | grep -c` друкують `0` і тоді, коли логи прочитати не вдалося.** Тому лічильники нижче загорнуто в `if`: якщо замість числа бачите `ЛОГИ НЕ ПРОЧИТАНО` (і повідомлення docker над ним), це **не** «помилок немає». Перевірте `docker compose ps` і `df -h /var/lib/docker`, а до того орієнтуйтесь на перевірку з кроку 3 і на дашборд.

| Питання | Команда | Як читати результат |
|---|---|---|
| Які саме помилки? | `docker compose logs --since 15m --no-log-prefix api \| grep '"level":"error"' \| grep -o '"error":"[^"]*"' \| sort \| uniq -c \| sort -rn` | Багато `db pool wait timeout` → пул, крок «Як підтвердити причину». Поодинокі `reading 'trim'` → відомий фоновий дефект, близько 30 на годину, не причина. Порожній вивід перевірте наступним рядком: він відрізняє «помилок немає» від «логи не прочитано» |
| Яка версія працює? | `curl -s http://localhost:8080/health` | Поле `version`; порівняйте з попереднім випуском |
| Який пул передано API? | `docker compose exec -T api printenv \| grep '^DB_POOL'` | Очікується `DB_POOL_MAX=20` і `DB_POOL_WAIT_MS=2000`. Немає `DB_POOL_MAX` або є інша назва → пул непомітно став 4 |
| Скільки запитів до API за останню хвилину впали через пул? | `if logs=$(docker compose logs --since 1m --no-log-prefix api); then printf '%s\n' "$logs" \| grep -c 'db pool wait timeout'; else echo 'ЛОГИ НЕ ПРОЧИТАНО'; fi` | `0` — за хвилину жоден запит не впав через пул, але це **не** доводить, що пул справний: очікування, коротше за `DB_POOL_WAIT_MS` (2 с), таймауту не дає, а кілька таких очікувань в одному запиті (`/pickup` бере з'єднання 3 рази) все одно додають секунди затримки. Тому при `0` звірте час відповіді з кроку 3 і `db_pool_waiting` на дашборді: очікування більше за 0 чи час понад 1 с — пул усе ще під підозрою. Десятки чи сотні — проблема триває. `ЛОГИ НЕ ПРОЧИТАНО` — результату немає, див. абзац над таблицею |
| Скільки з'єднань із базою? | `sudo -u postgres psql -d poshtomat -c "select count(*) from pg_stat_activity where datname='poshtomat'"` | Для орієнтиру: API і worker мають по 20 з'єднань максимум, а API зазвичай тримає 10–13. Набагато менше на піку підозріло, близько 40 → перевірте, чи не вичерпано ліміт самої БД |
| Чи не вікно бекапу? | `date; sudo tail -n 5 /var/log/poshtomat/backup.log` | З 02:00 до 02:30 за Києвом записи в БД чекають або падають; після 02:30 мало б минути само |
| Чи є пейдж про SMS? | `if logs=$(docker compose logs --since 5m --no-log-prefix worker); then printf '%s\n' "$logs" \| grep -c 'rate limited'; else echo 'ЛОГИ НЕ ПРОЧИТАНО'; fi` | Десятки 429 за хвилину в години пік — **норма**. API не працює з SMS, тому це не пояснює 503 на екрані |

Метрики `db_pool_in_use`, `db_pool_waiting` і `p95_ms` дивіться в моніторингу: `poshtomat-dashboard` (припущення, див. вище). Звичайна картина в години пік: зайнято 10–13, очікувань 0, p95 близько 240 мс.

**Не вводьте себе в оману.** Усе це буває і в справний день: heap до 82 % і рядки `heap usage high`, поодинокі `TLS handshake timeout`, 429 від SMS-провайдера.

## Як підтвердити причину

Причина в пулі, якщо одночасно виконуються дві умови:

1. **`db_pool_in_use` рівно на одному значенні, а `db_pool_waiting` більше за 0**, хоча rps не вищий за звичайний.
2. **Практично всі 5xx мають текст `db pool wait timeout`** (перший рядок таблиці діагностики).

Щоб знайти причину зміни, порівняйте змінні, які читає код у запущеному образі, з тими, що передає compose:

```bash
docker compose exec -T api grep -n 'env\.' src/config.js
docker compose exec -T api printenv | grep '^DB_POOL'
docker compose exec -T worker printenv | grep '^DB_POOL'
```

Назва в `printenv` має збігатися з `env.<НАЗВА>` у `src/config.js`. Якщо ні, код непомітно бере типове значення. (`docker compose config` тут не підходить: він друкує й `DATABASE_URL` з паролем.)

### Відкат

Реліз — це **і образ, і `compose.yaml`** (14.10 зламалась саме конфігурація, образ не змінювався). Тому основний спосіб повертає обидва.

**Основний: повторно запустити деплой попереднього релізу.**

1. GitHub → Actions → workflow `deploy` → фільтр гілки `main` → останній **успішний** запуск *перед* поточним, у якому job **Deploy to production** справді виконався: він зелений (не сірий «skipped»), а в summary запуску є рядок ``Deployed `…@sha256:…` ``.
   **Ризик:** ручний запуск (`Run workflow`) з іншої гілки теж буває зеленим, але job деплою в ньому пропущено (`if: github.ref == 'refs/heads/main'`). Повторний запуск такого прогону нічого не розгорне і сервіс не відновить.
2. **Re-run all jobs** і підтвердити деплой в environment `production`.

Повторний запуск бере коміт того запуску: на VM повертаються його `compose.yaml` і образ, зібраний з того самого коду. Якщо новий реліз не стане здоровим, pipeline сам поверне попередні файли.
**Ризик:** це займає кілька хвилин (тести й збірка) і потребує підтвердження рецензента environment. Якщо за 5 хвилин він не відповів — ескалація. GitHub дозволяє повторний запуск лише протягом 30 днів після початкового: якщо кнопки **Re-run all jobs** немає, див. наступний пункт.

**Якщо попередньому запуску понад 30 днів (повторний запуск недоступний):** розгорнути попередній стан через новий коміт у `main`.

1. У репозиторії сервісу відкотіть коміт(и) поганого релізу: `git revert <sha поганого релізу>` (sha — у запуску `deploy`, що розгорнув поганий реліз), відкрийте pull request і змерджте його в `main` з рев'ю другого розробника.
2. Push у `main` зі змінами в `app/` чи `deploy/` сам запускає `deploy`. Якщо revert цих тек не зачепив — GitHub → Actions → `deploy` → **Run workflow** з гілки `main`. Далі, як в основному шляху, підтвердіть деплой в environment `production`.
3. Поки йде рев'ю і збірка: якщо причина в конфігурації (як 14.10, неправильна назва змінної), тимчасово виправте її на VM — рядок «Деплою не було, але в API немає правильної змінної пулу» у «Що робити».

**Ризики:** це найдовший шлях (рев'ю PR, тести, збірка, підтвердження environment) — одразу повідомте в `#poshtomat-oncall`, що відновлення займе більше 15 хвилин, і ескалюйте. Revert може дати конфлікт, якщо після поганого релізу були інші коміти: тоді відкочуйте лише зміни поганого релізу і не чіпайте решту без другого розробника. Образ збирається заново з того самого коду, тож його digest буде новим. Якщо реліз змінював схему БД, revert коду її не поверне — ескалація, як для відкату зі зміною схеми. Ручна правка на VM з кроку 3 зникне на наступному деплої, і це очікувано.

**Запасний, лише якщо Actions недоступні і реліз не змінював `deploy/compose.yaml`:** повернути тільки образ.

```bash
cd /opt/poshtomat
cp -p .env .env.bad                     # копія з секретами — видаліть після інциденту
docker image ls --digests --format '{{.Repository}}@{{.Digest}}  {{.CreatedSince}}' | grep poshtomat
# підставте digest попереднього релізу (його також видно в summary запуску deploy: "Deployed `…`")
sed -i 's|^POSHTOMAT_IMAGE=.*|POSHTOMAT_IMAGE=<попередній образ@sha256:…>|' .env
docker compose up -d && docker compose up -d --wait --wait-timeout 120 --no-recreate api
```

**Ризики запасного шляху:**
- він **не** повертає `compose.yaml`, тож проблему в конфігурації, як 14.10, не виправить;
- після деплою VM виходить із GHCR, а pipeline видаляє невикористані образи старші за 30 днів: якщо попереднього образу немає локально, лишається тільки основний шлях або шлях через revert;
- наступний деплой перезапише `.env`: зафіксуйте, що зроблено, у `#poshtomat-oncall` і видаліть `.env.bad` (`rm -f .env.bad`).

## Коли ескалювати і кого кликати

- **За 15 хв сервіс не відновлено, або потрібен відкат зі зміною схеми БД** → другий розробник у `#poshtomat-oncall`; він же на зв'язку поза чергуванням.
- **Є вплив на мешканців понад 15 хв** → координаторка проєкту: вона попереджає гарячу лінію.
- **Підозра на проблему SMS-провайдера** → `support@sms.example.net` і `status.sms.example.net`. Відповідають протягом робочого дня, тому не чекайте на них, перш ніж відкочуватись.
- **Номери телефонів чи коди могли потрапити не туди** → `dpo@example.org` протягом доби.
- **Загальна командна пошта** → `poshtomat-team@example.org`.

## Як переконатися, що все гаразд

Зачекайте 2–3 хвилини після дії, потім перевірте:

- **Пул працює:** команда з кроку 3 «Перших 5 хвилин» дає `403` швидше ніж за 1 с.
- **503 зникли:** `if logs=$(docker compose logs --since 2m --no-log-prefix api); then printf '%s\n' "$logs" | grep -c '"status":503'; else echo 'ЛОГИ НЕ ПРОЧИТАНО'; fi` дає `0`. `ЛОГИ НЕ ПРОЧИТАНО` — це не успіх: спершу з'ясуйте, чому docker не віддає логи.
- **Метрики:** p95 нижче 300 мс, `db_pool_waiting` дорівнює 0. Минулого разу p95 був 618 мс у першу хвилину, а 296 мс — у другу.
- **Пейджі:** `ApiLatencyP95High` і `Api5xxRateHigh` закрились, зазвичай протягом кількох хвилин.
- **Реальна видача:** гаряча лінія більше не отримує скарг із поштоматів.

Наприкінці напишіть у `#poshtomat-oncall`, що зроблено, і заведіть задачу на розбір.
