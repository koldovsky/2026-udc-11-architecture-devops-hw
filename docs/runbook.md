# Runbook: API повільний або віддає 5xx

- **Алерт(и):**
  - `ApiLatencyP95High` (page): `p95_ms > 2000` протягом 3 хв.
  - `Api5xxRateHigh` (page): `error_rate > 0.05` протягом 3 хв.
  - `SmsProvider429RateHigh` (warning): `sms_429_per_min > 20` протягом 5 хв. Сам по собі пейджу не
    потребує. Темп уже нижчий за ліміт провайдера, тож стійкі 429 тепер незвичні (див. «Діагностика»).
- **Що це означає для користувачів:** екран поштомата після введення коду пише «Сервіс зайнятий,
  спробуйте пізніше», і людина не може забрати посилку. Сканер служби доставки теж може не зареєструвати
  посилку, а персонал — не побачити список.
- **Скільки є часу:** вдень люди відчувають це одразу, тому **рішення про відкат — протягом 10 хвилин**.
  Посилки не зникають, а нові SMS працюють окремим процесом. Вночі звернень менше, але спершу перевірте
  вікно бекапу (крок 4).

> **Не робіть:** не вводьте випадковий 6-значний код у `POST /pickup` для перевірки: він може збігтися зі
> справжнім і видати чужу посилку. Не довіряйте `/health`: він не звертається до бази й відповідає 200
> навіть під час збою. З тієї самої причини `healthy` у `dc ps` нічого не гарантує, а автовідкат у
> деплої такий збій не спіймає: він дивиться лише на цю перевірку.

## Перші 5 хвилин

1. **Візьміть алерт** у #poshtomat-oncall: напишіть час і що взялися.
2. **Зайдіть на VM і вставте допоміжні команди** (їх використовують усі кроки нижче):

   ```bash
   ssh poshtomat-prod-1
   cd /opt/poshtomat

   # compose.yaml і .env лежать у цій теці, їх туди кладе деплой
   dc() { docker compose "$@"; }
   # Перевірка пулу без побічних ефектів: фіктивний токен шукається в базі через пул
   probe() { curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -H 'Authorization: Bearer probe' http://localhost:8080/admin/parcels; }
   # Причини помилок API за проміжок (типово 15 хв), найчастіші зверху
   api_errors() { dc logs --no-log-prefix --since "${1:-15m}" api | grep '"level":"error"' | grep -o '"error":"[^"]*"' | sort | uniq -c | sort -rn; }
   # Які повідомлення є в лозі і скільки разів: сервіс, проміжок (типово 15 хв)
   msgs() { dc logs --no-log-prefix --since "${2:-15m}" "$1" | grep -o '"msg":"[^"]*"' | sort | uniq -c | sort -rn; }
   # Помилки API по хвилинах, перші 20 хвилин (типово за 3 год), без давньої помилки trim
   err_min() { dc logs --no-log-prefix --since "${1:-3h}" api | grep '"level":"error"' | grep -v 'reading .trim.' | cut -c19-23 | uniq -c | head -20; }
   # Останні старти API: час і версія
   starts() { dc logs --no-log-prefix api | grep 'service started' | tail -n 3; }
   # Зберегти логи: після відкату контейнери створюються заново, і їхні логи зникають
   save_logs() { for s in api worker; do dc logs --no-log-prefix --since 3h "$s" > ~/incident-$s-$(date +%F-%H%M).jsonl; done; ls -lh ~/incident-*; }
   # Образи сервісу на VM, новіші зверху: для ручного відкату
   prev_images() { docker images --digests --filter label=org.opencontainers.image.title=poshtomat --format '{{.CreatedSince}}  {{.Repository}}@{{.Digest}}'; }
   ```

3. **Перевірте, чи є збій зараз:** `probe`.
   - `403` швидше за 0,5 с — пул вільний; збій минув або причина не в ньому.
   - `503` приблизно за 2 с — пул вичерпано, користувачі зараз отримують помилки.
4. **Перевірте час:** `TZ=Europe/Kyiv date +%H:%M`. Якщо це 02:00–02:30, база блокує запис через бекап
   (`docs/ops/backup-runbook.md:10-11`), і це очікувано: дивіться рядок «Вікно бекапу» в «Що робити».
5. **Перевірте, чи був нещодавно реліз:** `starts`. Якщо остання версія стартувала протягом останньої
   години, а `probe` дає `503`, **не шукайте причину далі**: виконайте `save_logs` і відкочуйте за розділом
   «Як відкотити». Причину знайдете потім.

## Діагностика

**Норма для порівняння** (звичайний день, у метриках моніторингу):

| Метрика | Вдень | У пік 13:30–15:00 |
|---|---|---|
| `p95_ms` | до 260 | до 260 |
| `error_rate` | до 0,007 | до 0,007 |
| `db_pool_in_use` | до 11 | 9–13 |
| `db_pool_waiting` | **завжди 0** | **завжди 0** |
| `heap_used_pct` | 54–82, «пилка» | 54–82, «пилка» |
| `sms_429_per_min` | близько 0 | очікувано близько 0 при темпі 5 SMS/с |

Значення взято за 13.10, усі крім останнього рядка. Тоді темп був 20 SMS/с за ліміту 10/с, і 429 у пік сягали 46 за
хвилину; нове значення ще не виміряне в продакшні.

| Питання | Команда | Як читати результат |
|---|---|---|
| Чому падають запити? | `api_errors` | `db pool wait timeout after 2000ms` → проблема з пулом, переходьте до «Як підтвердити причину». `Cannot read properties of undefined (reading 'trim')` у невеликій кількості → давня окрема помилка (близько 125 за 4 години), не причина. Інший текст → ескалація |
| Коли це почалося? | `err_min`, потім `starts` | Кожен рядок — кількість помилок і хвилина. Перша хвилина збігається зі стартом версії → причина в релізі або його конфігу. Помилки почалися раніше за старт → реліз ні до чого, шукайте далі. Нічого не вивело → інших помилок, крім `trim`, немає |
| Що ще відбувається в API? | `msgs api` | Багато `request failed` → дивіться `api_errors`. Кілька `shutting down` і `service started` → були перезапуски. `heap usage high` — норма, близько 65 за 4 години. `request` — лише кожен сотий запит, за цим числом трафік не оцінити |
| Який реальний розмір пулу? | `dc exec api node -e 'import("./src/config.js").then(m=>console.log(m.loadConfig().dbPoolMax))'` | Має бути те, що в `grep DB_POOL compose.yaml`. **`4` — змінна не дійшла до коду**, це значення для локальної розробки |
| Чи задано змінну в контейнері? | `dc exec api printenv DB_POOL_MAX` | Порожньо і код виходу 1 → назву змінної втрачено. Значення є → конфіг правильний, шукайте далі |
| Чи стоїть черга до пулу? | Метрики `db_pool_in_use` і `db_pool_waiting` | `waiting > 0` при `in_use` менше за розмір пулу з `compose.yaml` і рівно на одному значенні → занижена стеля. `in_use` дорівнює розміру пулу → запитів справді забагато або база повільна |
| Чи жива база? | `pg_isready -d poshtomat` | `accepting connections` → база приймає з'єднання. Інше → ескалація |
| Скільки з'єднань у базі? | `sudo -u postgres psql -d poshtomat -Atc "select count(*) from pg_stat_activity where datname='poshtomat'"` і `sudo -u postgres psql -Atc 'show max_connections'` | Перше близьке до другого → вичерпано ліміт бази, ескалація. Значно менше → база не є вузьким місцем |
| Чи не завис бекап? | `pgrep -fa backup.sh` і `sudo tail -n 5 /var/log/poshtomat/backup.log` | Процес живий після 02:30 → блокування запису може тривати, ескалація. Останній рядок `backup ok …` за сьогодні → бекап завершено |
| Чи винен SMS-провайдер? | `msgs worker` | **Сам 429 не спричиняє 5xx в API:** SMS шле лише worker. Багато `sms provider rate limited` → перевірте `grep SMS_RATE_PER_SEC compose.yaml`: має бути менше за 10, але це не терміново. Багато `sms send failed` або `sms delivery failed` (назва залежить від версії) → перевірте status.sms.example.net; це окрема проблема, а коди затримуються |
| Чи це пам'ять? | Метрика `heap_used_pct` | До 82 % і падає — норма, навіть із `heap usage high` у лозі. Стабільно понад 90 % або контейнер перезапускається → ескалація |
| Чи є ресурси на VM? | `df -h /; free -m; dc ps` | Диск заповнений, немає пам'яті, сервіс не `Up` або `unhealthy` → ескалація. `healthy` нічого не доводить: перевірка не звертається до бази |

**Порівняти метрики зі звичайним днем.** Якщо є CSV-експорт метрик за сьогодні і за схожий день (колонки як у
`incident/metrics/2026-10-14.csv`), запустіть на своїй машині в Git Bash:

```bash
# Середнє і максимум колонки у проміжку часу: файл, колонка, від, до
metric() { node -e '
const [file, col, from, to] = process.argv.slice(1);
const [head, ...rows] = require("fs").readFileSync(file, "utf8").trim().split("\n");
const i = head.split(",").indexOf(col);
const v = rows.map((r) => r.split(",")).filter((r) => r[0].slice(11, 16) >= from && r[0].slice(11, 16) < to).map((r) => +r[i]);
console.log(col, from + "-" + to, "avg", (v.reduce((a, b) => a + b, 0) / v.length).toFixed(1), "max", Math.max(...v));
' "$@"; }

metric incident/metrics/2026-10-14.csv db_pool_in_use 14:02 14:47
metric incident/baseline/metrics-2026-10-13.csv db_pool_in_use 14:02 14:47
```

Як читати, на прикладі 14.10 і 13.10: `db_pool_in_use` дає `avg 4.0 max 4` проти `avg 11.8 max 13`. Рівні середнє й
максимум означають стелю, бо реальне навантаження завжди коливається. Якщо колонка в обидва дні майже однакова,
як `heap_used_pct` (`max 82` в обох), то це норма, а не причина.

## Як підтвердити причину

Найчастіша причина такого набору алертів — **стеля пулу нижча за потребу**. Її відрізняють три факти:

1. `probe` дає `503` приблизно за 2 с, а `curl -s http://localhost:8080/health` при цьому дає 200.
2. `api_errors` показує майже лише `db pool wait timeout after 2000ms`.
3. Команда з розміром пулу дає значення, менше за задане в `compose.yaml`, а метрика `db_pool_in_use` стоїть
   рівно на цьому числі. Вдень API потрібно 10–13 з'єднань.

Якщо `db_pool_in_use` дорівнює повному розміру пулу, стеля ні до чого: запитів забагато або база відповідає
повільно. Тоді дивіться трафік (`rps`, норма в пік — близько 12) і з'єднання в базі.

Приклад із реального збою: `docs/rca.md`, інцидент 14.10.2026, де реліз перейменував змінну й пул упав із 20
до 4. Тоді підозрювали 429, heap і TLS-таймаут, але всі вони були нормою того дня.

| Ситуація | Дія | Команда | Ризик / що перевірити після |
|---|---|---|---|

| Реліз давно, але пул менший за заданий або змінної немає | Виправити змінну й перестворити контейнери | Виправте назву в `compose.yaml`, потім `dc up -d api worker` | Перезапуск без виправлення не допоможе. Наступний деплой перезапише файл на VM, тому правка має потрапити в `deploy/compose.yaml` у `main` |

| Лише 429 без 5xx і без скарг | Нічого не робити зараз, позначити на ранок | — | Не перезапускайте сервіс: API від цього не залежить. Вранці перевірте темп у `compose.yaml` |

## Як відкотити

Потрібно повернути і образ, і `compose.yaml`: збій 14.10 був саме в конфігу. Деплой видаляє попередні копії цих файлів
після успіху, тому на VM їх немає.

**Основний шлях.** GitHub → Actions → workflow `deploy` → останній успішний запуск **до** проблемного релізу → Re-run jobs
→ лише `deploy` → погодьте в environment `production`. Запуск бере `compose.yaml` зі свого коміту, а образ — за дайджестом
(`pipeline/deploy.yml:178`). Якщо новий стан не стане `healthy`, деплой не зможе відкотитися сам: попередньою для
нього буде проблемна версія.

**Запасний шлях, якщо GitHub недоступний або нема кому погодити:**

```bash
# На своїй машині, у клоні репо: повернути compose.yaml попереднього релізу
git show <коміт попереднього релізу>:deploy/compose.yaml | ssh poshtomat-prod-1 'cat > /opt/poshtomat/compose.yaml'

# На VM: знайти попередній образ (другий рядок prev_images) і запустити його
prev_images
sed -i "s|^POSHTOMAT_IMAGE=.*|POSHTOMAT_IMAGE='<репозиторій@sha256:…>'|" .env
dc up -d --wait --wait-timeout 120
```

Образи старші за 14 днів деплой видаляє (`pipeline/deploy.yml:212-214`). Наступний деплой перезапише обидва файли, тому
заведіть задачу на виправлення в `main`, інакше проблема повернеться.

## Коли ескалювати і кого кликати

- **Не відновилось за 30 хвилин, або потрібен відкат зі зміною схеми бази** → другий розробник (хто не на чергуванні),
  #poshtomat-oncall.
- **Не відповідає база, або бекап тримає блокування після 02:30** → розробник, відповідальний за інфраструктуру.
- **Вдень збій довший за 15 хвилин** → координаторка проєкту: вона попередить гарячу лінію (пн–пт, 9:00–18:00).
- **Схоже на проблему SMS-провайдера** → support@sms.example.net, статус — status.sms.example.net. Підтримка
  відповідає лише протягом робочого дня, тож не чекайте їхньої відповіді, якщо є реліз для відкату.
- **Персональні дані могли потрапити не туди** → dpo@example.org, протягом доби.
- **Проблема з посилками після збою** → розробник бекенду: `/pickup` змінює статус і пише подію окремими кроками, тому
  після 503 посилка могла стати `picked_up`, а повторний код дає 404. Такі скарги — на ранкову перевірку в базі.

## Як переконатися, що все гаразд

Чекайте 2–3 хвилини після дії.

- `probe` тричі поспіль дає `403` швидше за 0,5 с.
- `api_errors 3m` не показує `db pool wait timeout`.
- Метрики: `p95_ms` менше 300, `error_rate` менше 0,01, `db_pool_waiting` дорівнює 0, а `db_pool_in_use` вдень
  більше 4. Після відкату 14.10 перша хвилина ще мала p95 618 мс, друга — 296 мс.
- Пейджі закриваються приблизно за хвилину після відновлення.

Після цього напишіть у #poshtomat-oncall, що сталося й що зроблено, збережіть час дій і заведіть задачу на розбір.
Логи з `save_logs` не видаляйте до розбору.

## Що звірити на VM перед першим використанням

Ці деталі виведено з документів, а не перевірено на продакшні. Власник runbook має підтвердити їх заздалегідь, а не
під час нічного збою, і прибрати цей розділ:

- **Тека сервісу:** `/opt/poshtomat` взято з конфігу деплою (`pipeline/deploy.yml:121`), на самій VM не перевірено.
- **Доступ до `.env`:** файл має режим 600 і належить користувачу деплою, а без нього `docker compose` не запускається навіть
  для `logs`. Черговий має заходити під цим користувачем або мати право читати файл.
- **Відкат:** жоден із двох шляхів не пробувався. Чи може черговий сам погодити деплой уночі, залежить від Required
  reviewers; перевірте до першого збою.
- **Нічна задача:** cron запускає `docker compose run` (`docs/ops/backup-runbook.md:18-19`), тож має виконуватись у `/opt/poshtomat`.
- **Перший деплой через pipeline:** проєкт тепер називається `poshtomat` (`deploy/compose.yaml:10`), а раніше назва бралася з теки
  файлу. Перед першим деплоєм виконайте `docker compose ls`. Якщо старий стек працює під іншою назвою (наприклад, `deploy`), він
  тримає порт 8080, тож `api` нового стеку не стартує, а новий `worker` може лишитись працювати поруч зі старим і слати SMS паралельно.
  Автовідкату тут не буде: попередніх файлів у `/opt/poshtomat` ще немає (`pipeline/deploy.yml:203-207`). Тому зупиніть старий стек
  одразу перед погодженням деплою: `docker compose -p <стара назва> down`. Сервіс буде недоступний до старту нового стеку; база лежить поза compose і не постраждає.
- **Відновлення з бекапу:** `docs/ops/backup-runbook.md:32` зупиняє сервіс через `-f deploy/compose.yaml`, а деплой кладе файл у
  `/opt/poshtomat/compose.yaml`. На VM виконуйте цей крок як `cd /opt/poshtomat && docker compose stop api worker` і так само запускайте сервіс
  після відновлення. Власник документа має оновити його після першого деплою.
- **Адреса моніторингу і телефон другого розробника:** у матеріалах їх немає, допишіть.
- **Команди `dc`, `pg_isready`, `psql`:** на продакшні не запускались, бо доступу до нього немає.
