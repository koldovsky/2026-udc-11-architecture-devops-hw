# Runbook: API віддає 5xx або відповідає повільно

_Клас алертів: деградація API. Складено після інциденту 2026-10-14
([`docs/rca.md`](rca.md), [`docs/postmortem.md`](postmortem.md))._

- **Алерт(и):**
  - `ApiLatencyP95High` — `p95_ms > 2000` протягом 3 хв (page + дзвінок черговому)
  - `Api5xxRateHigh` — `error_rate > 0.05` протягом 3 хв (page + дзвінок черговому)
  - `DbPoolSaturated` — `db_pool_waiting > 0` протягом 2 хв (page). Спрацьовує раніше за
    обидві попередні і одразу вказує на пул — якщо прийшов він, починайте з кроку 3.
- **Що це означає для користувачів:** люди не можуть забрати посилку — поштомат після
  введення коду показує «Сервіс зайнятий, спробуйте пізніше» (це HTTP 503 від API) або
  довго думає. Паралельно не приймаються нові посилки і не працює кабінет персоналу.
- **Скільки є часу:** вплив серйозний **з першої хвилини** — кожна хвиліна це люди, що
  стоять біля поштомата. Орієнтир: прибрати вплив за 15 хвилин, не чекаючи на розуміння
  причини. Відкат — нормальна перша дія, не остання.

> **Головне правило цього класу алертів.** Спочатку перевірте, чи був деплой — і лише
> потім шукайте причину всередині. На інциденті 2026-10-14 команда 40 хвилин розбиралася
> із зовнішнім SMS-провайдером, бо його алерт відкрився на 29 хвилин раніше. Алерт, що
> вже горить, — не причина того, що зламалося щойно.

## Перші 5 хвилин

1. **Перевірте симптом очима користувача** — з будь-якої машини:

   ```bash
   curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' \
     --connect-timeout 5 --max-time 10 \
     -X POST https://poshtomat.example.org/pickup \
     -H 'content-type: application/json' -d '{"code":"000000"}' ||
     echo "БЕЗ ВІДПОВІДІ (curl exit $?)"
   ```

   Три різні результати, і їх не треба плутати:

   - `404` або `200` швидко — API живий, симптом уже зник;
   - **будь-який код 5xx (500–599) — інцидент підтверджено**, ідіть далі. 503 — найчастіший
     вигляд цього класу, але 500 чи 502 підтверджують його так само;
   - `БЕЗ ВІДПОВІДІ` (код у рядку `-w` при цьому `000`) — відповіді немає за відведені
     10 секунд: `28` — таймаут, `7` — з'єднання відмовлено, `6` — DNS. Без обмежень часу
     curl чекав би хвилини й перевірка зависла б; тут вона завершується керовано, і це
     теж підтверджений інцидент — **одразу** переходьте до «Коли ескалювати», а
     діагностику ведіть паралельно.

2. **Чи був деплой або ручна дія за останню годину?**

   ```bash
   ssh poshtomat-prod-1 'tail -n 5 /opt/poshtomat/deploys.log'
   ```

   Є рядок за останні 60 хв — **це головний підозрюваний**, незалежно від того, наскільки
   невинно виглядає note («config cleanup», «bump version», «docs»). Переходьте до кроку 3,
   а потім до «Що робити», рядок 1. Немає — переходьте до кроку 3 і далі діагностуйте.

3. **Подивіться на пул з'єднань — це найчастіша причина цього класу:**

   ```bash
   ssh poshtomat-prod-1 'curl -s localhost:8080/metrics | grep -E "db_pool_(in_use|waiting)"'
   ```

   `db_pool_waiting > 0` — запити стоять у черзі за з'єднанням. Запам'ятайте значення
   `db_pool_in_use`: саме воно відрізнить причини в наступному розділі.

4. **Напишіть у `#poshtomat-oncall`, що взяли інцидент**, і вкажіть три числа: код з кроку 1,
   рядок з кроку 2, `in_use`/`waiting` з кроку 3. Це стартова точка для всіх, хто
   підключиться.

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Який саме текст помилки віддає API? | `ssh poshtomat-prod-1 'docker compose -f /opt/poshtomat/compose.yaml logs --since 10m api \| grep "\"level\":\"error\"" \| grep -o "\"error\":\"[^\"]*\"" \| sort \| uniq -c \| sort -rn'` | Один домінуючий текст — шукайте його в таблиці «Що робити». `db pool wait timeout after …ms` → пул (рядки 1–3). Помилки з'єднання до БД → рядок 4. Різні тексти вроздріб — причина не одна, ескалюйте |
| Пул просто насичений — чи його **стеля впала**? | `ssh poshtomat-prod-1 'curl -s localhost:8080/metrics \| grep -E "db_pool_(in_use\|max)"'` | `in_use` = `max` і `max` звичний (20) — справжнє перевантаження, рядок 3. `in_use` = `max` і `max` **менший за звичний** (4, 5, 10) — конфігурацію зламано, рядок 1. Це ключова розвилка цього runbook-а |
| Чи змінилася конфігурація процесу проти попереднього релізу? | `ssh poshtomat-prod-1 'set -eo pipefail; f=$(mktemp); trap "rm -f $f" EXIT; docker compose -f /opt/poshtomat/compose.yaml exec -T api env \| grep -E "^(DB_\|SMS_\|DATABASE_URL)" \| sed "s/=.*/=<set>/" \| sort > "$f" && diff "$f" /opt/poshtomat/env-last-known-good.names.txt'` | Порівнюємо **назви**, а не значення: `sed` замінює кожне значення на `<set>`, тому ні `DATABASE_URL` з паролем, ні `SMS_TOKEN` не потрапляють у файл на проді й не поїдуть в артефакти розслідування. Файл-еталон тримається в тому самому вигляді (той самий конвеєр після успішного релізу). Будь-який рядок у `diff` — причина знайдена; `<` без пари = змінну **перейменували або додали**, `>` без пари = **зникла**. Це важливіше за змінене значення: код не бачить нової назви і беззвучно бере дефолт. Якщо потрібне саме значення пулу — наступний розділ, пункт 2, без доступу до прода. Тимчасовий файл знімається до `diff` і лише за успішного `exec` (`&&`): якщо `exec` впав, `trap` прибирає файл, команда повертає його код виходу, а `diff` не запускається і еталон не порівнюється з порожнім файлом |
| Чи трафік справді виріс? | Поточне значення: `ssh poshtomat-prod-1 'date -Is; curl -s localhost:8080/metrics \| grep -E "^(rps\|p95_ms\|error_rate)"' \| tee -a ~/incident-metrics.txt` — `tee` обов'язковий: `/metrics` віддає **лише поточні** числа, історії в ньому немає, і за годину це значення вже нічим не відтворити. За попередній робочий день: **спершу з'ясуйте, яке джерело історії тут узагалі є** — чи піднято систему моніторингу, що збирає `/metrics` (анотації деплоїв і графіки — ще не зроблений action item #7 постмортему), чи лишилися тільки знімки, збережені вручну за рядком 5 «Що робити» (`ssh poshtomat-prod-1 'ls -d /tmp/incident-*'`). Якщо джерела немає — так і зафіксуйте в каналі, не припускаючи неіснуючого endpoint-а | `rps` на звичному рівні, а p95 виріс — причина **всередині** сервісу (конфігурація, реліз, БД), а не в навантаженні. `rps` у 1,5–2 рази вище звичного — рядок 3. **Якщо порівняти не з чим** — цей рядок діагностики не дає відповіді: не вважайте це доказом ні перевантаження, ні його відсутності, а йдіть за рядком 2 (стеля пулу), де висновок не потребує історії |
| Чи жива БД і чи не вона повільна? | `ssh poshtomat-prod-1 'time psql -h 192.0.2.10 -U poshtomat -c "select 1" && psql -h 192.0.2.10 -U poshtomat -c "select count(*) from pg_stat_activity"'` | Відповідь за <50 мс і число з'єднань помітно менше `max_connections` — **БД не до діла**, не витрачайте на неї час. Повільно або помилка — рядок 4 |
| Чи не йде зараз нічний бекап? (блокує запис 02:00–02:30) | `ssh poshtomat-prod-1 'tail -n 3 /var/log/poshtomat/backup.log'` | Інцидент у вікні 02:00–02:30 і бекап ще йде — див. [`docs/ops/backup-runbook.md`](ops/backup-runbook.md); це очікувана поведінка, не цей клас алертів |
| Чи це взагалі API, а не worker? | `ssh poshtomat-prod-1 'docker compose -f /opt/poshtomat/compose.yaml ps'` | Обидва `Up` — проблема в поведінці, не в падінні. `worker` у `Restarting` — окремий інцидент: SMS не йдуть, але видача посилок має працювати |

**Чого НЕ робити на цьому кроці:**

- **Не покладайтеся на `/health`.** `GET /health` не торкається БД і віддає 200 навіть
  тоді, коли сервіс не обслуговує жодного запиту. На інциденті 2026-10-14 це зняло
  підозру о 14:29, коли все було зламано. «Сервіс працює» підтверджує **лише крок 1**
  цього runbook-а. Окремого ендпоїнта «процес живий» у сервісі **немає**: `createHandler`
  обробляє один шлях здоров'я — `GET /health` (`app/src/server.js:37`), тому `/health/live`
  віддасть `404` і скаже тільки те, що процес приймає з'єднання. Розділити ці дві
  перевірки — action item #6 постмортему, його ще не зроблено.
- **Не вважайте алерт, що вже горів до паги, причиною паги.** Перевірте його час
  спрацювання: якщо він відкрився задовго до деградації і його метрика не змінилася на
  межі деградації — він непов'язаний. Класичний приклад — `SmsProvider429RateHigh`.
- **Не перезапускайте сервіс замість діагностики.** Рестарт тієї ж версії з тією ж
  конфігурацією не допоможе, якщо причина — конфігурація; але він **зіпсує докази**
  (лічильники, стан пулу). Якщо вже перезапустили і не допомогло, то доведено рівно одне:
  **рестарт сервіс не відновив**. Це знімає з підозри лише те, що рестарт скидає —
  накопичений стан процесу (витік з'єднань, зіпсований кеш). Коло підозрюваних
  залишається ширшим за реліз і конфігурацію: навантаження (рядок 4 діагностики),
  сама БД і вікно бекапу (рядки 5–6), незавершений старт — перевірте, що процес
  узагалі дійшов до `service started`, а не падає й піднімається по колу
  (`docker compose ps` у рядку 7, стовпець `STATUS`, і логи старту). Реліз і конфігурація
  лишаються **першими** в черзі перевірки — але не єдиними.

## Як підтвердити причину

Два факти відрізняють «зламану конфігурацію пулу» (найчастіший випадок цього класу) від
усіх інших причин:

1. **Стеля пулу нижча за звичну.** `db_pool_in_use` стоїть на числі, меншому за робочі
   12–14, і **не рухається**, тоді як `db_pool_waiting` > 0. Перевантаження виглядає
   навпаки: `in_use` упирається в звичний `max` (20). Команда — у таблиці діагностики,
   рядок 2.

2. **Різниця в оточенні проти останнього справного релізу.** `diff` з таблиці діагностики,
   рядок 3, показує зниклу або перейменовану змінну `DB_*`. Остаточне підтвердження —
   прогнати той самий `loadConfig`, що й сервіс, двічі: з оточенням старого релізу і з
   оточенням нового. Робиться локально, без доступу до прода; `$REPO` — абсолютний шлях,
   тому команди не залежать від поточного каталогу:

   ```bash
   REPO=/шлях/до/робочої-копії-репозиторію

   # $@ — змінні пулу так, як їх задає compose.yaml відповідного релізу.
   # env -u гарантує, що жодна з двох назв не просочиться з вашої оболонки.
   poolmax() {
     env -u DB_POOL_MAX -u DB_POOL_SIZE "$@" node -e 'const {pathToFileURL} = require("node:url");
       import(pathToFileURL(process.argv[1]).href)
         .then(({loadConfig}) => console.log("dbPoolMax =", loadConfig(process.env).dbPoolMax));' \
       "$REPO/app/src/config.js"
   }

   poolmax DB_POOL_MAX=20    # оточення старого релізу
   poolmax DB_POOL_SIZE=20   # оточення нового релізу — назви беріть із diff, рядок 3
   ```

   Назви й значення для кожного виклику беріть із `diff` (рядок 3 діагностики) або з
   `compose.yaml` обох релізів. Різні числа — причина доведена. На 14.10 ці два виклики
   давали `dbPoolMax = 20` і `dbPoolMax = 4`.

Якщо жоден із двох фактів не підтверджується, це **не** конфігурація пулу: повертайтеся до
таблиці діагностики і йдіть за домінуючим текстом помилки.

## Що робити

| Ситуація | Дія | Команда | Ризик / що перевірити після |
|---|---|---|---|
| 1. Був деплой за останню годину, і/або стеля пулу впала | **Відкат на попередню версію.** Не чекайте на повне розуміння причини — відкат прибирає вплив і зберігає можливість розбиратися потім | `ssh poshtomat-prod-1 '/opt/poshtomat/rollback.sh <попередня-версія>'` | Відкат повертає і код, і `compose.yaml` разом. Ризик: якщо між релізами була міграція БД — спершу уточніть у автора релізу. Після: крок 1 з «Перших 5 хвилин» має дати код поза діапазоном 5xx, `db_pool_waiting` → 0 протягом 1 хв. Зафіксуйте в `deploys.log` і напишіть у канал |
| 2. Деплою не було, але в `diff` оточення видно зниклу/перейменовану змінну | Повернути правильну назву змінної в `compose.yaml` і підняти сервіс | `ssh poshtomat-prod-1 'cd /opt/poshtomat && docker compose up -d api worker'` | Виправляйте **назву в compose**, а не дефолт у коді. Після: `docker compose exec api env \| grep DB_POOL` показує очікувану змінну; `db_pool_in_use` повертається до 12–14 під навантаженням |
| 3. Справжнє перевантаження: `rps` значно вище звичного, `in_use` = звичний `max` | Тимчасово підняти пул і, якщо треба, обмежити найважчий трафік. Паралельно кликати власника сервісу — це питання ємності, не інциденту конфігурації | `ssh poshtomat-prod-1 'cd /opt/poshtomat && DB_POOL_MAX=30 docker compose up -d api'` | Пул понад `max_connections` БД зробить гірше: спершу запитайте стелю **у тієї самої БД, з якою працює API** (хост, користувач і база — ті, що в його `DATABASE_URL`): `ssh poshtomat-prod-1 'psql -h 192.0.2.10 -U poshtomat -d poshtomat -c "show max_connections"'` — і порахуйте з іншими споживачами (worker, нічна задача, бекап, ваші власні `psql`). Після: `db_pool_waiting` → 0, p95 < 500 мс. Обов'язково створіть тікет на ємність — це не фікс, а відтяжка |
| 4. БД недоступна або повільна | Це інший клас інциденту: API лише віддає наслідок | `ssh poshtomat-prod-1 'sudo systemctl status postgresql && sudo tail -n 50 /var/log/postgresql/postgresql-main.log'` | Не рестартуйте БД без власника. Перевірте вікно бекапу ([`docs/ops/backup-runbook.md`](ops/backup-runbook.md)) і місце на диску `df -h`. Ескалюйте за таблицею нижче |
| 5. Симптом зник сам, причина невідома | **Не закривайте інцидент.** Зафіксуйте вікно і зніміть дані, поки вони є | `ssh poshtomat-prod-1 'set -eo pipefail; d=/tmp/incident-$(date +%Y%m%dT%H%M); mkdir -p "$d"; cd /opt/poshtomat; docker compose logs --since 2h api > "$d/api.jsonl"; docker compose exec -T api env \| grep -E "^(DB_\|SMS_\|DATABASE_URL)" \| sed "s/=.*/=<set>/" \| sort > "$d/env-names.txt"; { date -Is; curl -s localhost:8080/metrics; } > "$d/metrics.txt"; echo "$d"'` | Оточення зберігаємо **назвами із затертими значеннями** (`=<set>`), як у рядку 3 діагностики: артефакти розслідування переживають інцидент і їх пересилають — пароля БД і `SMS_TOKEN` у них бути не повинно. Для RCA потрібні саме назви. Логи ротуються — без цього кроку RCA написати буде нічим. Збережіть також метрики за ±1 година і дані за попередній робочий день: порівняння з контрольним днем — найсильніший інструмент у RCA |

## Коли ескалювати і кого кликати

- **Вплив триває понад 15 хвилин, а причини немає** → автор останнього релізу (`deploys.log`,
  колонка `by`) + власник сервісу в `#poshtomat-oncall`. Не чекайте: відкат (рядок 1) можна
  робити паралельно.
- **Відкат не допоміг** → власник сервісу, негайно. Це означає, що причина не в релізі, і
  коло підозрюваних ширше за цей runbook.
- **БД недоступна, повільна або близька до `max_connections`** → адміністратор БД (Андрій,
  власник [`docs/ops/backup-runbook.md`](ops/backup-runbook.md)).
- **`rps` понад подвійний звичний рівень без пояснення** → власник сервісу + безпека
  (можливе зловживання, а не органічне зростання).
- **Підозра на проблему в зовнішній залежності** → спершу перевірте її статус-сторінку і
  напишіть у їхню підтримку, але **не ставте інцидент на паузу в очікуванні відповіді**:
  на 2026-10-14 відповідь провайдера прийшла через 19 хвилин і була «у нас усе гаразд».
- **Вплив понад 30 хвилин** → повідомте гарячу лінію, щоб операторам було що казати людям
  біля поштоматів.

## Як переконатися, що все гаразд

Перевіряйте **усі чотири** пункти — перші два можуть виглядати добре при ще зламаному
сервісі:

1. **Симптом очима користувача** — крок 1 з «Перших 5 хвилин» не віддає **жодного 5xx
   (500–599)** і не завершується без відповіді. Та сама межа, що й при підтвердженні
   інциденту: 503 зник, а 500 лишився — це не відновлення. Повторіть перевірку кілька
   разів: один 200 серед 5xx нічого не підтверджує. Це головний критерій.
2. **Метрики повернулися до норми** і тримаються **не менше 10 хвилин**:

   ```bash
   ssh poshtomat-prod-1 'curl -s localhost:8080/metrics | grep -E "^(p95_ms|error_rate|rps)|db_pool_(in_use|waiting)"'
   ```

   Орієнтири робочого дня: `p95_ms` < 300, `error_rate` < 0,01, `db_pool_waiting` = 0,
   `db_pool_in_use` 10–14 при `rps` ~12.
3. **Нових помилок у логах немає за останні 10 хвилин:**

   ```bash
   ssh poshtomat-prod-1 'docker compose -f /opt/poshtomat/compose.yaml logs --since 10m api | grep -c "db pool wait timeout"'
   ```

   Очікуване — `0`. Ненульове при нормальному p95 означає, що проблема лише пригасла.
4. **Паги закрилися самі.** Якщо метрики в нормі, а алерт не закрився за 5 хвилин —
   проблема в алерті, і це теж треба зафіксувати.

**Після відновлення, доки дані ще є:** збережіть логи, оточення і метрики за вікно
інциденту (команда з рядка 5 «Що робити») і за той самий проміжок попереднього робочого
дня. Далі — RCA за шаблоном [`docs/templates/rca.md`](templates/rca.md); приклад
розбору цього класу — [`docs/rca.md`](rca.md).
