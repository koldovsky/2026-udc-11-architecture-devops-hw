# Runbook: API повільний / 5xx — `ApiLatencyP95High`, `Api5xxRateHigh`

- **Алерт(и):** `ApiLatencyP95High` — `p95_ms > 2000` протягом 3 хв; `Api5xxRateHigh` —
  `error_rate > 0.05` протягом 3 хв (`incident/alerts.json`). Обидва — `page`.
  Часто разом з ними горить `SmsProvider429RateHigh` (`warning`) — це **інший клас**
  проблеми, див. «Як підтвердити причину».
- **Що це означає для користувачів:** екран поштомата після введення коду показує
  «Сервіс зайнятий, спробуйте пізніше» (це відповідь `503 service busy, try again`,
  `app/src/server.js:65`), сканер служби доставки не може зареєструвати посилку
  (`POST /parcels`), адмінка не відкривається. Люди стоять біля поштомата і не можуть
  забрати посилку.
- **Скільки є часу:** вплив уже є. Мета — відновити за 15 хв. Після обіду, коли
  розвантажуються машини служби доставки (`materials/feature-brief.md:44-45`), кожна хвилина —
  десятки невдалих видач.

## Перші 5 хвилин

1. Напишіть у `#poshtomat-oncall`: «Взяв(ла) ApiLatencyP95High/Api5xxRateHigh, дивлюся».
2. **Чи був деплой за останню годину?** Це питання №1: 14.10 причиною був реліз за 4 хв до алерту.
   ```bash
   ssh poshtomat-prod-1
   tail -n 5 /opt/poshtomat/deploys.log          # той самий формат, що incident/deploys.log
   docker compose -f deploy/compose.yaml ps       # версія образу і час старту контейнерів
   ```
   Деплой був за ≤ 60 хв до алерту → одразу переходьте до «Як підтвердити причину», рядок
   «пул БД». Не чекайте відповіді від постачальників.
3. **`/health` = 200 нічого не доводить.** Він не ходить у БД (`app/src/server.js:37`) і відповідав
   200 увесь інцидент 14.10. Перевіряйте справжній запит:
   ```bash
   curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -X POST http://localhost:8080/pickup \
     -H 'content-type: application/json' -d '{"code":"000000"}'
   ```
   `404` швидко (< 0,5 с) — шлях до БД живий (коду 000000 просто немає). `503` або ~2 с — пул
   БД вичерпано.

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Які помилки віддає API? | `docker compose -f deploy/compose.yaml logs --since 15m api \| grep -o '"error":"[^"]*"' \| sort \| uniq -c \| sort -rn` | `db pool wait timeout after 2000ms` — пул БД (найчастіша причина 503). `Cannot read properties of undefined (reading 'trim')` — це хронічні 500 на `POST /parcels` без `sender`, вони є і в звичайні дні (≈ 1 на 2 хв), алерт ними не пояснюється. |
| Скільки з'єднань пулу реально доступно? | `docker compose -f deploy/compose.yaml exec api node -e 'import("./src/config.js").then(m=>console.log(m.loadConfig()))'` | `dbPoolMax: 4` — працює дефолт для локальної розробки (`app/src/config.js:9`), змінну не прочитано. У продакшні має бути `20`. |
| Які змінні реально отримав контейнер? | `docker compose -f deploy/compose.yaml exec api env \| grep -E '^(DB_|SMS_|PORT\|DATABASE_URL)' \| sed 's/=.*TOKEN.*/=***/'` | Порівняйте імена з `app/src/config.js:6-15`. Ім'я, якого там немає (наприклад, `DB_POOL_SIZE`), застосунок ігнорує мовчки. |
| Пул зайнятий «під стелю»? | Метрики `db_pool_in_use` і `db_pool_waiting` за останні 15 хв у моніторингу | `db_pool_in_use` стоїть рівно на одному числі (4) і `db_pool_waiting` > 0 — стеля пулу. Для порівняння, звичайний день після обіду: `in_use` 11–13, `waiting` 0. |
| Може, просто більше трафіку? | `rps` у моніторингу за ту саму годину сьогодні і тиждень/день тому | Сьогодні ≈ так само (14.10 і 13.10 о 14:03–14:47 — однаково 11,8 rps) → навантаження ні до чого. |
| Може, БД блокує записи? | `date +%H:%M`; `sudo tail -n 3 /var/log/poshtomat/backup.log` | 02:00–02:30 бекап тримає блокування на запис (`docs/ops/backup-runbook.md:10-11`) — тоді 503 на записах очікувані, на `POST /pickup` — теж (видача пише статус). В інший час це не воно. |

## Як підтвердити причину

Відрізнити «пул БД» від усього іншого можна двома фактами:

1. помилки API — майже всі `db pool wait timeout` (а не таймаути до SMS чи 500);
2. `db_pool_in_use` дорівнює рівно `dbPoolMax`, який реально бачить процес (команда вище), і він
   менший, ніж задумано в `deploy/compose.yaml`.

Що **не** є причиною 503 на `/pickup`, хоч і горить поруч:

- `SmsProvider429RateHigh` і `sms provider rate limited` у логах worker-а — worker окремий процес зі
  своїм пулом (`app/src/worker.js:43`), до запитів API він не причетний; 429 бувають щодня після
  обіду (див. `docs/rca.md`). Розбирайте окремо, у робочий час.
- `heap usage high` (75–82 %) — норма для цього процесу щодня.
- поодинокий `TLS handshake timeout to sms.example.net` — теж буває щодня.

## Коли ескалювати і кого кликати

- Відкат не допоміг за 10 хв, або деплою не було і за 15 хв причини немає → другий розробник
  (той, хто не на чергуванні) у `#poshtomat-oncall` і телефоном.
- Підозра на БД (PostgreSQL на VM не відповідає, `pg_isready` не `accepting connections`) →
  власник бекапів (`docs/ops/backup-runbook.md:3`).
- Інцидент зачепив персональні дані (номери телефонів потрапили не туди) → відповідальна за захист
  даних протягом доби (`materials/compliance.md:25-26`).
- Люди не можуть забрати посилки > 30 хв → повідомити координаторку проєкту, щоб гаряча лінія
  відповідала мешканцям.

## Як переконатися, що все гаразд

- `p95_ms` < 500 і `error_rate` < 0,01 три хвилини поспіль; обидва пейджі закрилися.
- `db_pool_waiting` = 0, `db_pool_in_use` знову змінюється (не стоїть на одній цифрі).
- Справжній запит з «Перших 5 хвилин» повертає `404` швидше ніж за 0,5 с.
- У логах API за останні 5 хв немає `db pool wait timeout`:
  `docker compose -f deploy/compose.yaml logs --since 5m api | grep -c 'db pool wait timeout'` → `0`.
- Напишіть у `#poshtomat-oncall`, що відновлено, і заведіть задачу на розбір.
