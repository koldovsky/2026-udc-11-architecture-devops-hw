# Runbook: `ApiLatencyP95High` / `Api5xxRateHigh` (API повільний або віддає 5xx)

- **Алерт(и):** `ApiLatencyP95High` — p95_ms > 2000 протягом 3 хв (page);
  `Api5xxRateHigh` — error_rate > 0.05 протягом 3 хв (page). Часто приходять парою.
- **Що це означає для користувачів:** екран поштомата показує «Сервіс зайнятий,
  спробуйте пізніше» — мешканці не можуть забрати посилки; сканери служби доставки не
  можуть реєструвати нові.
- **Скільки є часу:** вплив уже йде (page = користувачі вже страждають). Після ~15 хв
  почнуться дзвінки на гарячу лінію і заповнені комірки. Мета — відновити ≤ 30 хв.

Усі команди — на VM `poshtomat-prod-1` (`ssh poshtomat-prod-1`), якщо не сказано інше.
**Не вір `GET /health`:** він навмисне не торкається БД (`app/src/server.js:37`) і
відповідає 200 навіть коли все лежить.

## Перші 5 хвилин

1. Що саме відповідає API — здоровий запит проходить?
   ```bash
   curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' -X POST localhost:8080/pickup \
     -H 'content-type: application/json' -d '{"code":"000000"}'
   ```
   `404` за < 0,5 с — API і БД живі (404 — очікувано для неіснуючого коду), дивись у бік
   трафіку/метрик. `503` або > 2 с — проблема в API/БД, йди далі.
2. Чи був деплой або ручна дія перед початком?
   ```bash
   tail -n 5 /opt/poshtomat/deploys.log; docker compose -f /opt/poshtomat/compose.yaml ps
   ```
   Деплой за < 1 год до алерту — головний підозрюваний; тримай напоготові відкат.
3. Які помилки сиплються просто зараз?
   ```bash
   docker compose -f /opt/poshtomat/compose.yaml logs api --since 10m \
     | grep '"level":"error"' | grep -o '"error":"[^"]*"' | sort | uniq -c | sort -rn
   ```

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Це пул БД? | команда з кроку 3 | переважає `db pool wait timeout after …ms` → так, пул: далі «Як підтвердити причину». Інші помилки → дивись їх текст |
| Пул упирається в стелю? | у метриках за останні 10 хв: `db_pool_in_use` і `db_pool_waiting` | `in_use` — константа (4, 20…), а `waiting > 0` → пул насичений. `waiting = 0` → пул ні до чого |
| Стеля — та, що має бути? | `docker inspect poshtomat-api-1 --format '{{range .Config.Env}}{{println .}}{{end}}' \| grep -E 'DB_POOL'` | має бути `DB_POOL_MAX=20`. Немає рядка `DB_POOL_MAX` (або інша назва на кшталт `DB_POOL_SIZE`) → конфіг зламано: застосунок читає лише `DB_POOL_MAX` (`app/src/config.js:9`), без нього пул = 4 |
| Трафік аномальний? | `rps` у метриках проти того ж часу вчора | rps ×2–3 від учорашнього → можливо, справді навантаження. rps звичайний → причина всередині |
| БД сама жива/повільна? | `sudo -u postgres psql poshtomat -c 'select 1;'` і `...-c 'select count(*) from pg_stat_activity;'` | `select 1` висить → проблема в PostgreSQL на VM (диск? бекап-вікно 02:00–02:30?), а не в пулі застосунку |
| Це не 429 SMS-провайдера? | `docker compose -f /opt/poshtomat/compose.yaml logs worker --since 10m \| grep -c 'rate limited'` | 429 стосуються лише worker-а (SMS із затримкою). API їх не викликає (`grep -ci sms app/src/server.js` → 0) — 5xx на /pickup вони не пояснюють. Не відволікайся |

## Як підтвердити причину

«Пул замалий через конфіг» відрізняють від «БД повільна» дві ознаки разом:

1. `db_pool_in_use` прибитий до **константи нижче 20** (нашої штатної стелі) і
   `db_pool_waiting > 0` при **звичайному** rps;
2. у `docker inspect` контейнера api немає `DB_POOL_MAX=20` (змінну загубили або
   перейменували).

Обидві збіглися → це клас інциденту 2026-10-14 (див. `docs/rca.md`): лікується
конфігом/відкатом, рестарт **не** допоможе.

## Що робити

| Ситуація | Дія | Команда | Ризик / що перевірити після |
|---|---|---|---|
| Був деплой, причина не очевидна | Відкат на попередню версію | `cd /opt/poshtomat && IMAGE=<попередній тег з deploys.log> docker compose up -d` | найшвидший шлях; після — p95/error_rate 10 хв; запиши дію в deploys.log |
| `DB_POOL_MAX` загублено/перейменовано в compose | Поверни правильну назву/значення і перезапусти | виправити `compose.yaml` → `docker compose up -d` | перевір `docker inspect … \| grep DB_POOL_MAX` → `=20`; у репо зміну має зловити `npm run check:deploy` (правило C5) |
| Пул чесно замалий (rps виріс надовго) | Підніми `DB_POOL_MAX` помірно (20 → 30), слідкуй за PostgreSQL | те саме | не перевищуй можливості PostgreSQL на 4 GB VM; дивись `pg_stat_activity` |
| PostgreSQL не відповідає | Диск/пам'ять/бекап: дивись `df -h`, `free -m`, `/var/log/poshtomat/backup.log` | — | 02:00–02:30 база у read-only (`docs/ops/backup-runbook.md`) — записи в цей час падають штатно |
| Нічого з переліченого | Збери зріз (логи 10 хв, метрики, `docker ps`, `inspect`) і ескалюй | — | не рестарт наосліп: інцидент 14.10 показав, що рестарт маскує час, а не лікує |

## Коли ескалювати і кого кликати

- 15 хв без зрозумілої причини **або** будь-який відкат не повернув метрики → другий
  розробник (не-черговий цього тижня), `#poshtomat-oncall`.
- Підозра на втрату/витік персональних даних (телефони) → dpo@example.org протягом доби.
- Проблема на боці SMS-провайдера, що триває > 1 год → support@sms.example.net і
  статус-сторінка status.sms.example.net (це про затримку SMS, не про 5xx API).

## Як переконатися, що все гаразд

- 10 хв поспіль: `p95_ms` < 300, `error_rate` < 0.005, `db_pool_waiting` = 0,
  `db_pool_in_use` коливається (не константа-стеля).
- Обидва page-алерти перейшли в resolved.
- Тестовий `POST /pickup` з вигаданим кодом → `404` за < 0,5 с; реальна видача на
  найближчому поштоматі (попроси персонал) проходить.
- Запис у `#poshtomat-oncall`: що бачили, що зробили, що лишилося на розбір.
