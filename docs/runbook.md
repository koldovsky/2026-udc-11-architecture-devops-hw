# Runbook: API віддає 503 «Сервіс зайнятий» (`ApiLatencyP95High` + `Api5xxRateHigh`)

> Для чергового, який цього інциденту не бачив. Команди — для VM `poshtomat-prod-1`, з кореня репо
> (`docker compose -f deploy/compose.yaml …`). **Команди на проді не перевірялися** — вони взяті з
> `deploy/compose.yaml`, `incident/deploys.log` і `docs/ops/backup-runbook.md`; перший раз виконайте їх
> обережно. Те, що можна було перевірити в репо (читання конфігу, формат логів), перевірено.

- **Алерт(и):** `ApiLatencyP95High` — `p95_ms > 2000` протягом 3 хв (page); `Api5xxRateHigh` — `error_rate > 0.05` протягом 3 хв (page). Часто разом: `db_pool_waiting > 0`.
- **Що це означає для користувачів:** екран поштомата після введення коду пише «Сервіс зайнятий, спробуйте пізніше» — мешканці не можуть забрати посилку; служба доставки не може зареєструвати нову (`/parcels` теж 503).
- **Скільки є часу:** вплив повний від першої 503. 14.10.2026 p95 перевищив 2000 мс на 1-й хвилині після деплою, а частка 5xx — на 2-й; пейдж прийшов через ≈4 хв. Рахуйте, що 10 % запитів уже падають.

## Перші 5 хвилин

1. Чи був реліз або зміна конфігу за останні 30 хв? дивіться історію розгортань (на момент написання її копія — `incident/deploys.log`; де вона лежить на VM, у репо не зазначено — уточніть і впишіть сюди). **Якщо так — відкочуйте одразу, причину шукайте після** (розділ «Що робити», рядок 1). 14.10 відкат виправив усе за 2 хв, а пошук причини 43 хв нічого не дав.
2. Чи справді причина в пулі з'єднань? Рядок про `db pool wait timeout` має бути в логу:
   `docker compose -f deploy/compose.yaml logs --since 10m api | grep -c 'db pool wait timeout after'`
   — число > 0 означає «так, пул»; `0` — це інша причина, переходьте до «Діагностики».
3. Не дивіться спершу на SMS-провайдера, heap і `TLS handshake timeout`: ці сигнали бувають і в нормальні дні (14.10 і 13.10 однакові), `docs/rca.md`, розділ «Що з даних НЕ є причиною».

## Діагностика

| Питання | Команда | Як читати результат |
|---|---|---|
| Скільки 503 за останні 10 хв? | `docker compose -f deploy/compose.yaml logs --since 10m api \| grep -c '"status":503'` | десятки — активний інцидент; `0` — алерт міг закритися або причина не в пулі |
| Яка помилка в 503? | `docker compose -f deploy/compose.yaml logs --since 10m api \| grep '"status":503' \| grep -o '"error":"[^"]*"' \| sort \| uniq -c` | `db pool wait timeout after 2000ms` — пул; інакше — шукайте текст помилки |
| Який розмір пулу використовує працюючий API? | `docker compose -f deploy/compose.yaml exec api node -e 'import("./src/config.js").then(m=>console.log(m.loadConfig().dbPoolMax))'` | у проді має бути `20`; **`4` — спрацював тихий дефолт** (змінну не прочитано) |
| Що compose передає контейнеру? | `docker compose -f deploy/compose.yaml exec api env \| grep '^DB_POOL'` | має бути `DB_POOL_MAX=20` і `DB_POOL_WAIT_MS=2000`; якщо тут `DB_POOL_SIZE` — це та сама помилка, що 14.10 |
| Яка версія працює? | `docker compose -f deploy/compose.yaml logs api \| grep '"msg":"service started"' \| tail -n 1` | поле `version`; порівняйте з останнім записом в історії розгортань |
| Чи був реліз перед початком? | історія розгортань (див. «Перші 5 хвилин», крок 1): `grep "$(date +%Y-%m-%d)" <шлях до історії розгортань>` | рядок `deploy`/`restart` за кілька хвилин до першої 503 — підозрюваний |
| Чи пул справді стоїть на стелі? | у моніторингу: `db_pool_in_use` = константа, `db_pool_waiting` > 0 | `in_use` рівно 4 усю годину і `waiting` 15–23 — ознака стелі; витік виглядав би як повільне зростання |
| Чи живий процес? | `curl -s localhost:8080/health` | `{"status":"ok",…}` **не означає, що все добре**: цей endpoint не торкається БД |

## Як підтвердити причину

Два факти відрізняють цю причину від інших (SMS, пам'ять, кур'єр): (1) у 503 — рівно `db pool wait timeout after 2000ms`; (2) `db_pool_in_use` дорівнює **константі 4** (меншій за звичайні 10–13 у пік), а `db_pool_waiting` стабільно > 0. Якщо обидва — це стеля пулу, а не навантаження: рестарт процесу не допоможе (14:20 нічого не змінило), потрібно змінити конфіг або відкотити реліз.

## Що робити

| Ситуація | Дія | Команда | Ризик / що перевірити після |
|---|---|---|---|
| Щойно був реліз, і 503 почалися одразу після нього | Відкотити на попередню версію | повернути `deploy/compose.yaml` з попереднього релізу (`git log -n 5 -- deploy/compose.yaml`, потім `git checkout <коміт> -- deploy/compose.yaml`) і `docker compose -f deploy/compose.yaml up -d` | Це припущення про процедуру (як саме відкочували 14.10, у `deploys.log` не записано) — підтвердьте з тим, хто відкочував. Після: p95 < 300 мс за 2–3 хв, `db_pool_in_use` > 4 |
| Пул 4, а в compose стоїть `DB_POOL_SIZE` (змінну перейменовано) | Виправити ім'я в `deploy/compose.yaml` на `DB_POOL_MAX: "20"` в обох сервісах | редагувати файл, потім `docker compose -f deploy/compose.yaml up -d` | Перевірте обидва сервіси (`api` і `worker`); після рестарту знову виконайте команду про `dbPoolMax` → `20` |
| Релізу не було, 503 про пул, пул 20 | Подивитись, чи не повільна БД (бекап 02:00–02:30 блокує запис — `docs/ops/backup-runbook.md:10-12`) | `sudo tail -n 20 /var/log/poshtomat/backup.log` | Якщо збіг із вікном бекапу — чекати до 02:30; запис у БД у цей час чекає або падає за дизайном |
| 503 немає, але алерт висить | Алерти закриваються самі через 3 хв після нормалізації; якщо ні — перевірити `p95_ms` у моніторингу | — | Не закривайте вручну, поки метрики не повернулися |

## Коли ескалювати і кого кликати

- Відкат не допоміг за 10 хв, або в логах 503 з іншим текстом (не `db pool wait timeout`) → друга людина з команди (поточний тиждень — чергова, інший розробник — на зв'язку) у `#poshtomat-oncall` і `poshtomat-team@example.org`.
- Бекап падає кілька ночей поспіль, а 503 лишаються після 02:30 → `#poshtomat-oncall` і `poshtomat-team@example.org` (`docs/ops/backup-runbook.md:41-42`).
- Якщо торкнулися персональних даних (логи з номерами телефонів тощо) → повідомити відповідальну за захист даних dpo@example.org протягом доби (`materials/compliance.md:25-26`).
- Гаряча лінія працює пн–пт 9:00–18:00; у вихідні — лише форма на сайті (`materials/feature-brief.md:45-46`), тому в позаробочий час симптом ви побачите лише з алертів — не чекайте скарг.

## Як переконатися, що все гаразд

- `p95_ms` повернувся до 150–300 мс протягом 2–3 хв після дії; `error_rate` < 0.01; `db_pool_waiting` = 0.
- Команда про розмір пулу показує `20`; в логу немає нових рядків `db pool wait timeout` за останні 5 хв: `docker compose -f deploy/compose.yaml logs --since 5m api | grep -c 'db pool wait timeout'` → `0`.
- Алерти `ApiLatencyP95High` і `Api5xxRateHigh` закрилися самі.
- Напишіть у `#poshtomat-oncall`, що саме зробили і о котрій, і створіть тікет на розбір.
